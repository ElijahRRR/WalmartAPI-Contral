# 标准选品执行流程

本技能是**项目级技能**，随仓库提交，只在本仓库内使用。一轮选品通常跨两三天，中间会被卖家精灵额度、断网、审核低谷时段打断。本文把它写成一个**可随时中断、随时接着跑的闭环**：每次被唤起都从第一节的推进循环开始，进度只认磁盘和真实系统。

路径约定（全部相对路径）：
- **仓库命令**：在 WalmartAPI-Contral 仓库根目录执行，解释器 `.venv/bin/python`；文中 `cli.py …` 都指 `.venv/bin/python cli.py …`。
- **参考资料**：类目标准 v2 的两个 CSV 不进 git，放在 `<DATA_ROOT>/reference/category_standard/`，文中写作 `reference/…`。
- **`<DATA_ROOT>`**：默认是与仓库平级的 `WalmartAPI_data` 目录（设置了环境变量 `WALMART_DATA_ROOT` 时以它为准，见 `registry/paths.data_root()`）；密钥文件 `.env` 也在这个目录里，不在仓库里，内容不许输出。
- **`<RUN>`**：本周工作目录 `<DATA_ROOT>/exports/selection/<ISO周，如 2026-W48>/`。ISO 周按本机日期算。
- **时间**：文中的钟点都是北京时间。调度按本机时区跑，本机不是北京时间就先换算。
- `<…>` 替换为本轮实际值。

## 〇、红线（每一步都适用）

1. **没有审核结论的候选不许进预览。** 采集、检查、审核任何一段没走完，都不许跑分配预览，也不许出"先看一版"的分配表。审核被时段卡住时只能等，不能绕。
2. **每个候选只有三种去处**：继续往下走、落进一个有名字的终态（带原因）、或者在等一个写明了的条件。不许凭空消失，不许"先不管"。
3. **进度只认磁盘和真实系统，不认对话记忆。** 每次被唤起先读 `state.json`，再到数据库、采集器、卖家精灵、飞书核对。
4. **写操作只走 `cli.py` 工作流，直接真跑，不需要 `--dry-run`**：写入内容在所有者确认预览时已经核过。`from_csv` 三个入口真跑时也会先整份校验，任一行不过就整批拒绝、一行不写。编排脚本**只读**：连库用 `registry.db.pg_conn()`，开只读事务。不在脚本里直接写飞书或写库（采集的提交、记账、入库用现成的 `submit_batch`、`scrape_batches.record`、`pump_batch`，这三个除外）。
5. **所有者在关键节点控制，智能体不跨过节点。** 写进表格就等于执行（上架表写入后，当天 18:10 `audit_sheet` 审、20:00 `list_new` 上架；删除表写入后，15:00 `product_clear` 执行）。只有在所有者确认 I 段预览之后，才进入 J 段写占用、写表；确认范围之外不多写一行。
6. **身份键统一：** 产品 = 标准 ASIN（`services.sku_asin.is_standard_asin`）；品牌 = `services.brand_key.brand_key(brand, manufacturer)`；在线身份 = `catalog.listing_sources` + `sku_asin.pick_asin`，不从 SKU 解析 ASIN。
7. **不释放占用。** 只有已消失或已终止的店，在所有者明确授权后，才走 `store_release`。店铺暂停、产品下架、删除都不构成释放理由。
8. **结果不确定先对账，不盲目重提。** 写操作永不自动兜底。
9. **条件放宽到头仍不够时**，汇报真实缺口并询问所有者，不自行改价格、配送、类目、评分等条件。
10. **遇到本文没写的情况不自创流程**：记进 `events.log`，把该环节标成受阻（`need_owner`），继续推进其他环节，最后问所有者。

## 一、推进循环（每次被唤起都从这里开始）

"开始本周选品"和"继续本周选品"是同一件事，都执行下面的循环。

1. **定位本轮。** 在 `<DATA_ROOT>/exports/selection/` 下找最新的、`status` 不是 `done / abandoned / superseded` 的 `state.json`：
   - 属于本周 → 续跑。
   - 属于更早的周：
     - `executing` 或 `verifying` → 先把它跑完。已经写了占用或表格的那一轮不许丢下。
     - `awaiting_owner` → 所有者这次明确说确认那份预览，就执行它；否则标 `superseded`，在进度卡里写"上周预览已作废"，然后新建本周。
     - `collecting` → 标 `abandoned`，新建本周。它审过的结论留在库里，本周会自动复用。
   - 一个都没有 → 新建本周目录和 `state.json`，从 A 段开始。
   - 所有者明确说"重新开始" → 当前这轮还没到 `executing` 的标 `abandoned`，目录保留，再新建；已经到 `executing` 的先跑完。
2. **占锁。** 读 `<RUN>/run.lock`（会话标识 + `heartbeat`）。`heartbeat` 在 30 分钟以内 = 另一个会话正在跑：本次不做任何动作，直接结束（所有者明确说上一个会话已经断了，才直接接管）。否则写入自己的标识接管，此后每次落盘都更新 `heartbeat`，长动作中途至少每 10 分钟更新一次。
3. **对账。** `state.json` 里所有"进行中"的动作，逐个到真实系统核对后改成真实状态（规则见第四节"中断后的对账"）。然后跑一遍第二节的对账恒等式。
4. **推进。** 按第三节环节总表，找"入口闸成立、出口闸未成立、没有受阻"的环节，执行它的下一个动作；做完立刻落盘、核对，再回到本步。D、E、F、G 四个环节是流水线，**谁能动就推谁**，不等前一个环节整段做完：卖家精灵还在导，前面导出的就可以先采、先检查、先审。
5. **受阻就绕开。** 在 `state.json` 里记下受阻原因和最早恢复时间，转去推别的环节。全部环节都受阻时按第四节等待，到点回到第 3 步。
6. **只有三种情况可以停下：**
   - 预览已交付，等所有者确认（I 段）；
   - 剩下的环节全都卡在需要所有者亲自处理的事上（如卖家精灵登录失效）。还有环节只是在等时间的，先等、先推，不算这一种；
   - 全部完成（K 段出了最终报告）。

   停下前输出进度卡（第七节）。除此之外，不许以"今天先到这里""其余下次再做"为由结束。

**每个动作之前自问三件事，任何一个答不上就不做：**
- 这是环节总表里当前环节的下一个动作吗？
- 入口闸是刚用文件或 SQL 核对过的，还是凭印象？
- 做完以后拿什么证明它做完了？

## 二、台账

`<RUN>/` 下的文件：

| 文件 | 内容 |
|---|---|
| `state.json` | 本轮运行状态（见下） |
| `ledger.csv` | 逐款台账：本轮取得的每个 ASIN 一行，记录它走到哪了 |
| `sprite_plan.csv` | 卖家精灵查询计划与导出记录 |
| `events.log` | 追加式流水：时间、环节、动作、结果、数量 |
| `exports/` `batches/` `f/` `audit/` `preview/` `exec/` `logs/` | 导出原件、采集清单、检查结果、审核块、预览、执行清单、命令日志 |
| `run.lock` | 会话锁 |

落盘规则：
- **先落盘意图，再执行，再落盘结果。** 例如提交采集前，先把清单写进 `batches/`、把批次记成 `planned`。
- **每个最小动作落一次盘**（一次导出、一个批次、一批检查、一个审核块）。中断最多丢一个动作。
- 写文件用"写临时文件再改名"，不留半截文件。

### state.json 至少包含

```json
{
  "week": "2026-W48",
  "status": "collecting",
  "round": 1,
  "gap": {"computed_at": "…", "stores": {"<店>": {"有效目标": 0, "在线": 0, "有效待上架": 0, "缺口": 0}}, "倍数": 3, "初选量": 0},
  "lanes": {
    "D": {"stage": "S1", "target": 0, "got": 0, "ladder_exhausted": false, "done": false, "blocked": null},
    "E": {"batches": [{"name": "sel_2026W48_r1_b001", "batch_id": null, "n": 0, "status": "planned", "submitted_at": null, "pump": null}], "blocked": null},
    "F": {"batches_done": 0, "blocked": null},
    "G": {"chunks": [{"no": 1, "file": "audit/chunk_001.txt", "n": 0, "pid": null, "started_at": null, "finished_at": null, "exit": null, "summary": null, "judged": 0}], "rate_per_min": null, "fail_streak": 0, "blocked": null},
    "H": {"fresh_at": null, "gate_checked_at": null, "runs": []}
```

`status` 取值：`collecting`（A–H）、`awaiting_owner`（I）、`executing`（J）、`verifying`（K）、`done`、`abandoned`、`superseded`。
`blocked` 的形状：`{"reason": "…", "resume_at": "…", "need_owner": false, "since": "…"}`。

### ledger.csv

列：`asin, 来源, 轮次, 状态, 原因, 批次名, 快照时间, F1, F2, F依据, 审前状态, 审核状态, 审核版本, 审核时间, 送审次数, 分配店, 未分到原因, 更新时间`。
同一个 ASIN 只有一行；再次被导出时只在「来源」里追加，不新增行。

| 状态 | 含义 | 由哪个环节接手 |
|---|---|---|
| `new` | 已取得，还没编进采集批次 | E |
| `scraping` | 已编进批次（批次名在行上） | E |
| `ingested` | 本轮快照已入库且有标题 | F |
| `f_pass` | 检查通过，等确定审核去向 | G |
| `audit_wait` | 需要审核，还没有结论 | G |
| `pending_retry` | 审过一次、结果待定，满 24 小时后重审一次 | G |
| `approved` | 审核通过，且是当前规则版本 | H |
| `x_invalid` | 终态：编号不合法 | — |
| `x_scrape` | 终态：采集失败（原因写明） | — |
| `x_supply` | 终态：供货条件不符（哪一条写明） | — |
| `x_model` | 终态：经营模式排除（依据写明） | — |
| `x_hold` | 终态：待核，交所有者决定 | — |
| `x_rejected` | 终态：审核拒绝 | — |
| `x_pending` | 终态：审核两次仍待定 | — |

`approved` 的款在预览里要么有「分配店」，要么有「未分到原因」。

### 对账恒等式

每次改完 `ledger.csv` 都算一遍。**任何一条不成立就停止推进，先查清差在哪**，查清并修正后再继续，过程写进 `events.log`：

1. ledger 行数 = `exports/` 全部导出文件加 D1 清单合并去重后的编号数。
2. 每个采集批次：提交数 = 该批次里已是 `ingested` 及之后状态的 + `x_scrape` 的 + 已转进重采批次的。
3. 进过 F 的数量 = `x_supply` + `x_model` + `x_hold` + `f_pass` 及之后状态的。
4. `f_pass` 及之后状态的数量 = `f_pass` + `audit_wait` + `pending_retry` + `approved` + `x_rejected` + `x_pending`。
5. 预览之后：`pool.csv` 行数 = 有分配店的 + 各「未分到原因」之和。

## 三、环节总表

| 环节 | 入口闸 | 出口闸（全部成立才算完成） | 可能受阻于 |
|---|---|---|---|
| A–C 盘点与缺口 | 新的一轮；或上次计算已超过 24 小时；或 H 入口重算 | `state.gap` 里每家在营店都有「有效目标/缺口」或「不分配（原因）」；初选量已算出 | 数据库、飞书连不上 |
| D 候选 | C 完成 | 独立 ASIN 数 ≥ 累计初选量，或阶梯和查询计划全部走完（`ladder_exhausted`）；每个计划项都是 已导出 / 已拆分 / 零结果 之一；导出记录与卖家精灵"导出历史"对得上 | 当日额度、登录失效、断网 |
| E 采集入库 | ledger 有 `new` 行 | `new` = 0 且 `scraping` = 0；每个批次都是 `closed` | 采集器连不上、批次没落定 |
| F 检查 | ledger 有 `ingested` 行 | `ingested` = 0 | 数据库连不上 |
| G 审核 | 有 `f_pass`、`audit_wait` 或到期的 `pending_retry` | 三者都为 0，并通过"审核结论 SQL"复核 | 高峰时段、调度保留时段、锁、LLM 或网络故障 |
| H 预览分配 | **预览总闸**（见下）全部成立 | 预览成功产出；`pool.csv` 每一行都有分配店或未分到原因；循环判定已做 | 数据库、飞书连不上 |
| I 交付 | H 完成且循环判定为"交付" | 预览 Excel 和对账表已交给所有者；`status = awaiting_owner` | 等所有者 |
| J 执行 | 所有者明确确认（原话和时间已记录） | J1–J5 每一步 `done`，且回读核对通过 | 写表避让时段、锁、连不上 |
| K 核验 | J 完成 | 执行清单每一行都有最终结果，或写表满 3 天后标"未落定"；最终报告已交付；`status = done` | 等调度执行 |

### 预览总闸（H 的入口，五条逐条核对，结果写进 `state.lanes.H`）

1. D 的出口闸成立。
2. ledger 中 `new`、`scraping`、`ingested`、`f_pass`、`audit_wait` 五种状态合计为 0。
3. 到期的 `pending_retry` 为 0。没到期的留在原状态，不挡预览，但在预览里单列"审核待定"。
4. 对 ledger 中全部通过了 F 的 ASIN 跑"审核结论 SQL"（G4），结果必须是：不在库 0、未审 0、旧版本通过 0，`pending` 数等于 ledger 里 `pending_retry` + `x_pending` 的数。不成立就按 G1 的规则用库里的现值重新定去向，回 G。
5. `pool.csv` 等于 ledger 里全部 `approved` 的 ASIN，一个不多、一个不少。

系统侧还有一道保险：`pool.csv` 里只要有一个不在库或没有审核结论的 ASIN，`alloc_plan -p pool_csv=` 会整份拒绝（⛔）。**遇到这个拒绝说明前面的闸没核对好，回 E 或 G 补齐；不许从 `pool.csv` 里删掉它们来换取通过。**

## 四、受阻、等待与续跑

### 受阻怎么处理

| 情况 | 处理 | 什么时候恢复 |
|---|---|---|
| 卖家精灵当日导出次数用完（50 次，或页面提示上限） | D 记受阻；E、F、G 继续消化已经取得的 | 次日 00:05，以页面显示的剩余次数为准 |
| 卖家精灵登录失效、出验证码、页面读不到结果数，或浏览器工具不可用 | D 记受阻，`need_owner = true`；其他环节继续 | 所有者处理后 |
| 断网，或数据库、飞书、采集器连不上 | 相关环节记受阻；按 2、5、10、20、30 分钟退避重试，之后每 30 分钟一次。同一原因连续 6 小时没恢复，转 `need_owner` | 连上后 |
| 现在是 LLM 高峰时段，或在调度保留时段内 | G 记受阻；H0 的刷新同样要等 | 下一个审核窗口的起点（G2） |
| `cli.py` 退出码 3（同名工作流正在跑，锁被占） | 不算失败，不计入失败次数和送审次数 | 10 分钟后重新判断 |
| 审核块异常退出（退出码 1） | 按 G4 认领已审完的，其余留在 `audit_wait`；`fail_streak` 加 1，等 15、30、60 分钟后再开下一块；连续 3 块失败转 `need_owner` | 见左 |
| 采集批次迟迟不落定 | 每 20 分钟查一次；超过 2 小时在进度卡里写明，继续查 | 落定后 |
| 写表避让时段（J 段） | J 对应步骤记受阻 | 避让时段结束 |
| 对账恒等式不成立 | 全部环节暂停，先查清；查不清转 `need_owner`，把差异明细交给所有者 | 查清并修正后 |

### 怎么等

全部环节都受阻时，取最早的 `resume_at`，**在会话里等到那个时间**：用一条阻塞命令循环 sleep，每 60 秒更新一次 `run.lock` 的 `heartbeat`，到点退出；工具对单条命令有时长上限就分段执行。醒来回到推进循环第 3 步。

会话被环境终止、机器休眠、断电都没关系：下一次"继续本周选品"会从磁盘接上，已经做完的不会重做。

### 中断后的对账（推进循环第 3 步）

| `state.json` 里停在 | 怎么核对 | 结论 |
|---|---|---|
| 卖家精灵导出进行中 | 看卖家精灵"导出历史"有没有这条查询，本地 `exports/` 有没有文件 | 历史有、本地没有 → 从历史重新下载，不消耗次数；都没有 → 计划项回到"未导出" |
| 采集批次 `planned` | 用同一个批次名、同一份清单提交 | 成功 = 之前没交上；抛 `BatchExistsError` = 已经建过，拿它带回的 batch_id 继续 |
| 采集批次已提交、未入库 | `batch_status` 看是否落定；`pump_batch` 可以重复跑（按记录去重） | 按 E 段继续 |
| F 的一批进行中 | 该批结果文件行数等于输入数才算完成 | 不完整就整批重判 |
| 审核块 `started` | 进程还在（pid 存活）→ 继续等；不在了 → 按 G4 认账 | 已审的认领，没审的回 `audit_wait` |
| 预览进行中 | 只读，直接重跑 | — |
| J 的某一步进行中 | 回读真实系统（占用、上架表、删除表），见 J 段各步的"续跑" | — |

## 五、各环节细则

## A. 盘点（只读）

### A1 店铺范围
在营店 = `services.stores.enabled_names()` ∩ 限额表「店铺状态」= ACTIVE（支付状态取 `ops.store_kpi_daily` 最新一天 ACTIVE），扣除谭总系（`services.alloc_survey.is_excluded()`）。SUSPENDED/售出/终止/TERMINATED 的店不分配，但**仍持有占用**，H 段单列"品牌归属店不在本轮范围"。

### A2 配置（飞书「定价及上下架限制」表，`registry.resources.RETIRE_LIMITS`）
- 用 `api.feishu.list_records()` 读**原始值**（不要用 `store_limits.setup_limits()` —— 它把 0 当未填回落 5000）。
- `有效目标 = min(单店最大在线数, 商品上限)`；**任一为 0 或空 = 本轮不分配**（例：81刘何秀、A170毕海威、C021李小玲 商品上限 0）。系统 `alloc_plan` 不读商品上限，这条只能由编排拦，执行 CSV 不得含这些店。
- 商品上限是沃尔玛口径（按目录全部未缺席 item 计）；它小于单店最大在线数时（如 5000/1000/250 的店）用目录总数算余量。
- 同表还读：目标销售额/目标订单（日）、配送限制（规划内店均为 fba）、配送时长限制、类目 1/2/3。经营优先级：销售额优先，订单数其次。

## B. 经营分析与在架三分类（只读）

### B1 逐店经营分析
- 近 15 天、近 30 天，并与前 30 天对比的销量和销售额（`orders.order_lines`，按 `order_date`，排除 Cancelled，金额为毛额）。
- 在线 SKU 数、动销 SKU 数、动销率、每在线货位销售额。
- 亚马逊类目、沃尔玛类目、亚马逊采购价带分别统计。
- 最新有效绩效；按佣金和放款日估算余额。

产出：逐店判断，以及优先补的类目、价带、渠道。不能凭"高价品更多"推断销售额会上升。

### B2 统一退货率口径（B、C、D、F 共用同一段 SQL）
- 分子：90 天内**已成熟**订单（下单满 30 天）的实物退货件数。实物退货 = `orders.return_lines` 中 `return_method <> 'KEEP_ITEM'` 且 `is_keep_it` 不为真。通过 `order_line_id` 关联 `order_lines.asin`。
- 分母：同一批订单的件数，只用 API 期订单（`source IS NULL`）。
- 同时给出样本量。样本少于 10 件时只作"观察"。

### B3 在架三分类
- **建议下架**：持续缺货（≥3 个采集日、跨度 ≥7 天，且最新有效数据仍缺货）；高退货（B2 口径 >30% 且样本 ≥10）；长期低需求且 BSR 偏弱，并且有合理替代。
- **建议保留**：本店或他店有成交；BSR 在同类成交参照中较好或持续改善（≥25%）；供货正常。
- **继续观察**：历史不足、类目变化、短期缺货、排名改善中、样本少、用途待核、替代不足。

BSR 规则：近 60 天，最近 7 天中位数对比此前 21 天中位数；7 天窗口至少 3 个点、21 天窗口至少 7 个点；只比较同一 BSR 类目；参照组优先同类目同价带，不足时扩大到同类目。
BSR 取 `catalog.snapshots` 每次采集里的 BSR 字段（采集器已实测提供；字段在 `raw` 中，按采集器契约的键名读取，带类目一起读）。

其他规则：
- 60 天无单只是线索，不直接删除；不设每店删除比例上限。
- 本轮候选已在线且又在删除名单里的，保留在原店。
- 弱表现品没有足够替代时暂缓腾位。
- 已在 `ops.dispositions` 自动删除链中的 SKU 不重复列入，只引用。

## C. 缺口与初选量（只读）

按店计算（有效目标为 0 的店直接跳过）：

```
有效目标 = min(单店最大在线数, 商品上限)
预览缺口 = max(有效目标 − (在线 + 有效待上架 − 建议下架中仍在线的), 0)
```

- 商品上限是约束项的店，括号里的"在线"换成目录总数（含 UNPUBLISHED），"建议下架"只扣**删除**（停用是否释放沃尔玛名额以实测为准）。
- 在线已超有效目标的店（如 A106、A173、A175）缺口为 0，并在预览中标出超出数。
- 新公式扣减待上架，与系统既定的"占位不消耗容量"口径不同，**只在本编排中使用**，预览中写明。
- 缺口按 准入类目 × 货期上限 分桶汇总（规划内店都是 FBA）。
- `初选量 = Σ缺口 × 倍数`。倍数默认 3，或按上一轮实测漏斗（导出独立 ASIN 数 ÷ 可分配数）估算，取较大值并写进预览。数据库候选（D1）计入初选量，按独立 ASIN 计。

A–C 的结果写进 `state.gap`。超过 24 小时就重算一次（只读），差异记进 `events.log`；已经取得的候选不重做。H 入口还会再重算一次。

## D. 候选

### D1 数据库候选（只读）

### D2 卖家精灵（浏览器）
用保留的模板和确认的类目清单（类目标准 v2，`reference/卖家精灵勾选清单.csv`），不加回已删除的大类。

固定条件：价格 0–40、FBA、月销量 ≥20、评分 ≥4、上架时间近 1 年，BSR 增长率不限。

放宽阶梯（按阶段编号推进，**只进不退**；循环轮次从上一轮停下的地方继续）：

| 阶段 | 初选量 <50,000 | 初选量 ≥50,000（恰好 50,000 归这边） |
|---|---|---|
| S1 | 评论 ≥20，变体 1 | — |
| S2 | 5 ≤ 评论 ≤ 19，变体 1（只补 S1 没覆盖的区间） | 评论 ≥5，变体 1（起点） |
| S3 | 补选：评论 ≥5，变体 2–5 | 补选：评论 ≥5，变体 2–5 |

**先排计划，再执行。** `sprite_plan.csv` 每行一个计划项：阶段、类目组、价格区间、评论条件、变体条件、状态（未导出 / 已导出 / 已拆分 / 零结果）、页面结果数、导出编号、文件名、文件行数、导出时间。

- 顺序：家居 → 庭院 → 办公 → 户外运动 → 宠物 → 其他保留类目。
- 每次查询结果 ≤2,000 条（19:00–08:00 可到 3,000），尽量接近上限。超了按价格区间拆分，再超继续拆：父项标"已拆分"，子项加进计划。结果少的类目可以合并（条件一致）。
- 每天最多 50 次导出。

每次导出的闭环：
1. **导出前**：读页面上当天剩余次数（以页面为准，state 里的计数只作参考）；确认结果数不超上限；确认"导出历史"里没有同一条查询（有就直接下载，不重新导）。
2. **导出后**：文件存进 `exports/`；核对文件行数和页面结果数，对不上就从导出历史重新下载一次，仍对不上照实记录差异；解析出编号并入 ledger（不合法的记 `x_invalid`，新的记 `new`，已有的只追加来源）；计划项标"已导出"；更新 `lanes.D.got`。

推进与收口：
- 当前阶段的计划项全部完成而 `got < target` → 进入下一阶段，为它排计划。
- S3 的计划项也全部完成仍不足 → `ladder_exhausted = true`，D 完成，差额在预览里如实报告。
- `got ≥ target` → D 完成。没用到的计划项留作"未导出"，下一轮循环从这里接着用。
- 汇总按 ASIN 去重，保留全部来源，不因"库里已有 / 选过 / 交付过"排除。

## E. 采集与入库

1. **组批。** ledger 里 `new` 的行攒到 2,000 个就组一批；D 已完成或受阻时，把剩下的 `new` 全部组批，不等凑整。批次名固定格式 `sel_<周>_r<轮>_b<三位序号>`，例如 `sel_2026W48_r1_b003`。先把清单写进 `batches/<批次名>.txt`、state 里记 `planned`、ledger 行改成 `scraping` 并填批次名，然后才提交。
2. **提交。** `api.scraper.submit_batch("<批次名>", asins, zip_code="", needs_screenshot=False)`，用 `services.scrape_batches.record()` 记台账，保存回执。抛 `BatchExistsError` 表示这个批次已经建过：拿它带回的 batch_id 继续往下走，**不要换名重提**。
3. **等落定。** `scrape_batches.wait_settled(["<批次名>"], 20)`。没落定不算失败，转去推别的环节，20 分钟后再查。
4. **入库。** `services.product_ingest.pump_batch(scraper, db, "<批次名>", limit=1000, max_pages=400)`。**只有 `ok=True` 才算拉完**；`ok=False` 按网络故障退避重试，不要重置全局游标。`gone=True` 表示批次在采集侧已经没了：把这批里还没有本批快照的 ASIN 编进新批次（原名加 `_g1`），原批次标 `gone`（视同 `closed`）。新批次也 `gone` 的，这些款记 `x_scrape`，原因写"采集侧批次两次丢失"。
5. **逐款认账（只读 SQL）。** 批次 completed 不等于数据已入库，以库为准。对该批每个 ASIN：
   - 有一条 `scraped_at ≥ 批次提交时间` 的快照、`scrape_params ->> 'zip_verify'` 不是 `mismatch`、且 `catalog.products.title` 非空 → `ingested`，记下快照时间。每个 ASIN 取本轮最新一条。
   - 否则先跑 `scrape_batches.pull_failures()` 取失败明细（落在 `ops.scrape_failures`），按 `services.scrape_batches` 里的三档归类：
     - `TERMINAL` 档（如解析失败、服务端判不合法）→ `x_scrape`，原因写失败类型。
     - `RETRY_LATER` 档（变体偏移）→ `x_scrape`，原因写"变体偏移，本周不再采"。
     - `RETRYABLE` 档、`unknown`、没有失败记录也没有快照、地区校验不符、无标题 → **重采一次**：编进 `<原批次名>_retry`。重采后仍不成 → `x_scrape`，原因写明。每款最多重采一次。
6. **批次收口。** 该批每个 ASIN 都已经是 `ingested`、`x_scrape` 或转进了别的批次，批次标 `closed`，写对账：提交数 / 入库数 / 失败数（按类型）/ 转重采数。

`product_refresh` 只刷新在线品，不是新候选的上传入口；`cli.py product_ingest` 也不能证明本批已取全。

## F. 供货与经营模式检查（由 AI 直接执行）

对 ledger 里 `ingested` 的行分批处理。**每款恰好落进四个结果之一**：`x_supply`（供货不符）、`x_model`（排除）、`x_hold`（待核）、`f_pass`（可送审）。每批处理完核对"输入数 = 输出数"再落盘。F 不依赖任何时段，随时可以做。

### F1 供货硬条件（脚本判，逐 ASIN，用本批次的快照）
- 单价 >0 且 ≤40（另列落地价 = 单价 + 运费）；FBA；库存 ≥5 且**有确切数量**（系统会把"有货但无数量"按 10 件算，这里要拦）。
- 运费已知；货期 ≤7 天（各店更严的上限由分配引擎按限额表判）。
- 地区校验不是 mismatch；B2 退货率 ≤30%。

任何一条不过 → `x_supply`，原因写是哪一条。数据新鲜度在 H0 和 J1 把关，不在这里。

### F2 经营模式判定（AI 判，不交给人）

只对 F1 通过的款做。每批不超过 200 款，结果写进 `f/f2_<序号>.csv`（asin、结论、依据类型、证据原文片段），再并入 ledger。

依据按顺序使用：
1. 类目标准 v2：`reference/类目标准_v2_全部节点.csv`。用商品的亚马逊类目节点查（最长路径前缀匹配，脚本查表）：
   - 「不选」→ 排除；
   - 「有条件」→ 按该行「核实条件」逐款核对；
   - 「可选」→ 照样做下面的商品级检查。
   类目节点没有规则的，不默认放行，归入待核。
2. 商品级检查：看标题、五点、描述、套装内容，看不出来的再看主图和副图。命中下列任一条即排除：

| 排除项 | 包括 | 不算违规的情况 |

| 带电 | 插电、电池款（含附送电池、纽扣电池）、充电/USB、太阳能、LED 发光、石英钟机芯、电动/电子功能；不通电的电气件（灯座、接线盒/支架、无源转接头、电线电缆）；手电筒、台灯 | 金属丝、绳线等非电线材；纯手动工具 |

## G. 审核（只在低谷时段，分块，逐款认账）

### G1 定去向（只读，对 `f_pass` 的行）
用 G4 的 SQL 读库里的现值，逐款归类：

| 库里的状态 | ledger 改成 |
|---|---|
| approved，且 `audit_version` = 当前 `resources.AUDIT_RULES_VERSION` | `approved`（复用，不花钱） |
| rejected | `x_rejected`（沿用旧结论，不重审） |
| 没有结论；或 approved 但版本落后；或 pending 且上次审核在 24 小时以前（或没有审核时间） | `audit_wait` |
| pending 且上次审核在 24 小时以内 | `pending_retry`，到期时间 = 审核时间 + 24 小时 |
| 不在库，或标题为空 | 不该出现（E 的认账已经拦过）；出现了就按 E 第 5 步重采一次 |

"approved × 旧版本"会真重审、产生费用，数量记进预算。

### G2 审核窗口（每开一块之前都重新判断）
同时满足才能开审：
- a. `resources.llm_price_tier(datetime.now(timezone.utc)) == "offpeak"`。高峰是工作日 9–12 点和 14–18 点，周末全天低谷。**审核工作流自己不会在高峰停下，只能靠这里拦。**
- b. 不在调度保留时段内。手动审核和调度里的审核共用一把锁，占着锁跨进去会把当天的调度挡掉：
  - 12:40 起，到当天 `product_chain` 里那次审核结束为止。
  - 17:50 起，到当天 `audit_sheet` 结束为止。
  
  是否结束查 `ops.runs`：
  ```sql
  SELECT params, started_at, finished_at, status
  FROM ops.runs
  WHERE workflow = 'product_audit' AND started_at > now() - interval '10 hours'
  ORDER BY started_at;
  ```
  `params` 里带 `mode = online` 的是 `product_chain` 那次，带 `from_sheet` 的是 `audit_sheet`。`finished_at` 有值就算结束；还在 `running` 就继续等；查不到当天记录，分别按 15:30、20:30 结束算。调度钟点以 `registry/schedule.py` 的现值为准（现为 13:00 和 18:10）。
- c. 上一块已经认完账，没有本技能自己的审核进程还在跑。
- d. 窗口剩余时间 ≥30 分钟。窗口终点取之后最近的一个：工作日 09:00、工作日 14:00、每天 12:40、每天 17:50。

不满足就把 G 记成受阻，`resume_at` 写下一个窗口的起点，去推别的环节。

### G3 组块与执行
```
可用分钟 = 窗口终点 − 现在 − 20
块大小   = min(8000, 待审数, floor(速率 × 可用分钟))
```
- 速率取最近 3 块实测值（个/分钟）里最小的。还没有实测值时，第一块固定 300 个用来测速，并且要求窗口剩余 ≥120 分钟。
- 算出的块大小不足 100 且小于待审数 → 这个窗口不再开块，等下一个窗口。
- 块里只放 `audit_wait` 和到期的 `pending_retry`。**这个入口是点名强审，传进去的每一个都会真审、真花钱**，所以已有结论的绝不能混进去。
- 先把清单写进 `audit/chunk_<序号>.txt`、state 里记块的 `started_at`，再启动：
  ```
  ( .venv/bin/python cli.py product_audit -p asins=<逗号分隔的本块 ASIN> ; echo "EXIT=$?" ) > <RUN>/logs/audit_chunk_<序号>.log 2>&1 &
  ```
  后台运行，记下 pid。每 5–10 分钟看一次进程是否还在；等待期间继续推别的环节。
- 不用 `force=1`、`force_rerun`、`mode=nonpass`、`mode=pending`，不改审核层级。`--dry-run` 也会产生 LLM 费用，不能当免费预检。
- 块跑过了窗口终点：**不杀进程**，让它跑完；把实测速率记低，并在进度卡里写明超时了多久、是否挡到了调度。

### G4 逐款认账（每块结束后必做，只读）
```sql
SELECT t.asin, p.audit_status, p.audit_version, p.audited_at, p.audit_reason,
       (p.title IS NOT NULL AND p.title <> '') AS has_title
FROM unnest(%(asins)s::text[]) AS t(asin)
LEFT JOIN catalog.products p ON p.marketplace = 'US' AND p.asin = t.asin;
```
对本块每个 ASIN：
- `audited_at ≥ 块的 started_at` = 这一块审到了。approved → `approved`；rejected → `x_rejected`；pending → 第一次送审记 `pending_retry`（到期 = 审核时间 + 24 小时），第二次仍 pending 记 `x_pending`，原因写库里的审核类别。
- 否则 = 这一块没审到它：
  - 块是异常退出的（退出码 1 或 3）→ 留在 `audit_wait`，进下一块，不计送审次数。
  - 块正常结束（退出码 0）却没审到 → 看 `has_title`：标题为空的按 E 第 5 步重采一次（已经重采过的记 `x_scrape`，原因"无标题"）；有标题的留在 `audit_wait`，「送审次数」加 1，满 3 次仍没有结论 → `x_pending`，原因写"三次送审未出结论"。

审核是每 200 个落一次库的，所以块中途断掉时已经审完的不会丢，靠这一步认领回来。**不许把整块原样重跑**：重跑前必须先认账，只带没审到的。

同时记录本块：日志里的摘要行（`product_audit(<版本>):候选 N,判定 M(过 x/拒 y/待定 z)`）、退出码、耗时、实测速率、费用（日志里给了才记，没给写"未知"，不估算）。摘要里的"判定 M"和认账得到的数对不上时，以认账为准并记下差异。

### G5 出口
`f_pass` = 0、`audit_wait` = 0、到期的 `pending_retry` = 0，再对全部通过 F 的 ASIN 跑一遍 G4 的 SQL 复核。成立才算 G 完成。

## H. 预览分配（只读）

### H0 预览前刷新
进入条件：预览总闸的前四条已经成立。预览要用新数据，但刷新可能把个别款打回待审，所以**只在审核窗口开着时做**（G2 的 a、b 两条成立；没开就把 H 记成受阻，`resume_at` 写下一个窗口起点）。24 小时内做过就不重复，时间记在 `lanes.H.fresh_at`。刷新期间这些行的状态不变，只按下面的结果改；刷新批次收口之后才能进 H1。

1. 重算 A3 和 C，得到最新缺口。
2. ledger 里 `approved`、且最新快照超过 24 小时的款：按 E 段流程编一个 `sel_<周>_r<轮>_fresh<序号>` 批次重采、入库、认账。
3. 对重采到的款重跑 F1：不过的改 `x_supply`，原因写"刷新后不符：<哪一条>"。重采失败的再试一次，仍失败改 `x_supply`，原因写"无 24 小时内数据"。
4. 重采后库里审核状态变回 pending 的（商品内容变了，入库时会自动翻回待审）：重做 F2，不通过的按 F2 的结果落终态，通过的改 `audit_wait`，回 G。

### H1 核对预览总闸
逐条核对第三节的五条。有一条不成立就回对应环节，不出预览。

### H2 出预览
**用标准引擎出预览，不在仓库外重组 `alloc_engine`。** 把 ledger 里全部 `approved` 的 ASIN 写成 `preview/pool.csv`（表头 `ASIN`），把最新缺口写成 `preview/quota.csv`（表头 `店铺,配额`，有效目标为 0 的店写 0 或不写），然后跑
`cli.py alloc_plan -p pool_csv=<pool.csv> -p quota_csv=<quota.csv> --dry-run`。
这两个参数只出预览（方案表在 reports 目录），不落占用；限定池默认不设淘汰线。输出以 ⛔ 开头 = 被拒绝，按提示回去补齐，不改清单硬过。

约束：
- 以实时占用为准：品牌唯一去向；同一产品不重复；原占用店符合条件的归原店。
- 归属店不在本轮范围的单列，不算可分配。
- 不释放、不落占用、不写飞书；上一轮没执行的预览不算占用。

### H3 逐款归因
`pool.csv` 的每个 ASIN 都要有去处：方案表里分到了店的，填「分配店」；没分到的，对照预览摘要的漏斗填「未分到原因」（不在候选池：<原因> / 硬闸：<原因> / 已在架 / 没有店的条件容得下 / 组队时剔除 / 品牌归属店不在本轮范围 / 排名靠后没发到）。归不出原因的写"原因待查"，数量大于 0 要写在预览首页。然后核对恒等式第 5 条。

### H4 循环判定
```
剩余缺口 = Σ 各店 max(缺口 − 模拟分配, 0)
```
按顺序判断，命中即止：
1. 剩余缺口 = 0 → 交付（进 I）。
2. `ladder_exhausted = true` → 交付，预览首页写明真实剩余缺口，请所有者决定是否放宽条件。
3. 本轮新增候选里一个可分配的都没有 → 交付并说明。
4. 已经循环 5 轮 → 交付并说明。
5. 其余 → `round` 加 1；`新增初选需求 = 剩余缺口 × 倍数`，倍数取 `max(3, 本周累计独立 ASIN ÷ 累计模拟分配)`；把它加到 `lanes.D.target` 上，D 重新打开，回到推进循环。已取得的候选、已有的审核结论、本轮模拟的品牌归属都沿用。

循环中间的预览不交付所有者，只在进度卡里报数。

## I. 预览交付（等所有者确认）

一份 Excel，包含以下表：
- 首页：本轮结论、剩余缺口、需要所有者决定的事项
- 运营状况分析
- 总览：在线、目录总数、有效待上架、在途、建议下架、在线余量、目录余量、缺口、模拟分配、剩余缺口
- 亚马逊类目 / 沃尔玛类目 / 亚马逊价带销售总览（含 SKU 数和货位产出）
- 删除表：真实 SKU、ASIN、动作（停用或删除）、原因、库存时间、销量、退货样本
- 分配表：店、ASIN、品牌键、采购价、库存、配送、货期、快照时间、审核、占用依据
- 三分类明细（含 BSR 证据和参数）
- 待核（`x_hold`，逐款原因）
- 审核待定（`pending_retry` 和 `x_pending`，逐款原因）
- 未分到（逐款原因）
- 流程对账：ledger 各状态数量、每个采集批次的对账、每个审核块的结果和费用；初选目标 / 已取得候选 / 审核通过 / 可分配 分开列

检查公式、汇总、身份键和明细是否一一对应；对账表的各状态数量之和必须等于 ledger 行数。

交付后 `status = awaiting_owner`，输出进度卡并停下。之后被唤起时：
- 所有者**明确确认**（全部或指定范围）→ 把原话、时间、范围记进 `state.owner`，进 J。
- 所有者要求修改（删行、放行待核、调整删除表）→ 记进 `owner.decisions`。只删行的直接体现在执行清单里；放行待核的款要回 G 审完、再走 H 出新预览、重新交付。
- 所有者没有回复 → 不做任何写操作，输出一行状态后结束。

## J. 确认后执行

`status = executing`。每一步都是"核对前提 → 执行 → 回读核对 → 落盘"，一步 `done` 才做下一步。

**写表避让**：上架表不在 17:50 到当天 `audit_sheet` 结束之间写；删除表不在 14:45 到当天 `product_clear` 结束之间写（结束与否查 `ops.runs`）。在避让时段内就等。18:10 之前写进上架表的当晚上架，之后写的次日上架，在进度卡里告诉所有者是哪一天生效。

1. **J1 复核。**
   - 重新读实时在线、待上架、在途、占用、黑名单、登记簿、`ops.dispositions`。
   - 执行清单里快照超过 24 小时的款：按 H0 第 2–3 步重采、重跑 F1。
   - 用 G4 的 SQL 复核审核状态：不是"approved 且当前版本"的行，此刻审核窗口开着就立即按 G 段审完再定；窗口没开就从执行清单里剔除。
   - 占用、已在架、黑名单发生变化导致不再成立的行，从执行清单里剔除。
   - 所有剔除的行写进 `exec/dropped.csv`（原因逐行写明），进最终报告。
2. **J2 执行容量。** `当前空位 = 有效目标 − 在线(或目录总数) − 有效待上架`，**不预支未完成的删除**；有效目标为 0 的店不进清单。超出空位的行保留原定店，列入"待腾位"，不执行。产出 `exec/exec.csv`（UTF-8，表头 `店铺,ASIN`）。
3. **J3 落占用。** 跑 `cli.py alloc_plan -p from_csv=<exec.csv>`。任一行不过它会整批拒绝、一行不落：按报错剔除问题行（记进 `dropped.csv`）再跑；剔除三次仍被拒绝就停下，请所有者看报错。
   回读：`services.claims.load_active(conn, PRODUCT)` 里清单的每个 ASIN 都归在目标店。
   续跑：先回读。全部已落 = 完成；否则用同一份清单重跑（同一家店的占用可以重复落）。
4. **J4 写上架表。** 跑 `cli.py alloc_push -p from_csv=<exec.csv>`。只写店铺和 ASIN 两列，审核结果留空。已有未弃用 SKU（含 UNPUBLISHED）的会被拦下，单列出来。
   回读：`services.listing_sheet.read_rows()` 里有清单的每个（店, ASIN）。
   续跑：先回读，缺的用同一份清单重跑（表里已有的行会自动跳过）。
5. **J5 写删除表。**
   - 清单 CSV 表头 `店铺,SKU,动作,原因`；SKU 是沃尔玛真实 SKU；动作只写"停用"/"下架"/"删除"，**不能留空**（留空在系统里等于删除）。
   - 跑 `cli.py retire_push -p from_csv=<删除清单.csv>`。它整批校验：店铺在营、SKU 在目录未缺席、自动删除链（`ops.dispositions`）里没有同 SKU 未落定的 delete/retire；任一行不过就整批拒绝，按报错剔除后记录再跑。
   - 回读：`services.clear_sheet.read_rows()` 里有清单的每个（店, SKU）。
   - 续跑：先回读，缺的用同一份清单重跑（表里已有同 SKU 未落定行会自动跳过）。

五步都 `done` 后，把执行清单逐行写进 `exec/verify.csv`（初始结果"已写表"），记 `verify.written_at`，`status = verifying`。

## K. 核验与收尾

执行的结果由调度产生，K 段按时间点去核对，把 `verify.csv` 每一行推到最终结果：

| 什么时候 | 核对什么 | 行结果 |
|---|---|---|
| 当天 `audit_sheet` 结束后 | 上架表本轮各行的「审核结果」 | 审核通过 / 审核拒绝（终） / 仍为空（写明「具体内容」列的原因，次日再看） |
| 当天 `list_new` 结束后 | 行上的 feedid 和「上架结果」 | 已提交 / 上架失败：<原因>（终） / 未处理（次日再看） |
| 次日起，每天一次 | 先 `cli.py feed_poll -p store=<店>`，再 `cli.py catalog_sync -p store=<店> -p skip_feishu=1`，然后查目录 | 上架成功（目录里已 PUBLISHED，终） / 平台拒绝：<原因>（终） |
| `product_clear` 结束后 | 删除表本轮各行的执行结果 | 已停用 / 已删除（终） / 失败：<原因>（终） |

- 依次确认：占用已落库 → 表已写 → 平台已接收 → 逐 SKU 结果 → 目录生效。失败或不确定先对账；删除不释放占用。
- 调度当天该跑没跑（`ops.runs` 里没有记录）：在进度卡里报告并请所有者决定是否手动补跑，不自行补跑。手动的 `cli.py product_audit -p from_sheet=1` 会处理**整张上架表**，`product_clear` 会处理删除表里的全部待办，都不只是本轮的行。手动上架只用实际写进表格的清单：`cli.py list_new -p from_csv=<实际派工清单>`。
- 每一行都到了终态，或者写表已满 3 天（还没落定的标"未落定"并写明停在哪一步）→ 出最终报告：执行数、上架成功、各类失败、未落定、剔除（`dropped.csv`）、待腾位、删除结果。ledger 里还留在 `pending_retry` 的改成 `x_pending`，原因写"本轮结束前未到重审时间"。交给所有者后 `status = done`，删除 `run.lock`。

## 六、禁止事项

- 审核没出完就出预览或分配表，包括"先看一版""部分预览"。
- 为了让闸通过而缩小候选：从 `pool.csv` 或 ledger 里删行，或把在途状态直接改成终态。
- 在高峰时段开审；占着审核锁跨进调度保留时段；杀掉正在跑的审核进程。
- 把整块 ASIN 原样重跑（重跑前必须认账，只带没审到的）。
- 用 `force=1`、`force_rerun`、`mode=nonpass`、`mode=pending`，或拿 `--dry-run` 当免费预检。
- 换批次名重提同一份采集清单；重置采集游标。
- 重新导出卖家精灵导出历史里已有的查询；自行改价格、配送、类目、评分等固定条件。
- 在所有者确认之前写占用、写上架表、写删除表；在确认范围之外多写一行。
- 在脚本里直接写库或写飞书；在仓库外重组分配引擎；释放占用。
- 凭对话记忆判断进度；跳过对账；同一周同时开两个会话。
- 在三种允许的情况之外结束会话。

## 七、进度卡

每次停下、每次进入长等待之前输出，固定格式：

```
【选品 2026-W48】状态 collecting，第 1 轮
缺口 12,400｜初选目标 37,200｜已取得 21,400（卖家精灵 S1，今日导出 50/50）
采集：已入库 18,900｜采集中 2,000｜失败 500
检查：可送审 9,800｜排除 7,900｜待核 300｜供货不符 900
审核：通过 4,200｜拒绝 1,100｜待定 60｜未审 4,440
受阻：卖家精灵额度用尽（明天 00:05 恢复）；审核等窗口（今天 20:35）
下一步：20:35 开第 3 个审核块
需要你：无
```

"需要你"一栏只写必须由所有者处理的事：确认预览、登录卖家精灵、决定是否放宽条件、看拒绝报错。没有就写"无"。
