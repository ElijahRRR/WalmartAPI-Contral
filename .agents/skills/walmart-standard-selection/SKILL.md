# 标准选品执行流程

本技能是**项目级技能**，随仓库提交，只在本仓库内使用。

路径约定（全部相对路径）：
- **仓库命令**：在 WalmartAPI-Contral 仓库根目录执行，解释器 `.venv/bin/python`；文中 `cli.py …` 都指 `.venv/bin/python cli.py …`。
- **参考资料**：类目标准 v2 的两个 CSV 不进 git，放在 `<DATA_ROOT>/reference/category_standard/`，文中写作 `reference/…`，即指这个目录。
- **本周进度与产出**：`<DATA_ROOT>/exports/selection/…`，`<DATA_ROOT>` 默认是与仓库平级的 `WalmartAPI_data` 目录（设置了环境变量 `WALMART_DATA_ROOT` 时以它为准，见 `registry/paths.data_root()`）；密钥文件 `.env` 也在这个目录里，不在仓库里。
- `<…>` 替换为本轮实际值。

## 〇、红线（每一步都适用）

1. **写操作只走 `cli.py` 工作流，直接真跑，不需要 `--dry-run`**：写入内容在所有者确认预览时已经核过。`from_csv` 三个入口真跑时也会先整份校验，任一行不过就整批拒绝、一行不写。编排脚本**只读**：连库用 `registry.db.pg_conn()`，开只读事务。不在脚本里直接写飞书或写库（采集入库用现成的 `pump_batch` 除外）。
2. **所有者在关键节点控制，智能体不跨过节点。** 写进表格就等于执行（上架表写入后，当天 18:10 `audit_sheet` 审、20:00 `list_new` 上架；删除表写入后，15:00 `product_clear` 执行）。因此只有在所有者确认 I 段预览之后，才进入 J 段写占用、写表；确认后按确认的内容直接写入。
3. **身份键统一：** 产品 = 标准 ASIN（`services.sku_asin.is_standard_asin`）；品牌 = `services.brand_key.brand_key(brand, manufacturer)`；在线身份 = `catalog.listing_sources` + `sku_asin.pick_asin`，不从 SKU 解析 ASIN。
4. **不释放占用。** 只有已消失或已终止的店，在所有者明确授权后，才走 `store_release`。店铺暂停、产品下架、删除都不构成释放理由。
5. **结果不确定先对账，不盲目重提。** 写操作永不自动兜底。
6. **条件放宽到头仍不够时**，汇报真实缺口并询问所有者，不自行改价格、配送、类目等条件。
7. **每轮产出存到本周工作目录**（见下方「跨天续跑」），包括参数、各步清单、执行摘要和对账表。

## 跨天续跑（记忆）

一轮选品可能要连续两三天。进度存在本机文件里，**不靠对话记忆**：

- 工作目录：`<DATA_ROOT>/exports/selection/<ISO周，如 2026-W47>/`，核心是 `state.json`，另加各步产出文件。
- **每次开始先读本周的 `state.json`**：
  - 存在且 `status != "done"` → 从记录的位置续跑，不重做已完成的步骤；
  - 不存在（新的一周），或所有者明确说"重新开始" → 新建，从 A 段跑起。上周目录保留不动，只用来参考上一轮漏斗倍数。
- `state.json` 至少记录：
  - `round`（第几轮循环）、`step`（当前段落 A–K）、`status`；
  - A–C 段结果：各店有效目标、缺口、初选量、倍数，以及计算时间；
  - 卖家精灵进度：当前阶段（S1/S2/S3）、类目顺序里已完成到哪、每次导出的（类目、价区间、评论、变体、页面结果数、导出编号、文件名、行数、导出日期）、当天已用导出次数；
  - 已取得的独立 ASIN 数和候选文件路径；
  - 采集批次：批次名、batch_id、提交数、`pump_batch` 结果；
  - 审核：已完成的块、每块的 ASIN 文件、结果、费用；
  - 模拟分配：已定的 品牌→店、ASIN→店；
  - 所有者确认记录（确认了什么、什么时间）。
- **每完成一个小动作就立即落盘**（每次导出、每个批次、每个审核块），中断后最多丢一个动作。
- 续跑时：
  - 已完成的卖家精灵查询**不重查**，按记录接着往下；
  - 超过 24h 的采集数据在 J 段复核时重采，不在续跑时整批重来；
  - A–C 段的缺口如果算出已超过 24h，续跑当天先重算一次缺口（只读），差异写进 state，不重做已取得的候选。

## A. 盘点（只读）

### A1 店铺范围
在营店 = `services.stores.enabled_names()` ∩ 限额表「店铺状态」= ACTIVE（支付状态取 `ops.store_kpi_daily` 最新一天 ACTIVE），扣除谭总系（`services.alloc_survey.is_excluded()`）。SUSPENDED/售出/终止/TERMINATED 的店不分配，但**仍持有占用**，第 H 段单列"品牌归属店不在本轮范围"。

### A2 配置（飞书「定价及上下架限制」表，`registry.resources.RETIRE_LIMITS`）
- 用 `api.feishu.list_records()` 读**原始值**（不要用 `store_limits.setup_limits()` —— 它把 0 当未填回落 5000）。
- `有效目标 = min(单店最大在线数, 商品上限)`；**任一为 0 或空 = 本轮不分配**（例：81刘何秀、A170毕海威、C021李小玲 商品上限 0）。系统 `alloc_plan` 不读商品上限，这条只能由编排拦，执行 CSV 不得含这些店。
- 商品上限是沃尔玛口径（按目录全部未缺席 item 计）；它小于单店最大在线数时（如 5000/1000/250 的店）用目录总数算余量。
- 同表还读：目标销售额/目标订单（日）、配送限制（规划内店均为 fba）、配送时长限制、类目 1/2/3。经营优先级：销售额优先，订单数其次。

### A3 现状数据
| 项 | 来源与口径 |
|---|---|
| 在线 | `catalog.walmart_items`：`missing_since IS NULL AND published_status='PUBLISHED'`，按店计数 |
| 目录总数（硬限用） | `catalog.walmart_items`：`missing_since IS NULL`，任意状态 |
| 有效待上架 | 上架表 `services.listing_sheet.read_rows()` 中同时满足：`是否上架 ∈ {空, No}`、无 feedid、`上架结果 ∉ {SKU_LOCKED, PROHIBITED, CONTENT_REJECTED}`、重试 <3 次、库里审核不是 rejected，且该 (店, ASIN) 当前不在线 |
| 上架在途 | `ops.feed_log` 中状态为 submitted/pending 的 MP_ITEM，与 `ops.feed_items` 关联 |
| 占用 | `services.claims.load_active(conn, BRAND / PRODUCT)` |
| 自动删除链在途 | `ops.dispositions` 中未落定的 delete/retire |

待上架和在途按 (店, ASIN) 合并，同一产品只计一次。
先查各表的最新更新时间。目录确实过旧时，才执行 `cli.py catalog_sync -p store="<店>" -p skip_feishu=1`（会写库，不是纯查询）。

## B. 经营分析与在架三分类（只读）

### B1 逐店经营分析
- 近 15 天、近 30 天，并与前 30 天对比的销量和销售额（`orders.order_lines`，按 `order_date`，排除 Cancelled，金额为毛额）。
- 在线 SKU 数、动销 SKU 数、动销率、每在线货位销售额。
- 亚马逊类目、沃尔玛类目、亚马逊采购价带分别统计。
- 最新有效绩效；按佣金和放款日估算余额。

产出：逐店判断，以及优先补的类目、价带、渠道。不能凭"高价品更多"推断销售额会上升。

### B2 统一退货率口径（第 B、C、D 段共用同一段 SQL）
- 分子：90 天内**已成熟**订单（下单满 30 天）的实物退货件数。实物退货 = `orders.return_lines` 中 `return_method <> 'KEEP_ITEM'` 且 `is_keep_it` 不为真。通过 `order_line_id` 关联 `order_lines.asin`。
- 分母：同一批订单的件数，只用 API 期订单（`source IS NULL`）。
- 同时给出样本量。样本少于 10 件时只作"观察"。

### B3 在架三分类
- **建议下架**：持续缺货（≥3 个采集日、跨度 ≥7 天，且最新有效数据仍缺货）；高退货（B2 口径 >30% 且样本 ≥10）；长期低需求且 BSR 偏弱，并且有合理替代。
- **建议保留**：本店或他店有成交；BSR 在同类成交参照中较好或持续改善（≥25%）；供货正常。
- **继续观察**：历史不足、类目变化、短期缺货、排名改善中、样本少、用途待核、替代不足。

BSR 规则：近 60 天，最近 7 天中位数对比此前 21 天中位数；7 天窗口至少 3 个点、21 天窗口至少 7 个点；只比较同一 BSR 类目；参照组优先同类目同价带，不足时扩大到同类目。
BSR 取 `catalog.snapshots` 每次采集里的 BSR 字段（采集器已实测提供；字段在 `raw` 中，按采集器契约的键名读取，带类目一起读）。

其他规则：
- 60 天无单只是线索，不直接删除；不设每店删除比例上限。
- 本轮候选已在线且又在删除名单里的，保留在原店。
- 弱表现品没有足够替代时暂缓腾位。
- 已在 `ops.dispositions` 自动删除链中的 SKU 不重复列入，只引用。

## C. 缺口与初选量（只读）

按店计算（有效目标为 0 的店直接跳过）：

```
有效目标 = min(单店最大在线数, 商品上限)
预览缺口 = max(有效目标 − (在线 + 有效待上架 − 建议下架中仍在线的), 0)
```

- 商品上限是约束项的店，括号里的"在线"换成目录总数（含 UNPUBLISHED），"建议下架"只扣**删除**（停用是否释放沃尔玛名额以实测为准）。
- 在线已超有效目标的店（如 A106、A173、A175）缺口为 0，并在预览中标出超出数。
- 新公式扣减待上架，与系统既定的"占位不消耗容量"口径不同，**只在本编排中使用**，预览中写明。
- 缺口按 准入类目 × 货期上限 分桶汇总（规划内店都是 FBA）。
- `初选量 = Σ缺口 × 倍数`。倍数默认 3，或按上一轮实测漏斗（可分配数 ÷ 导出独立 ASIN 数）估算，取较大值并写进预览。
- 写明数据库候选（D1）是否计入初选量（默认计入，按独立 ASIN 计）。

## D. 候选

### D1 数据库候选（只读）
当前不在线、累计至少 2 单、B2 退货率 ≤30%，类目和价带符合 B1 方向。保留来源、成交样本、退货率、入选依据。历史审核通过**不等于**可以跳过采集。

### D2 卖家精灵（浏览器）
用保留的模板和确认的类目清单（类目标准 v2，`reference/卖家精灵勾选清单.csv`），不加回已删除的大类。

固定条件：价格 0–40、FBA、月销量 ≥20、评分 ≥4、上架时间近 1 年，BSR 增长率不限。

放宽阶梯（按阶段编号推进，**只进不退**；循环轮次从上一轮停下的阶段继续）：

| 阶段 | 初选量 <50,000 | 初选量 ≥50,000（恰好 50,000 归这边） |
|---|---|---|
| S1 | 评论 ≥20，变体 1 | — |
| S2 | 5 ≤ 评论 ≤ 19，变体 1（只补 S1 没覆盖的区间） | 评论 ≥5，变体 1（起点） |
| S3 | 补选：评论 ≥5，变体 2–5 | 补选：评论 ≥5，变体 2–5 |

已拿到的不丢；独立 ASIN 数达到初选量即停。

查询纪律：
- 顺序：家居 → 庭院 → 办公 → 户外运动 → 宠物 → 其他保留类目。
- 每次查询结果 ≤2,000 条（19:00–08:00 可到 3,000），尽量接近上限。超了按价格区间拆分，再超继续拆；结果少的类目可以合并（条件一致）。
- 每天最多 50 次导出，先排计划再执行。
- 记录每次导出的类目、价区间、评论、变体、页面结果数、导出编号、文件行数。
- 汇总按 ASIN 去重，保留全部来源，不因"库里已有/选过/交付过"排除。

### D3 采集前不做剔除（所有者定稿 2026-11-19）
D1、D2 的全部合法 ASIN 都进入 E 段采集。「不选」类目节点、ASIN 黑名单、TRO 品牌都**不在采集前剔除**，统一放到 F 段和审核环节判定。

## E. 采集与入库

1. 合法 ASIN 全部提交（非法编号单列，不修改）：`api.scraper.submit_batch("<sel_YYYYMMDD_轮次>", asins, zip_code="", needs_screenshot=False)`。用 `services.scrape_batches.record()` 记台账，保存提交清单和回执。
   - 抛出 `BatchExistsError` 表示已经建过批次：拿它带回的 batch_id 继续往下走，**不要换名重提**。
2. 用 `scrape_batches.wait_settled([...], timeout_min)` 或 `api.scraper.batch_status()` 等批次结束，然后用 `scrape_batches.pull_failures()`（底层是 `batch_failures`）取失败明细。
3. 入库：`services.product_ingest.pump_batch(scraper, db, name, limit=1000, max_pages=400)`。**只有 `ok=True` 才算拉完**；`ok=False` 或 `gone=True` 时如实上报，不要重置全局游标。
4. 对账：提交数 / 接收数 / 成功 / not_found / 解析失败；导出事件数与独立 ASIN 数分开统计；入库数 / 重复数 / 缺失数。
   - 批次 completed 不等于数据已入库，以快照为准。
   - 每个 ASIN 取本轮最新一条，`zip_verify='mismatch'` 的不用，失败不能当成功。

`product_refresh` 只刷新在线品，不是新候选的上传入口；`cli.py product_ingest` 也不能证明本批已取全。

## F. 供货与经营模式检查（由 AI 直接执行）

### F1 供货硬条件（逐 ASIN，用本轮快照）
- 单价 >0 且 ≤40（另列落地价 = 单价 + 运费）；FBA；库存 ≥5 且**有确切数量**（系统会把"有货但无数量"按 10 件算，这里要拦）。
- 运费已知；货期 ≤7 天，且满足目标店更严的上限。
- 采集时间在 24h 内；地区校验不是 mismatch；B2 退货率 ≤30%。

### F2 经营模式判定（AI 判，不交给人）

依据按顺序使用：
1. 类目标准 v2：`reference/类目标准_v2_全部节点.csv`。用商品的亚马逊类目节点查（最长路径前缀匹配）：
   - 「不选」→ 排除；
   - 「有条件」→ 按该行「核实条件」逐款核对；
   - 「可选」→ 照样做下面的商品级检查。
   类目节点没有规则的，不默认放行，归入待核。
2. 商品级检查：看标题、五点、描述、套装内容，看不出来的再看主图和副图。命中下列任一条即排除：

| 排除项 | 包括 | 不算违规的情况 |
|---|---|---|
| 带电 | 插电、电池款（含附送电池、纽扣电池）、充电/USB、太阳能、LED 发光、石英钟机芯、电动/电子功能；不通电的电气件（灯座、接线盒/支架、无源转接头、电线电缆）；手电筒、台灯 | 金属丝、绳线等非电线材；纯手动工具 |
| 燃气 | 燃气器具及配件：软管、调压阀、燃料瓶 | 木炭烤炉、户外炊具（无燃气组件）属"有条件"，按核实条件判 |
| 资质/预审批 | 需预审批、BIZ-CN 限制、品牌授权、上架即需资质材料；3C 电子及其配件 | 只在被要求时上传 GCC 的：能出 GCC 的可做 |
| 儿童 | 定位 12 岁以下、婴儿、玩具、儿童学生文具、儿童安全用品 | 成人通用品，仅在标题中顺带提到"适合全家"的 |
| 化学品 | 清洁剂、洗涤剂、胶粘剂、润滑剂、气雾剂、燃料、农药/杀虫/除草剂、含 PFAS 的 | 不含化学品的清洁工具（刷、布、桶） |
| 武器 | 枪械及配件、弹药、弓弩、电击器、刀具（户外刀、厨刀、弯刀一律不选） | — |
| 食药医 | 食品、膳食补充剂、药品、医疗器械或医疗功效宣称（老花镜、护具、治疗/矫正宣称）、化妆品、化妆刷/海绵 | 靠垫/坐垫等去掉医疗宣称后可做 |
| 穿戴 | 鞋、帽、围裙、发饰、头盔、运动护具、珠宝首饰、行李箱 | 人穿的衣服；园艺/家务手套；首饰收纳本身可做，但该类目沃尔玛品牌删除约 80%，类目标准判不选，以类目标准为准 |
| 其他封禁 | 汽配（含无电件）、成人用品、成人拼图/派对/桌游、打印机配件、覆膜袋、家酿器具、活体植物 | 家电的无电配件已放开 |
| 品牌/IP | 标题或图片带知名品牌、授权角色/球队/影视 IP、"compatible with 某品牌"类仿冒信号；品牌在 TRO/品牌黑名单（`services.risk_gate`） | 自有品牌或无品牌的通用品 |

判定纪律：
- 不能只看大类名，也不能把关键词命中直接当违规。例如 "battery organizer" 是收纳，不是电池款；"kids" 出现在"适合全家"里不等于儿童定位。
- 拿不准时依次看五点、描述、图片。依据仍然冲突的，归"待核"、不送审，比例应低于 5%，超过就先停下来汇报。
- 每款都要写理由，注明依据来自哪一项（类目节点规则 / 商品级排除项 / 证据原文片段）。

产出三张表：可送审、排除、待核（逐款原因）。待核表放进 I 段预览，由所有者处理。

## G. 必要审核

1. 筛选只读：对可送审清单按 `_DEFAULT_CANDIDATE` 口径筛（未审 / pending 已过 1 天 / approved 但 `audit_version` ≠ 当前版本）。已有有效 approved 的直接复用；rejected 不重审；不在库或无标题的不送审。
2. 每块 ≤8,000 个，直到必要审核全部做完。每块开始前都要：
   - 确认 `resources.llm_price_tier(datetime.now(timezone.utc)) == "offpeak"`（高峰是北京时间工作日 9–12 点、14–18 点）；
   - 重新按第 1 步口径过滤一遍；
   - 避开 18:10 的 `audit_sheet`。

   然后执行 `.venv/bin/python cli.py product_audit -p asins=<本块>`（这个入口是点名**强审**，所以只能传筛过的子集）。
3. 不用 `force=1`、`force_rerun`、`mode=nonpass`；不改审核层级。`--dry-run` 也会产生 LLM 费用，不能当作免费预检。
4. 每块记录：ASIN、审前状态、通过/拒绝/待定、费用、异常。"approved × 旧版本"的重审费用要计入预算。

## H. 预览分配（只读）

**用标准引擎出预览，不在仓库外重组 `alloc_engine`。** 做法：把本轮候选 ASIN 写成 `pool.csv`（表头 `ASIN`），把 C 段算出的每店缺口写成 `quota.csv`（表头 `店铺,配额`，有效目标为 0 的店写 0 或不写），然后跑
`cli.py alloc_plan -p pool_csv=<pool.csv> -p quota_csv=<quota.csv> --dry-run`。
这两个参数只出预览（方案表在 reports 目录），不落占用；限定池默认不设淘汰线，不在池的 ASIN 会按原因计数列出。

约束：
- 以实时占用为准：品牌唯一去向；同一产品不重复；原占用店符合条件的归原店。
- 归属店不在本轮范围的单列，不算可分配。
- 不释放、不落占用、不写飞书；上一轮没执行的预览不算占用。

循环：`剩余缺口 = 预览缺口 − 已模拟分配`，`下一轮初选需求 = 剩余缺口 × 倍数`。从 D2 当前阶段继续；本轮模拟的品牌归属沿用，已有审核结论复用，积压候选先消化。达到目标即停；阶梯走完仍不足就汇报并询问。

## J. 确认后执行

1. **复核**：重新读实时在线、待上架、在途、占用、黑名单、登记簿、`ops.dispositions`。超过 24h 的 ASIN 先重采：`cli.py product_audit -p asins=<…> -p refresh=1` 会对没有 12h 内快照的补采后再审，注意它也是强审；或者提交新批次后再走 E。重采后再过一遍 F 段规则。
2. **执行容量**：`当前空位 = 有效目标 − 在线(或目录总数) − 有效待上架`，**不预支未完成的删除**；有效目标为 0 的店不进清单。超出空位的行保留原定店，列入"待腾位"。
3. **落占用**：执行清单 CSV（UTF-8，表头 `店铺,ASIN`），直接跑 `cli.py alloc_plan -p from_csv=<csv>`。任一行不过它会整批拒绝、一行不落：按报错剔除问题行并记录到 state，再跑一次。
4. **写上架表**（写入 = 当晚 18:10 审核、20:00 上架）：直接跑 `cli.py alloc_push -p from_csv=<csv>`。只写店铺和 ASIN 两列，审核结果留空。已有未弃用 SKU（含 UNPUBLISHED）的会被拦下，单列出来。
5. **写删除表**（写入 = 次日 15:00 前执行）：
   - 清单 CSV 表头 `店铺,SKU,动作,原因`；SKU 是沃尔玛真实 SKU；动作只写"停用"/"下架"/"删除"，**不能留空**（留空在系统里等于删除）。
   - 直接跑 `cli.py retire_push -p from_csv=<删除清单.csv>`。它整批校验：店铺在营、SKU 在目录未缺席、自动删除链（`ops.dispositions`）里没有同 SKU 未落定的 delete/retire；任一行不过就整批拒绝，按报错剔除后记录到 state 再跑。表里已有同 SKU 未落定行会自动跳过；追加到表尾并逐行回读。

## K. 后续与核验

- 审核回填：调度 18:10 自动执行。手动跑 `cli.py product_audit -p from_sheet=1`（不加 `force=1`）会处理**整张上架表**，跑之前确认授权范围，并遵守低价时段。
- 上架：调度 20:00 自动执行。手动跑只用**实际已写进表格**的清单：直接跑 `cli.py list_new -p from_csv=<实际派工清单>`；清单里只要有一行不在表上就整批拒绝。
- 删除：调度 15:00 的 `product_clear` 会处理删除表里的全部待办，不只本轮。
- 核验：先 `cli.py feed_poll -p store=<店>`，再 `cli.py catalog_sync -p store=<店> -p skip_feishu=1`。依次确认：占用已落库 → 表已写 → 平台已接收 → 逐 SKU 结果 → 目录生效。失败或不确定先对账；删除不释放占用。
