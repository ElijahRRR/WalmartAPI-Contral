# 标准选品执行流程

本技能是**项目级技能**，随仓库提交，只在本仓库内使用。一周的选品通常要连续做两三天，中间会被卖家精灵额度、断网、审核低谷时段打断。本文把它写成一个**可随时中断、随时接着跑的闭环**：每次被唤起都从第一节的推进循环开始，进度只认磁盘和真实系统。选品按轮推进，每一轮交付一份预览；所有者可以在任何一轮确认预览，确认后写入飞书表，后面的上架和下架由系统调度完成。

路径约定（全部相对路径）：
- **仓库命令**：在 WalmartAPI-Contral 仓库根目录执行，解释器 `.venv/bin/python`；文中 `cli.py …` 都指 `.venv/bin/python cli.py …`。
- **参考资料**：类目标准 v2 的两个 CSV 不进 git，放在 `<DATA_ROOT>/reference/category_standard/`，文中写作 `reference/…`。
- **`<DATA_ROOT>`**：默认是与仓库平级的 `WalmartAPI_data` 目录（设置了环境变量 `WALMART_DATA_ROOT` 时以它为准，见 `registry/paths.data_root()`）；密钥文件 `.env` 也在这个目录里，不在仓库里，内容不许输出。
- **`<RUN>`**：本周工作目录 `<DATA_ROOT>/exports/selection/<ISO周，如 2026-W48>/`。ISO 周按本机日期算。
- **时间**：文中的钟点都是北京时间。调度按本机时区跑，本机不是北京时间就先换算。
- `<…>` 替换为本轮实际值。

## 〇、红线（每一步都适用）

1. **没有审核结论的候选不许进预览。** 采集、检查、审核任何一段没走完，都不许跑分配预览，也不许出"先看一版"的分配表。审核被时段卡住时只能等，不能绕。
2. **每个候选只有三种去处**：继续往下走、落进一个有名字的终态（带原因）、或者在等一个写明了的条件。不许凭空消失，不许"先不管"。
3. **进度只认磁盘和真实系统，不认对话记忆。** 每次被唤起先读 `state.json`，再到数据库、采集器、卖家精灵、飞书核对。
4. **写操作只走 `cli.py` 工作流，直接真跑，不需要 `--dry-run`**：写入内容在所有者确认预览时已经核过。`from_csv` 三个入口真跑时也会先整份校验，任一行不过就整批拒绝、一行不写。编排脚本**只读**：连库用 `registry.db.pg_conn()`，开只读事务。不在脚本里直接写飞书或写库（采集的提交、记账、入库用现成的 `submit_batch`、`scrape_batches.record`、`pump_batch`，这三个除外）。
5. **所有者在关键节点控制，智能体不跨过节点。** 写进表格就等于执行（上架表写入后，当天 18:10 `audit_sheet` 审、20:00 `list_new` 上架；删除表写入后，15:00 `product_clear` 执行）。只有所有者确认了某一份预览，才对那一份进入 J 段写占用、写表；确认范围之外不多写一行。
6. **身份键统一：** 产品 = 标准 ASIN（`services.sku_asin.is_standard_asin`）；品牌 = `services.brand_key.brand_key(brand, manufacturer)`；在线身份 = `catalog.listing_sources` + `sku_asin.pick_asin`，不从 SKU 解析 ASIN。
7. **不释放占用。** 只有已消失或已终止的店，在所有者明确授权后，才走 `store_release`。店铺暂停、产品下架、删除都不构成释放理由。
8. **结果不确定先对账，不盲目重提。** 写操作永不自动兜底。
9. **条件放宽到头仍不够时**，汇报真实缺口并询问所有者，不自行改价格、配送、类目、评分等条件。
10. **遇到本文没写的情况不自创流程**：记进 `events.log`，把该环节标成受阻（`need_owner`），继续推进其他环节，最后问所有者。
11. **选品只有两种结束方式**：缺口为零，或获准的查询范围全部走完。本轮没产出、轮数多、所有者还没确认，都不是停止选品的理由。
12. **先采完、对完账，再花钱审。** 本轮的采集批次全部逐款认账、检查全部做完之前，不开任何审核块。
13. **新的一周默认从头开始**，不自动接上周没做完的运行；所有者点名要求时才接。

## 一、推进循环（每次被唤起都从这里开始）

"开始本周选品"和"继续本周选品"是同一件事，都执行下面的循环。

**一轮**的定义：取一批候选（D）→ 全部采完并逐款对账（E）→ 检查（F）→ 审核（G）→ 出预览（H）→ 交付（I）。**每一轮都以交付一份预览收尾**；交付之后只要还有缺口、查询范围还没走完，就接着开下一轮，不等所有者确认。所有者中途确认了哪一份预览，就执行哪一份（J），写进去的行会变成"有效待上架"，下一轮算缺口时自然扣掉。

1. **定位本周的运行。** 看 `<DATA_ROOT>/exports/selection/<本周>/state.json`：
   - 存在，且 `status` 不是 `done / closed` → 续跑。
   - 不存在 → **新的一周默认从头开始**：新建本周目录和 `state.json`，从 A 段做起。更早的周里没收尾的运行一律不接，把它的 `status` 改成 `closed`（原因写"新的一周"），其余文件原样保留；在本周第一张进度卡里用一行说明它停在哪里。停在 J 中间的要写明哪几步已经写入、哪几步没写，由所有者决定要不要补。它审过的结论留在库里，本周会自动复用。
   - 所有者明确说"继续上周"或点名某一周 → 续跑那一周的运行，不新建。
   - 所有者明确说"重新开始" → 把本周这次运行标 `closed`、目录改名保留，再新建。
   - 本周的运行已经 `done`，所有者也没说重新开始 → 输出一行"本周选品已完成"后结束。
2. **占锁。** 读 `<RUN>/run.lock`（会话标识 + `heartbeat`）。`heartbeat` 在 30 分钟以内 = 另一个会话正在跑：本次不做任何动作，直接结束（所有者明确说上一个会话已经断了，才直接接管）。否则写入自己的标识接管，此后每次落盘都更新 `heartbeat`，长动作中途至少每 10 分钟更新一次。
3. **对账。** `state.json` 里所有"进行中"的动作，逐个到真实系统核对后改成真实状态（规则见第四节"中断后的对账"）。然后跑一遍第二节的对账恒等式。
4. **先看所有者有没有新指令。** 每做完一个最小动作都看一次：
   - 确认了某一份预览 → 优先做 J，做完再回来继续选品；
   - 要求修改某一份预览 → 按 I 段处理；
   - 没有新指令 → 往下走。
5. **推进。** 按第三节环节总表，找"入口闸成立、出口闸未成立、没有受阻"的环节，执行它的下一个动作；做完立刻落盘、核对，再回到第 4 步。同一轮里 D、E、F 可以交叠：卖家精灵还在导，前面导出的就可以先采；一个采集批次对完账，就可以先做检查。**审核（G）不交叠**，必须等本轮的采集全部对完账、检查全部做完才开。
6. **受阻就绕开。** 在 `state.json` 里记下受阻原因和最早恢复时间，转去推别的环节。全部环节都受阻时按第四节等待，到点回到第 3 步。
7. **只有三种情况可以停下：**
   - **选品已经结束**（缺口为零，或获准的查询范围全部走完），最新一份预览已交付，只剩等所有者确认；
   - 剩下的环节全都卡在需要所有者亲自处理的事上（如卖家精灵登录失效）。还有环节只是在等时间的，先等、先推，不算这一种；
   - 全部完成（`status = done`）。

   停下前输出进度卡（第七节）。**交付一份中间预览不是停下的理由**，也不许以"今天先到这里""其余下次再做"为由结束。

**每个动作之前自问三件事，任何一个答不上就不做：**
- 这是环节总表里当前环节的下一个动作吗？
- 入口闸是刚用文件或 SQL 核对过的，还是凭印象？
- 做完以后拿什么证明它做完了？

## 二、台账

`<RUN>/` 下的文件：

| 文件 | 内容 |
|---|---|
| `state.json` | 本周运行状态（见下） |
| `ledger.csv` | 逐款台账：本周取得的每个 ASIN 一行，记录它走到哪了 |
| `sprite_plan.csv` | 卖家精灵查询计划与导出记录（整个获准范围） |
| `events.log` | 追加式流水：时间、环节、动作、结果、数量 |
| `exports/` `batches/` `f/` `audit/` `preview/` `exec/` `logs/` | 导出原件、采集清单与回执、检查结果、审核块、各份预览、执行清单、命令日志 |
| `run.lock` | 会话锁 |

落盘规则：
- **先落盘意图，再执行，再落盘结果。** 例如提交采集前，先把清单写进 `batches/`、把批次记成 `planned`。
- **每个最小动作落一次盘**（一次导出、一个批次、一批检查、一个审核块）。中断最多丢一个动作。
- 写文件用"写临时文件再改名"，不留半截文件。

- `status`：`running`（选品在推进）、`waiting_owner`（选品已结束，只等确认）、`done`、`closed`（被新的一周或"重新开始"关闭）。
- `selection_end`：`null`、`gap_zero`、`range_exhausted`。
- 预览的 `status`：`delivered`（已交付）、`executing`、`executed`、`superseded`（作废）。
- `rounds[].d_closed_by`：`target`（选够）、`range_exhausted`（范围走完）、`blocked`（D 长时间受阻，按已取得的收口）。
- `blocked` 的形状：`{"reason": "…", "resume_at": "…", "need_owner": false, "since": "…"}`。

### ledger.csv

列：`asin, 来源, 轮次, 状态, 原因, 批次名, 认账来源, source_id, 快照时间, F1, F2, F依据, 审前状态, 审核状态, 审核版本, 审核时间, 送审次数, 分配店, 未分到原因, 执行预览号, 更新时间`。
同一个 ASIN 只有一行；再次被导出时只在「来源」里追加，不新增行，状态不回退。

| 状态 | 含义 | 由哪个环节接手 |
|---|---|---|
| `new` | 已取得，还没编进采集批次 | E |
| `scraping` | 已编进批次（批次名在行上） | E |
| `ingested` | 已逐款认账：有一条成功且完整的采集结果（`source_id` 在行上） | F |
| `f_pass` | 检查通过，等确定审核去向 | G |
| `audit_wait` | 需要审核，还没有结论 | G |
| `pending_retry` | 审过一次、结果待定，满 24 小时后重审一次 | G |
| `approved` | 审核通过，且是当前规则版本；还没执行 | H |
| `executed` | 所有者确认后已写入占用和上架表（预览号在行上） | 系统调度 |
| `x_invalid` | 终态：编号不合法 | — |
| `x_scrape` | 终态：采集失败（原因写明） | — |
| `x_supply` | 终态：供货条件不符（哪一条写明） | — |
| `x_model` | 终态：经营模式排除（依据写明） | — |
| `x_hold` | 终态：待核，交所有者决定 | — |
| `x_rejected` | 终态：审核拒绝 | — |
| `x_pending` | 终态：审核两次仍待定 | — |

`approved` 的款在最新一份预览里要么有「分配店」，要么有「未分到原因」。

### 对账恒等式

每次改完 `ledger.csv` 都算一遍。**任何一条不成立就停止推进，先查清差在哪**，查清并修正后再继续，过程写进 `events.log`：

1. ledger 行数 = `exports/` 全部导出文件加 D1 清单合并去重后的编号数。
2. 每个采集批次：提交数 = 本批成功 + 他批成功 + 本批失败；本批失败 = 转进重采批次的 + 记成 `x_scrape` 的。
3. 进过 F 的数量 = `x_supply` + `x_model` + `x_hold` + `f_pass` 及之后状态的。
4. `f_pass` 及之后状态的数量 = `f_pass` + `audit_wait` + `pending_retry` + `approved` + `executed` + `x_rejected` + `x_pending`。
5. 每份预览：`pool.csv` 行数 = 有分配店的 + 各「未分到原因」之和。

## 三、环节总表

环节按轮执行。下表的"本轮"指 `state.round` 这一轮。

| 环节 | 入口闸 | 出口闸（全部成立才算完成） | 可能受阻于 |
|---|---|---|---|
| A–C 盘点与缺口 | 每一轮开头（A3、C 每轮重算；A1、A2、B 超过 24 小时才重算） | `state.gap` 里每家在营店都有「有效目标/缺口」或「不分配（原因）」；本轮初选量已算出 | 数据库、飞书连不上 |
| D 候选 | C 完成，且选品没有结束 | **本轮收口**，三种之一：本轮新增独立 ASIN ≥ 本轮初选量；获准的查询范围全部走完；D 长时间受阻且本轮已有新增候选（见 D2）。已导出的计划项都与卖家精灵"导出历史"对得上 | 当日额度、登录失效、断网 |
| E 采集入库 | ledger 有 `new` 行（可以边导边采） | D 已收口，`new` = 0 且 `scraping` = 0，本轮每个批次都已**逐款认账**并 `closed` | 采集器连不上、批次没落定 |
| F 检查 | 有 `ingested` 行（一个批次认完账就可以开始） | D 已收口、E 出口闸成立，且 `ingested` = 0 | 数据库连不上 |
| G 审核 | **D 已收口、E 出口闸成立、F 出口闸成立**；并且有 `f_pass`、`audit_wait` 或到期的 `pending_retry` | 三者都为 0，并通过"审核结论 SQL"复核 | 高峰时段、调度保留时段、锁、LLM 或网络故障 |
| H 预览分配 | **预览总闸**（见下）全部成立 | 预览成功产出；`pool.csv` 每一行都有分配店或未分到原因；续轮判定已做 | 数据库、飞书连不上 |
| I 交付 | H 完成 | 本轮预览已交给所有者并登记进 `state.previews`；按续轮判定开了下一轮，或记下选品结束 | — |
| J 执行 | 所有者明确确认某一份预览（原话和时间已记录） | 该预览的 J1–J5 每一步 `done`，回读核对通过，预览标 `executed` | 写表避让时段、锁、连不上 |
| K 执行回报 | 有已执行的预览 | 只读，随每轮盘点做，不阻塞任何环节 | — |

### 预览总闸（H 的入口，五条逐条核对，结果写进 `state.lanes.H`）

1. 本轮 D 已收口。
2. ledger 中 `new`、`scraping`、`ingested`、`f_pass`、`audit_wait` 五种状态合计为 0。
3. 到期的 `pending_retry` 为 0。没到期的留在原状态，不挡预览，但在预览里单列"审核待定"。
4. 对 ledger 中全部通过了 F 的 ASIN 跑"审核结论 SQL"（G4），结果必须是：不在库 0、未审 0、旧版本通过 0，`pending` 数等于 ledger 里 `pending_retry` + `x_pending` 的数。不成立就按 G1 的规则用库里的现值重新定去向，回 G。
5. `pool.csv` 等于 ledger 里全部 `approved` 的 ASIN，一个不多、一个不少。

系统侧还有一道保险：`pool.csv` 里只要有一个不在库或没有审核结论的 ASIN，`alloc_plan -p pool_csv=` 会整份拒绝（⛔）。**遇到这个拒绝说明前面的闸没核对好，回 E 或 G 补齐；不许从 `pool.csv` 里删掉它们来换取通过。**

### 选品什么时候结束

**只有两种结束方式：缺口为零，或获准的查询范围全部走完。** 在 H4 判定，写进 `state.selection_end`。
"本轮一个都没分到""已经跑了很多轮"都不是结束的理由，只作为诊断提醒写进预览首页和进度卡，然后照常开下一轮。
获准的查询范围 = 确认的类目清单 × 固定条件 × 本周阶梯路径上的全部阶段（到 S3 为止）× 各价格段，也就是 `sprite_plan.csv` 的全部计划项。

## 四、受阻、等待与续跑

### 受阻怎么处理

| 情况 | 处理 | 什么时候恢复 |
|---|---|---|
| 卖家精灵当日导出次数用完（50 次，或页面提示上限） | D 记受阻。本轮已有新增候选 → 本轮按已取得的收口，照常走完采集、检查、审核、预览；下一轮从计划里没导出的地方接着做 | 次日 00:05，以页面显示的剩余次数为准 |
| 卖家精灵登录失效、出验证码、页面读不到结果数，或浏览器工具不可用 | D 记受阻，`need_owner = true`。本轮已有新增候选 → 同上收口；其他环节继续 | 所有者处理后 |
| 断网，或数据库、飞书、采集器连不上 | 相关环节记受阻；按 2、5、10、20、30 分钟退避重试，之后每 30 分钟一次。同一原因连续 6 小时没恢复，转 `need_owner` | 连上后 |
| 现在是 LLM 高峰时段，或在调度保留时段内 | G 记受阻；H0 的刷新同样要等 | 下一个审核窗口的起点（G2） |
| `cli.py` 退出码 3（同名工作流正在跑，锁被占） | 不算失败，不计入失败次数和送审次数 | 10 分钟后重新判断 |
| 审核块异常退出（退出码 1） | 按 G4 认领已审完的，其余留在 `audit_wait`；`fail_streak` 加 1，等 15、30、60 分钟后再开下一块；连续 3 块失败转 `need_owner` | 见左 |
| 采集批次迟迟不落定 | 每 20 分钟查一次；超过 2 小时在进度卡里写明，继续查 | 落定后 |
| 写表避让时段（J 段） | J 对应步骤记受阻；选品照常推进 | 避让时段结束 |
| 对账恒等式不成立 | 全部环节暂停，先查清；查不清转 `need_owner`，把差异明细交给所有者 | 查清并修正后 |

### 怎么等

全部环节都受阻时，取最早的 `resume_at`，**在会话里等到那个时间**：用一条阻塞命令循环 sleep，每 60 秒更新一次 `run.lock` 的 `heartbeat`，到点退出；工具对单条命令有时长上限就分段执行。醒来回到推进循环第 3 步。

会话被环境终止、机器休眠、断电都没关系：下一次"继续本周选品"会从磁盘接上，已经做完的不会重做。

`status = waiting_owner` 时被唤起：先看所有者有没有确认或修改；没有的话，缺口超过 24 小时没算就重算一次（只读）。重算后有缺口、且查询范围没走完，就把 `status` 改回 `running` 接着开下一轮；否则输出一行状态后结束。

### 中断后的对账（推进循环第 3 步）

| `state.json` 里停在 | 怎么核对 | 结论 |
|---|---|---|
| 卖家精灵导出进行中 | 看卖家精灵"导出历史"有没有这条查询，本地 `exports/` 有没有文件 | 历史有、本地没有 → 从历史重新下载，不消耗次数；都没有 → 计划项回到"未导出" |
| 采集批次 `planned` | 用同一个批次名、同一份清单提交 | 成功 = 之前没交上；抛 `BatchExistsError` = 已经建过，拿它带回的 batch_id 继续 |
| 采集批次已提交、未认账 | `batch_status` 看是否落定；`pump_batch` 和取回执都可以重复跑 | 按 E 段第 3 步起继续 |
| F 的一批进行中 | 该批结果文件行数等于输入数才算完成 | 不完整就整批重判 |
| 审核块 `started` | 进程还在（pid 存活）→ 继续等；不在了 → 按 G4 认账 | 已审的认领，没审的回 `audit_wait` |
| 预览进行中 | 只读，直接重跑 | — |
| 某份预览 `executing` | 回读真实系统（占用、上架表、删除表），见 J 段各步的"续跑" | 只在本周的运行里续；上周的不自动续 |

## A. 盘点（只读）

### A1 店铺范围
在营店 = `services.stores.enabled_names()` ∩ 限额表「店铺状态」= ACTIVE（支付状态取 `ops.store_kpi_daily` 最新一天 ACTIVE），扣除谭总系（`services.alloc_survey.is_excluded()`）。SUSPENDED/售出/终止/TERMINATED 的店不分配，但**仍持有占用**，H 段单列"品牌归属店不在本轮范围"。

### A2 配置（飞书「定价及上下架限制」表，`registry.resources.RETIRE_LIMITS`）
- 用 `api.feishu.list_records()` 读**原始值**（不要用 `store_limits.setup_limits()` —— 它把 0 当未填回落 5000）。
- `有效目标 = min(单店最大在线数, 商品上限)`；**任一为 0 或空 = 本轮不分配**（例：81刘何秀、A170毕海威、C021李小玲 商品上限 0）。系统 `alloc_plan` 不读商品上限，这条只能由编排拦，执行 CSV 不得含这些店。
- 商品上限是沃尔玛口径（按目录全部未缺席 item 计）；它小于单店最大在线数时（如 5000/1000/250 的店）用目录总数算余量。
- 同表还读：目标销售额/目标订单（日）、配送限制（规划内店均为 fba）、配送时长限制、类目 1/2/3。经营优先级：销售额优先，订单数其次。

### A3 现状数据
| 项 | 来源与口径 |
|---|---|
| 在线 | `catalog.walmart_items`：`missing_since IS NULL AND published_status='PUBLISHED'`，按店计数 |
| 目录总数（硬限用） | `catalog.walmart_items`：`missing_since IS NULL`，任意状态 |
| 有效待上架 | 上架表 `services.listing_sheet.read_rows()` 中同时满足：`是否上架 ∈ {空, No}`、无 feedid、`上架结果 ∉ {SKU_LOCKED, PROHIBITED, CONTENT_REJECTED}`、重试 <3 次、库里审核不是 rejected，且该 (店, ASIN) 当前不在线 |
| 上架在途 | `ops.feed_log` 中状态为 submitted/pending 的 MP_ITEM，与 `ops.feed_items` 关联 |

| 自动删除链在途 | `ops.dispositions` 中未落定的 delete/retire |

先查各表的最新更新时间。目录确实过旧时，才执行 `cli.py catalog_sync -p store="<店>" -p skip_feishu=1`（会写库，不是纯查询）。

## B. 经营分析与在架三分类（只读）

### B1 逐店经营分析
- 近 15 天、近 30 天，并与前 30 天对比的销量和销售额（`orders.order_lines`，按 `order_date`，排除 Cancelled，金额为毛额）。
- 在线 SKU 数、动销 SKU 数、动销率、每在线货位销售额。
- 亚马逊类目、沃尔玛类目、亚马逊采购价带分别统计。
- 最新有效绩效；按佣金和放款日估算余额。

产出：逐店判断，以及优先补的类目、价带、渠道。不能凭"高价品更多"推断销售额会上升。

### B2 统一退货率口径（B、C、D、F 共用同一段 SQL）
- 分子：90 天内**已成熟**订单（下单满 30 天）的实物退货件数。实物退货 = `orders.return_lines` 中 `return_method <> 'KEEP_ITEM'` 且 `is_keep_it` 不为真。通过 `order_line_id` 关联 `order_lines.asin`。
- 分母：同一批订单的件数，只用 API 期订单（`source IS NULL`）。
- 同时给出样本量。样本少于 10 件时只作"观察"。

### B3 在架三分类
- **建议下架**：持续缺货（≥3 个采集日、跨度 ≥7 天，且最新有效数据仍缺货）；高退货（B2 口径 >30% 且样本 ≥10）；长期低需求且 BSR 偏弱，并且有合理替代。
- **建议保留**：本店或他店有成交；BSR 在同类成交参照中较好或持续改善（≥25%）；供货正常。
- **继续观察**：历史不足、类目变化、短期缺货、排名改善中、样本少、用途待核、替代不足。

BSR 规则：近 60 天，最近 7 天中位数对比此前 21 天中位数；7 天窗口至少 3 个点、21 天窗口至少 7 个点；只比较同一 BSR 类目；参照组优先同类目同价带，不足时扩大到同类目。
BSR 取 `catalog.snapshots` 每次采集里的 BSR 字段（采集器已实测提供；字段在 `raw` 中，按采集器契约的键名读取，带类目一起读）。

其他规则：
- 60 天无单只是线索，不直接删除；不设每店删除比例上限。
- 本轮候选已在线且又在删除名单里的，保留在原店。
- 弱表现品没有足够替代时暂缓腾位。
- 已在 `ops.dispositions` 自动删除链中的 SKU、已在删除表里待执行的 SKU，都不重复列入，只引用。

## C. 缺口与初选量（只读）

按店计算（有效目标为 0 的店直接跳过）：

```
有效目标 = min(单店最大在线数, 商品上限)
预览缺口 = max(有效目标 − (在线 + 有效待上架 − 建议下架中仍在线的), 0)
```

- 商品上限是约束项的店，括号里的"在线"换成目录总数（含 UNPUBLISHED），"建议下架"只扣**删除**（停用是否释放沃尔玛名额以实测为准）。
- 在线已超有效目标的店（如 A106、A173、A175）缺口为 0，并在预览中标出超出数。
- 新公式扣减待上架，与系统既定的"占位不消耗容量"口径不同，**只在本编排中使用**，预览中写明。**所有者中途确认并执行过的预览，写进上架表的行就是在这里被扣掉的**，所以每轮开头必须重读上架表，不能沿用上一轮的数。
- 缺口按 准入类目 × 货期上限 分桶汇总（规划内店都是 FBA）。

每一轮的初选量：

```
剩余缺口   = Σ 各店 max(预览缺口 − 最新一份未执行预览里给该店的模拟分配, 0)
本轮初选量 = 剩余缺口 × 倍数
```

- 第一轮还没有预览，剩余缺口就是各店预览缺口之和。
- 倍数 = max(3, 本周累计独立 ASIN ÷ 本周累计可分配数)；第一轮没有本周数据时，用上一周目录里的实测值和 3 取较大者。倍数写进预览。
- 数据库候选（D1）只在第一轮取，计入第一轮的初选量，按独立 ASIN 计。
- 本周的阶梯路径（<50,000 还是 ≥50,000）按第一轮的初选量定，记在 `lanes.D.path`，本周不再变。

结果写进 `state.gap` 和 `state.rounds`。A3 和 C 每轮开头重算；差异记进 `events.log`；已经取得的候选不重做。

## D. 候选

### D1 数据库候选（只读，只在第一轮）
当前不在线、累计至少 2 单、B2 退货率 ≤30%，类目和价带符合 B1 方向。保留来源、成交样本、退货率、入选依据。清单存为 `exports/db_candidates.csv`，并写进 ledger（来源 `db`，状态 `new`）。历史审核通过**不等于**可以跳过采集。

### D2 卖家精灵（浏览器）
用保留的模板和确认的类目清单（类目标准 v2，`reference/卖家精灵勾选清单.csv`），不加回已删除的大类。

固定条件：价格 0–40、FBA、月销量 ≥20、评分 ≥4、上架时间近 1 年，BSR 增长率不限。

放宽阶梯（按阶段编号推进，**只进不退**；每一轮都从上一轮停下的地方接着做）：

| 阶段 | 路径 <50,000 | 路径 ≥50,000（恰好 50,000 归这边） |
|---|---|---|
| S1 | 评论 ≥20，变体 1 | — |
| S2 | 5 ≤ 评论 ≤ 19，变体 1（只补 S1 没覆盖的区间） | 评论 ≥5，变体 1（起点） |
| S3 | 补选：评论 ≥5，变体 2–5 | 补选：评论 ≥5，变体 2–5 |

**先排计划，再执行。** `sprite_plan.csv` 是整个获准范围的清单，每行一个计划项：阶段、类目组、价格区间、评论条件、变体条件、状态（未导出 / 已导出 / 已拆分 / 零结果）、页面结果数、导出编号、文件名、文件行数、导出时间、轮次。进入一个阶段时，一次把这个阶段覆盖全部类目的计划项排出来。

- 顺序：家居 → 庭院 → 办公 → 户外运动 → 宠物 → 其他保留类目。
- 每次查询结果 ≤2,000 条（19:00–08:00 可到 3,000），尽量接近上限。超了按价格区间拆分，再超继续拆：父项标"已拆分"，子项加进计划。结果少的类目可以合并（条件一致）。
- 每天最多 50 次导出。

每次导出的闭环：
1. **导出前**：读页面上当天剩余次数（以页面为准，state 里的计数只作参考）；确认结果数不超上限；确认"导出历史"里没有同一条查询（有就直接下载，不重新导）。
2. **导出后**：文件存进 `exports/`；核对文件行数和页面结果数，对不上就从导出历史重新下载一次，仍对不上照实记录差异；解析出编号并入 ledger（不合法的记 `x_invalid`，新的记 `new` 并填本轮轮次，已有的只追加来源）；计划项标"已导出"；更新本轮的 `got`。**`got` 只数本轮新进 ledger 的独立 ASIN**，以前轮次见过的不算。

**一轮里怎么推进、怎么收口：**
- 每一轮都从计划里第一个"未导出"的计划项接着做。当前阶段没有未导出项了，才进入下一阶段并为它排计划。
- **选够即收口**：本轮 `got` ≥ 本轮初选量 → 本轮 D 收口（`d_closed_by = target`）。没用到的计划项保持"未导出"，留给下一轮，不算遗漏。
- **范围走完**：路径上最后一个阶段（S3）的计划项全部是 已导出 / 已拆分 / 零结果 → `range_exhausted = true`，本轮 D 收口（`d_closed_by = range_exhausted`）。本轮没取到新候选也照样往下走到预览。
- **长时间受阻收口**：D 受阻，恢复时间在 2 小时以后或需要所有者处理，而本轮 `got` > 0 → 本轮按已取得的收口（`d_closed_by = blocked`），不为等额度而停住整轮。本轮 `got` = 0 时没有东西可往下走，等 D 恢复。
- 汇总按 ASIN 去重，保留全部来源，不因"库里已有 / 选过 / 交付过"排除。

### D3 采集前不做剔除（所有者定稿 2026-11-19）
D1、D2 的全部合法 ASIN 都进入 E 段采集。「不选」类目节点、ASIN 黑名单、TRO 品牌都**不在采集前剔除**，统一放到 F 段和审核环节判定。

## E. 采集与入库

候选可以边导边采，但**本轮所有批次都逐款认完账之前，不开任何审核**。

1. **组批。** ledger 里 `new` 的行攒到 2,000 个就组一批；本轮 D 收口时，把剩下的 `new` 全部组批，不等凑整。批次名固定格式 `sel_<周>_r<轮>_b<三位序号>`，例如 `sel_2026W48_r1_b003`。先把清单写进 `batches/<批次名>.txt`、state 里记 `planned`、ledger 行改成 `scraping` 并填批次名，然后才提交。
2. **提交。** `api.scraper.submit_batch("<批次名>", asins, zip_code="", needs_screenshot=False)`，用 `services.scrape_batches.record()` 记台账，保存回执（batch_id、提交时间、提交数）。抛 `BatchExistsError` 表示这个批次已经建过：拿它带回的 batch_id 继续往下走，**不要换名重提**。
3. **等落定。** `scrape_batches.wait_settled(["<批次名>"], 20)`。没落定不算失败，转去推别的环节，20 分钟后再查。
4. **入库。** `services.product_ingest.pump_batch(scraper, db, "<批次名>", limit=1000, max_pages=400)`。**只有 `ok=True` 才算拉完**；`ok=False` 按网络故障退避重试，不要重置全局游标。`gone=True` 表示批次在采集侧已经没了：把这批的 ASIN 全部编进新批次（原名加 `_g1`），原批次标 `gone`（视同 `closed`）。新批次也 `gone` 的，这些款记 `x_scrape`，原因写"采集侧批次两次丢失"。
5. **取本批回执。** 批次 completed 不等于数据已入库，库里有标题也不等于这一批采到了。用 `api.scraper.export_batch_records("<批次名>", cursor, 1000)` 从游标 0 翻到 `has_more = False`（只读），把每条记录存进 `batches/<批次名>_records.csv`：`asin, source_id, outcome, completeness_ok, scraped_at, zip_verify（在 scrape_params 里）, 标题是否非空（slow.title）`。同时记下返回的 `coverage`（`asin_total`、`asin_with_event`）：`asin_total` 应等于提交数，对不上照实记录。
6. **核对回执已入库。** 回执里的每个 `source_id` 都必须在 `catalog.snapshots` 里查得到。有缺的重跑一次第 4 步；仍缺就把 E 记成受阻，不往下认账。
7. **逐款认账。** 对该批每个 ASIN 归进三类之一，**三类分开计数**：
   - **本批成功**：回执里这个 ASIN 有一条记录同时满足 `outcome = 'ok'`、`completeness_ok` 不为 false、`zip_verify` 不是 `mismatch`、标题非空（有多条取 `scraped_at` 最新的一条）。→ `ingested`，认账来源写"本批"，记下那条的 `source_id` 和快照时间。
   - **他批成功**：本批没有成功记录，但同期别的任务采到了合格结果。用下面的 SQL 找，找到的 → `ingested`，认账来源写"他批"，记下那条的 `source_id` 和快照时间：
     ```sql
     SELECT DISTINCT ON (s.asin) s.asin, s.source_id, s.scraped_at
     FROM catalog.snapshots s
     JOIN catalog.products p ON p.marketplace = s.marketplace AND p.asin = s.asin
     WHERE s.marketplace = 'US' AND s.asin = ANY(%(asins)s)
       AND s.outcome = 'ok' AND s.completeness_ok IS NOT FALSE
       AND coalesce(s.scrape_params ->> 'zip_verify', '') <> 'mismatch'
       AND s.scraped_at >= %(batch_submitted_at)s
       AND s.source_id <> ALL(%(this_batch_source_ids)s)
       AND p.title IS NOT NULL AND btrim(p.title) <> ''
     ORDER BY s.asin, s.scraped_at DESC;
     ```
   - **本批失败**：其余全部。原因按这个顺序取：回执里的 `outcome`（`not_found`、`blocked`、`parse_failed`、`stale`）；`completeness_ok = false`（采到了但不完整）；地区校验不符；回执里根本没有这个 ASIN → 跑 `scrape_batches.pull_failures()` 取失败明细（落在 `ops.scrape_failures`）里的失败类型。
8. **失败的去向。** 每款最多重采一次。
   - `not_found`、`parse_failed`，以及失败类型属于 `services.scrape_batches` 的 `TERMINAL` 档 → `x_scrape`，原因写明。
   - 失败类型属于 `RETRY_LATER` 档（变体偏移）→ `x_scrape`，原因写"变体偏移，本周不再采"。
   - 其余（`blocked`、`stale`、不完整、地区校验不符、`RETRYABLE` 档、`unknown`、查不到任何记录）→ 编进 `<原批次名>_retry` 重采一次，照第 2–7 步走；仍失败 → `x_scrape`，原因写明。
9. **批次收口。** 该批每个 ASIN 都已经是 `ingested`、`x_scrape` 或转进了重采批次，批次标 `closed`，把对账写进 state 的 `tally`：提交数 / 本批成功 / 他批成功 / 本批失败（按原因）/ 转重采 / 终态失败。

认账之后，F1 和预览里的"快照时间"都用 ledger 行上记的那条 `source_id` 对应的快照，不是"库里最新一条"。

`product_refresh` 只刷新在线品，不是新候选的上传入口；`cli.py product_ingest` 也不能证明本批已取全。

## F. 供货与经营模式检查（由 AI 直接执行）

对 ledger 里 `ingested` 的行分批处理；一个采集批次认完账就可以开始，不用等整轮采完。**每款恰好落进四个结果之一**：`x_supply`（供货不符）、`x_model`（排除）、`x_hold`（待核）、`f_pass`（可送审）。每批处理完核对"输入数 = 输出数"再落盘。F 不依赖任何时段，随时可以做。

### F1 供货硬条件（脚本判，逐 ASIN，用认账时记下的那条快照）
- 单价 >0 且 ≤40（另列落地价 = 单价 + 运费）；FBA；库存 ≥5 且**有确切数量**（系统会把"有货但无数量"按 10 件算，这里要拦）。
- 运费已知；货期 ≤7 天（各店更严的上限由分配引擎按限额表判）。
- 地区校验不是 mismatch；B2 退货率 ≤30%。

任何一条不过 → `x_supply`，原因写是哪一条。数据新鲜度在 H0 和 J1 把关，不在这里。

### F2 经营模式判定（AI 判，不交给人）

只对 F1 通过的款做。每批不超过 200 款，结果写进 `f/f2_<序号>.csv`（asin、结论、依据类型、证据原文片段），再并入 ledger。

依据按顺序使用：
1. 类目标准 v2：`reference/类目标准_v2_全部节点.csv`。用商品的亚马逊类目节点查（最长路径前缀匹配，脚本查表）：
   - 「不选」→ 排除；
   - 「有条件」→ 按该行「核实条件」逐款核对；
   - 「可选」→ 照样做下面的商品级检查。
   类目节点没有规则的，不默认放行，归入待核。
2. 商品级检查：看标题、五点、描述、套装内容，看不出来的再看主图和副图。命中下列任一条即排除：

| 排除项 | 包括 | 不算违规的情况 |
|---|---|---|
| 带电 | 插电、电池款（含附送电池、纽扣电池）、充电/USB、太阳能、LED 发光、石英钟机芯、电动/电子功能；不通电的电气件（灯座、接线盒/支架、无源转接头、电线电缆）；手电筒、台灯 | 金属丝、绳线等非电线材；纯手动工具 |
| 燃气 | 燃气器具及配件：软管、调压阀、燃料瓶 | 木炭烤炉、户外炊具（无燃气组件）属"有条件"，按核实条件判 |
| 资质/预审批 | 需预审批、BIZ-CN 限制、品牌授权、上架即需资质材料；3C 电子及其配件 | 只在被要求时上传 GCC 的：能出 GCC 的可做 |
| 儿童 | 定位 12 岁以下、婴儿、玩具、儿童学生文具、儿童安全用品 | 成人通用品，仅在标题中顺带提到"适合全家"的 |
| 化学品 | 清洁剂、洗涤剂、胶粘剂、润滑剂、气雾剂、燃料、农药/杀虫/除草剂、含 PFAS 的 | 不含化学品的清洁工具（刷、布、桶） |
| 武器 | 枪械及配件、弹药、弓弩、电击器、刀具（户外刀、厨刀、弯刀一律不选） | — |
| 食药医 | 食品、膳食补充剂、药品、医疗器械或医疗功效宣称（老花镜、护具、治疗/矫正宣称）、化妆品、化妆刷/海绵 | 靠垫/坐垫等去掉医疗宣称后可做 |
| 穿戴 | 鞋、帽、围裙、发饰、头盔、运动护具、珠宝首饰、行李箱 | 人穿的衣服；园艺/家务手套；首饰收纳本身可做，但该类目沃尔玛品牌删除约 80%，类目标准判不选，以类目标准为准 |
| 其他封禁 | 汽配（含无电件）、成人用品、成人拼图/派对/桌游、打印机配件、覆膜袋、家酿器具、活体植物 | 家电的无电配件已放开 |
| 品牌/IP | 标题或图片带知名品牌、授权角色/球队/影视 IP、"compatible with 某品牌"类仿冒信号；品牌在 TRO/品牌黑名单（`services.risk_gate`） | 自有品牌或无品牌的通用品 |

判定纪律：
- 不能只看大类名，也不能把关键词命中直接当违规。例如 "battery organizer" 是收纳，不是电池款；"kids" 出现在"适合全家"里不等于儿童定位。
- 拿不准时依次看五点、描述、图片。依据仍然冲突的，归"待核"、不送审。
- 每款都要写理由，注明依据来自哪一项（类目节点规则 / 商品级排除项 / 证据原文片段）。

待核的款（`x_hold`）放进 I 段预览，由所有者处理。所有者放行的，改回 `f_pass`，随当前这一轮走审核，出现在下一份预览里。

## G. 审核（只在低谷时段，分块，逐款认账）

**开审前提**：本轮 D 已收口；本轮每个采集批次都已逐款认账并收口（E 的出口闸）；本轮的检查全部做完（F 的出口闸）。三条都成立之前，不做 G1，也不开任何审核块。这样送审的清单是完整的，每一款只付一次钱。

### G1 定去向（只读，对 `f_pass` 的行）
用 G4 的 SQL 读库里的现值，逐款归类：

| 库里的状态 | ledger 改成 |
|---|---|
| approved，且 `audit_version` = 当前 `resources.AUDIT_RULES_VERSION` | `approved`（复用，不花钱） |
| rejected | `x_rejected`（沿用旧结论，不重审） |
| 没有结论；或 approved 但版本落后；或 pending 且上次审核在 24 小时以前（或没有审核时间） | `audit_wait` |
| pending 且上次审核在 24 小时以内 | `pending_retry`，到期时间 = 审核时间 + 24 小时 |
| 不在库，或标题为空 | 不该出现（E 的认账已经拦过）；出现了记 `x_scrape`，原因写"不在库或无标题，无法审核"，并记进 `events.log` |

"approved × 旧版本"会真重审、产生费用，数量记进预算。

### G2 审核窗口（每开一块之前都重新判断）
同时满足才能开审：
- a. `resources.llm_price_tier(datetime.now(timezone.utc)) == "offpeak"`。高峰是工作日 9–12 点和 14–18 点，周末全天低谷。**审核工作流自己不会在高峰停下，只能靠这里拦。**
- b. 不在调度保留时段内。手动审核和调度里的审核共用一把锁，占着锁跨进去会把当天的调度挡掉：
  - 12:40 起，到当天 `product_chain` 里那次审核结束为止。
  - 17:50 起，到当天 `audit_sheet` 结束为止。
  
  是否结束查 `ops.runs`：
  ```sql
  SELECT params, started_at, finished_at, status
  FROM ops.runs
  WHERE workflow = 'product_audit' AND started_at > now() - interval '10 hours'
  ORDER BY started_at;
  ```
  `params` 里带 `mode = online` 的是 `product_chain` 那次，带 `from_sheet` 的是 `audit_sheet`。`finished_at` 有值就算结束；还在 `running` 就继续等；查不到当天记录，分别按 15:30、20:30 结束算。调度钟点以 `registry/schedule.py` 的现值为准（现为 13:00 和 18:10）。
- c. 上一块已经认完账，没有本技能自己的审核进程还在跑。
- d. 窗口剩余时间 ≥30 分钟。窗口终点取之后最近的一个：工作日 09:00、工作日 14:00、每天 12:40、每天 17:50。

不满足就把 G 记成受阻，`resume_at` 写下一个窗口的起点，去推别的环节。

### G3 组块与执行
```
可用分钟 = 窗口终点 − 现在 − 20
块大小   = min(8000, 待审数, floor(速率 × 可用分钟))
```
- 速率取最近 3 块实测值（个/分钟）里最小的。还没有实测值时，第一块固定 300 个用来测速，并且要求窗口剩余 ≥120 分钟。
- 算出的块大小不足 100 且小于待审数 → 这个窗口不再开块，等下一个窗口。
- 块里只放 `audit_wait` 和到期的 `pending_retry`。**这个入口是点名强审，传进去的每一个都会真审、真花钱**，所以已有结论的绝不能混进去。
- 先把清单写进 `audit/chunk_<序号>.txt`、state 里记块的 `started_at`，再启动：
  ```
  ( .venv/bin/python cli.py product_audit -p asins=<逗号分隔的本块 ASIN> ; echo "EXIT=$?" ) > <RUN>/logs/audit_chunk_<序号>.log 2>&1 &
  ```
  后台运行，记下 pid。每 5–10 分钟看一次进程是否还在；等待期间继续推别的环节。
- 不用 `force=1`、`force_rerun`、`mode=nonpass`、`mode=pending`，不改审核层级。`--dry-run` 也会产生 LLM 费用，不能当免费预检。
- 块跑过了窗口终点：**不杀进程**，让它跑完；把实测速率记低，并在进度卡里写明超时了多久、是否挡到了调度。

### G4 逐款认账（每块结束后必做，只读）
```sql
SELECT t.asin, p.audit_status, p.audit_version, p.audited_at, p.audit_reason,
       (p.title IS NOT NULL AND p.title <> '') AS has_title
FROM unnest(%(asins)s::text[]) AS t(asin)
LEFT JOIN catalog.products p ON p.marketplace = 'US' AND p.asin = t.asin;
```
对本块每个 ASIN：
- `audited_at ≥ 块的 started_at` = 这一块审到了。approved → `approved`；rejected → `x_rejected`；pending → 第一次送审记 `pending_retry`（到期 = 审核时间 + 24 小时），第二次仍 pending 记 `x_pending`，原因写库里的审核类别。
- 否则 = 这一块没审到它：
  - 块是异常退出的（退出码 1 或 3）→ 留在 `audit_wait`，进下一块，不计送审次数。
  - 块正常结束（退出码 0）却没审到 → 看 `has_title`：标题为空的记 `x_scrape`，原因"无标题，无法审核"；有标题的留在 `audit_wait`，「送审次数」加 1，满 3 次仍没有结论 → `x_pending`，原因写"三次送审未出结论"。

审核是每 200 个落一次库的，所以块中途断掉时已经审完的不会丢，靠这一步认领回来。**不许把整块原样重跑**：重跑前必须先认账，只带没审到的。

同时记录本块：日志里的摘要行（`product_audit(<版本>):候选 N,判定 M(过 x/拒 y/待定 z)`）、退出码、耗时、实测速率、费用（日志里给了才记，没给写"未知"，不估算）。摘要里的"判定 M"和认账得到的数对不上时，以认账为准并记下差异。

### G5 出口
`f_pass` = 0、`audit_wait` = 0、到期的 `pending_retry` = 0，再对全部通过 F 的 ASIN 跑一遍 G4 的 SQL 复核。成立才算 G 完成。

## H. 预览分配（只读）

每一轮都要出一份预览。预览是**累计版**：池子是 ledger 里全部审核通过、还没执行的款（不只是本轮新增的），配额是本轮重算的最新缺口。

### H0 预览前刷新
进入条件：预览总闸的前四条已经成立。预览要用新数据，但刷新可能把个别款打回待审，所以**只在审核窗口开着时做**（G2 的 a、b 两条成立；没开就把 H 记成受阻，`resume_at` 写下一个窗口起点）。24 小时内做过就不重复，时间记在 `lanes.H.fresh_at`。刷新期间这些行的状态不变，只按下面的结果改；刷新批次收口之后才能进 H1。

1. 重算 A3 和 C，得到最新缺口。
2. ledger 里 `approved`、且认账的那条快照已超过 24 小时的款：按 E 段流程编一个 `sel_<周>_r<轮>_fresh<序号>` 批次重采、入库、取回执、逐款认账。
3. 认账成功的款换成新的 `source_id`，重跑 F1：不过的改 `x_supply`，原因写"刷新后不符：<哪一条>"。认账失败的按 E 第 8 步重采一次，仍失败改 `x_supply`，原因写"无 24 小时内数据"。
4. 重采后库里审核状态变回 pending 的（商品内容变了，入库时会自动翻回待审）：重做 F2，不通过的按 F2 的结果落终态，通过的改 `audit_wait`，回 G。

### H1 核对预览总闸
逐条核对第三节的五条。有一条不成立就回对应环节，不出预览。

### H2 出预览
**用标准引擎出预览，不在仓库外重组 `alloc_engine`。** 把 ledger 里全部 `approved` 的 ASIN 写成 `preview/pool_<预览号>.csv`（表头 `ASIN`），把最新缺口写成 `preview/quota_<预览号>.csv`（表头 `店铺,配额`，有效目标为 0 的店写 0 或不写），然后跑
`cli.py alloc_plan -p pool_csv=<pool.csv> -p quota_csv=<quota.csv> --dry-run`。
这两个参数只出预览（方案表在 reports 目录），不落占用；限定池默认不设淘汰线。输出以 ⛔ 开头 = 被拒绝，按提示回去补齐，不改清单硬过。跑完把 reports 目录里的方案表复制进 `preview/`，带上预览号。

约束：
- 以实时占用为准：品牌唯一去向；同一产品不重复；原占用店符合条件的归原店。
- 归属店不在本轮范围的单列，不算可分配。
- 不释放、不落占用、不写飞书；没执行的预览不算占用。
- `approved` 为 0 时也照样出预览：分配表为空，其余各表照出。

### H3 逐款归因
`pool.csv` 的每个 ASIN 都要有去处：方案表里分到了店的，填「分配店」；没分到的，对照预览摘要的漏斗填「未分到原因」（不在候选池：<原因> / 硬闸：<原因> / 已在架 / 没有店的条件容得下 / 组队时剔除 / 品牌归属店不在本轮范围 / 排名靠后没发到）。归不出原因的写"原因待查"，数量大于 0 要写在预览首页。分到了店、但这个（店, ASIN）已经在上架表里有效待上架的，改记未分到原因"已在上架表"，不计入模拟分配。然后核对恒等式第 5 条。

引擎读的是库里最新一条地区校验没问题的快照，可能比认账那条更新（别的任务后来又采过）。两者不一致时以引擎的结果为准，差异落在"硬闸"这类未分到原因里，不另行改判。

### H4 续轮判定
```
剩余缺口 = Σ 各店 max(缺口 − 本份预览给该店的模拟分配, 0)
```
按顺序判断：
1. 剩余缺口 = 0 → 选品结束，`selection_end = gap_zero`。
2. `range_exhausted = true` → 选品结束，`selection_end = range_exhausted`。预览首页写明真实剩余缺口，请所有者决定是否放宽条件。
3. 其余 → 交付本份预览之后**立刻开下一轮**：`round` 加 1，回到 A3、C 重算缺口和本轮初选量，D 从计划里第一个未导出项接着做。已取得的候选、已有的审核结论都沿用。

**只有前两条能结束选品。** 下面两种情况只提醒、不停，写进预览首页和进度卡的"提醒"栏，同时记进 `rounds[].notes`：
- **本轮零产出**：本轮新增候选里一个可分配的都没有。写出本轮新增多少款，分别掉在哪一层（采集失败 / 供货不符 / 经营模式排除 / 待核 / 审核拒绝 / 各未分到原因），列出占比最高的三项。
- **轮数偏多**：已到第 5 轮及以后。写出本周累计导出独立 ASIN、累计可分配、实测倍数、还剩多少计划项没导出。

## I. 预览交付（每一轮都交付，不等确认）

每一轮出一份 Excel：`preview/preview_<两位预览号>.xlsx`，包含以下表：
- 首页：本轮结论、本轮新增与累计、剩余缺口、提醒（零产出 / 轮数偏多）、需要所有者决定的事项、此前各份预览的状态
- 运营状况分析
- 总览：在线、目录总数、有效待上架、在途、建议下架、在线余量、目录余量、缺口、模拟分配、剩余缺口
- 亚马逊类目 / 沃尔玛类目 / 亚马逊价带销售总览（含 SKU 数和货位产出）
- 删除表：真实 SKU、ASIN、动作（停用或删除）、原因、库存时间、销量、退货样本（不含已经在删除表里待执行的）
- 分配表：店、ASIN、品牌键、采购价、库存、配送、货期、快照时间、审核、占用依据、是否本轮新增
- 三分类明细（含 BSR 证据和参数）
- 待核（`x_hold`，逐款原因）
- 审核待定（`pending_retry` 和 `x_pending`，逐款原因）
- 未分到（逐款原因）
- 已执行批次回报（见 K）
- 流程对账：ledger 各状态数量、每个采集批次的对账（本批成功 / 他批成功 / 本批失败）、每个审核块的结果和费用；本轮初选量 / 本轮新增 / 审核通过 / 可分配 分开列

检查公式、汇总、身份键和明细是否一一对应；对账表的各状态数量之和必须等于 ledger 行数。

交付 = 把文件路径和进度卡发给所有者，并在 `state.previews` 里登记（预览号、轮次、文件、交付时间、池子数、分配数、剩余缺口，`status = delivered`）。**交付之后不等回复**，按 H4 的结论继续：开下一轮，或者选品已结束就把 `status` 改成 `waiting_owner` 后停下。

所有者的回复随时可能到，按下面处理：
- **确认某一份预览**（全部或指定范围；没说哪一份就是最新一份）→ 把原话、时间、范围记进那份预览的 `owner_text`，进 J。任何一份 `delivered` 状态的预览都可以确认。
- **执行完一份之后**：其余还没执行的预览全部标 `superseded`（它们和刚执行的内容有重叠）。当前有一轮正在进行的，不单独重出，这一轮收尾时的预览自然不含已执行的款；选品已经结束的，只要 ledger 里还有在途或 `approved` 的款、且还有店有缺口，就把在途的走完（G），重算缺口，按 H 重出一份新预览交付。
- **要求修改**（删行、放行待核、调整删除表）→ 记进那份预览。只删行的直接体现在执行清单里；放行待核的款改回 `f_pass`，随当前这一轮走审核，出现在下一份预览里。
- **没有回复** → 继续选品，不做任何写操作。

## J. 确认后执行（针对被确认的那一份预览）

把那份预览标 `executing`。每一步都是"核对前提 → 执行 → 回读核对 → 落盘"，一步 `done` 才做下一步。J 做完之后，上架和下架由系统调度完成，本技能不等它们的结果，回去继续选品。

**写表避让**：上架表不在 17:50 到当天 `audit_sheet` 结束之间写；删除表不在 14:45 到当天 `product_clear` 结束之间写（结束与否查 `ops.runs`）。在避让时段内就等，等的时候选品照常推进。18:10 之前写进上架表的当晚上架，之后写的次日上架，在进度卡里告诉所有者是哪一天生效。

1. **J1 复核。**
   - 重新读实时在线、待上架、在途、占用、黑名单、登记簿、`ops.dispositions`。
   - 执行清单里认账快照超过 24 小时的款：按 H0 第 2–3 步重采、认账、重跑 F1。
   - 用 G4 的 SQL 复核审核状态：不是"approved 且当前版本"的行，此刻审核窗口开着就立即按 G 段审完再定；窗口没开就从执行清单里拿掉，改回 `audit_wait`，留给当前这一轮。
   - 占用、已在架、黑名单发生变化导致不再成立的行，从执行清单里拿掉。
   - 所有拿掉的行写进 `exec/dropped_<预览号>.csv`（原因逐行写明）。供货不符的落 `x_supply`；其余仍是 `approved` 的，会出现在下一份预览里。
2. **J2 执行容量。** `当前空位 = 有效目标 − 在线(或目录总数) − 有效待上架`，**不预支未完成的删除**；有效目标为 0 的店不进清单。超出空位的行列入"待腾位"，不执行，仍是 `approved`，留给下一份预览。产出 `exec/exec_<预览号>.csv`（UTF-8，表头 `店铺,ASIN`）。
3. **J3 落占用。** 跑 `cli.py alloc_plan -p from_csv=<exec.csv>`。任一行不过它会整批拒绝、一行不落：按报错拿掉问题行（记进 `dropped`）再跑；拿掉三次仍被拒绝就停下，请所有者看报错。
   回读：`services.claims.load_active(conn, PRODUCT)` 里清单的每个 ASIN 都归在目标店。
   续跑：先回读。全部已落 = 完成；否则用同一份清单重跑（同一家店的占用可以重复落）。
4. **J4 写上架表。** 跑 `cli.py alloc_push -p from_csv=<exec.csv>`。只写店铺和 ASIN 两列，审核结果留空。已有未弃用 SKU（含 UNPUBLISHED）的会被拦下，单列出来。
   回读：`services.listing_sheet.read_rows()` 里有清单的每个（店, ASIN）。
   续跑：先回读，缺的用同一份清单重跑（表里已有的行会自动跳过）。
5. **J5 写删除表。**
   - 清单 CSV 表头 `店铺,SKU,动作,原因`；SKU 是沃尔玛真实 SKU；动作只写"停用"/"下架"/"删除"，**不能留空**（留空在系统里等于删除）。
   - 跑 `cli.py retire_push -p from_csv=<删除清单.csv>`。它整批校验：店铺在营、SKU 在目录未缺席、自动删除链（`ops.dispositions`）里没有同 SKU 未落定的 delete/retire；任一行不过就整批拒绝，按报错拿掉后记录再跑。
   - 回读：`services.clear_sheet.read_rows()` 里有清单的每个（店, SKU）。
   - 续跑：先回读，缺的用同一份清单重跑（表里已有同 SKU 未落定行会自动跳过）。

五步都 `done` 后：
- 执行清单里的款在 ledger 里改成 `executed`，填上预览号；预览标 `executed`。
- 向所有者报告一行：落占用多少、写上架表多少、写删除表多少、拿掉多少、待腾位多少、哪一天生效。
- 按 I 段"执行完一份之后"处理其余预览。
- 以下全部成立 → `status = done`：选品已结束；没有 `delivered` 状态的预览；ledger 里没有在途状态的款（`new` 到 `audit_wait`）；没有 `approved` 的款，或各店缺口都为 0。收尾时把还留在 `pending_retry` 的改成 `x_pending`（原因"本周结束前未到重审时间"），剩下的 `approved` 在最后一行报告里按"未执行"报数，删除 `run.lock`。

## K. 执行回报（只读，不阻塞）

写进表格之后的事由系统调度完成：18:10 `audit_sheet` 审、20:00 `list_new` 上架、15:00 `product_clear` 执行删除表。本技能**不等这些结果**，只在每一轮盘点（A3）时顺手读一遍已执行各行的现状，写进下一份预览的"已执行批次回报"表：

| 现状 | 判据 |
|---|---|
| 已上架 | 该（店, ASIN）在目录里且 PUBLISHED |
| 待上架 | 在上架表里，符合 A3"有效待上架"的口径 |
| 审核拒绝 | 上架表「审核结果」为拒绝，或库里审核是 rejected |
| 上架失败 | 上架表「上架结果」是失败类（写明原因） |
| 删除表：已执行 / 待执行 / 失败 | 删除表该行的执行结果列 |

- 这些行在缺口公式里已经各归其位：已上架的算在线，待上架的算有效待上架，被拒绝或失败的两边都不算、货位自然回到缺口里。不需要另外处理。
- 调度当天该跑没跑（`ops.runs` 里没有记录）：在进度卡的"提醒"栏报告，不自行补跑。所有者要求手动补跑时注意：`cli.py product_audit -p from_sheet=1` 处理的是**整张上架表**，`product_clear` 处理删除表里的全部待办，都不只是本周写入的行；手动上架只用实际写进表格的清单 `cli.py list_new -p from_csv=<实际派工清单>`。
- 失败或不确定先对账；删除不释放占用。

## 六、禁止事项

- 审核没出完就出预览或分配表，包括"先看一版""部分预览"。
- 本轮采集批次还没全部逐款认账、检查还没做完，就开审核块。
- 只凭"库里有快照、有标题"认定这一批采到了，不看本批回执的 `source_id`、结果和完整性。
- 缺口不为零、查询范围也没走完，却因为"本轮没产出""轮数多了""等所有者确认"而停止选品。
- 新的一周自动接着做上周没做完的运行（所有者点名要求的除外）。
- 为了让闸通过而缩小候选：从 `pool.csv` 或 ledger 里删行，或把在途状态直接改成终态。
- 在高峰时段开审；占着审核锁跨进调度保留时段；杀掉正在跑的审核进程。
- 把整块 ASIN 原样重跑（重跑前必须认账，只带没审到的）。
- 用 `force=1`、`force_rerun`、`mode=nonpass`、`mode=pending`，或拿 `--dry-run` 当免费预检。
- 换批次名重提同一份采集清单；重置采集游标。
- 重新导出卖家精灵导出历史里已有的查询；自行改价格、配送、类目、评分等固定条件。
- 在所有者确认之前写占用、写上架表、写删除表；在确认范围之外多写一行；执行一份已经 `superseded` 的预览。
- 在脚本里直接写库或写飞书；在仓库外重组分配引擎；释放占用。
- 凭对话记忆判断进度；跳过对账；同一周同时开两个会话。
- 在三种允许的情况之外结束会话。

## 七、进度卡

每交付一份预览、每次停下、每次进入长等待之前输出，固定格式：

```
【选品 2026-W48】状态 running，第 2 轮
缺口 12,400｜剩余缺口 5,100｜本轮初选量 15,300｜本轮新增 9,800（卖家精灵 S1，今日导出 50/50，计划项剩 37 个未导出）
采集：本批成功 9,100｜他批成功 120｜失败 580（其中转重采 300）
检查：可送审 4,700｜排除 3,600｜待核 150｜供货不符 770
审核：通过 2,100｜拒绝 500｜待定 30｜未审 2,070
预览：01 已执行｜02 已交付，待确认（preview/preview_02.xlsx，分配 7,300）
受阻：卖家精灵额度用尽（明天 00:05 恢复）；审核等窗口（今天 20:35）
提醒：无
下一步：20:35 开第 3 个审核块
需要你：确认或修改预览 02（不确认也会继续选品）
```

- "提醒"栏写诊断信息：本轮零产出、轮数偏多、调度没跑、审核块超时等。没有就写"无"。
- "需要你"栏只写必须由所有者处理的事：确认预览、登录卖家精灵、决定是否放宽条件、看拒绝报错、上周停在执行中途的运行要不要补。没有就写"无"。
