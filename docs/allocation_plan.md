# 第一部分 现行设计(唯一权威)

## 一、需求(所有者原述,未变)

1. 一个品牌只能同时存在于一家店(采集数据带真实品牌;提交沃尔玛仍
   Unbranded,两不冲突);
2. 一个产品(ASIN)只能同时存在于一家店;
3. 一个店最多做**两个大类目**;
4. 一个店只做**一种配送方式**(FBA 或 FBM)(2026-08-13 追加);
5. 约束在**前期产品进来后的分配阶段**执行;
6. 店铺终止运营 → 释放其占用的品牌与产品;暂停 → 绑定保持;
   救不回来的暂停店 → 手动点名释放;
7. **只要没决定停止运营,品牌和产品就不能出现在其他店——即使当前没有上架
   到这个店也不行**(占用与在线状态无关);
8. 分配本身是复杂决策:好坏产品要筛,店铺间怎么分要参考订单/销量/销售额/
   在线数/容量等数据。

## 二、核心原则

**占用是决策台账,不从在线快照推导。** 在线产品(`catalog.walmart_items`)
是观测,天天抖动;归属(占用)是决策,只有"分配"和"释放"两个显式动作能改。
两者解耦,占用才稳定——与病历(`product_events`)的"决策/观测"分层同源。

**释放只走显式动作,没有任何代码自动释放占用。** 这是稳定性的根本保证。

**永久决策要更硬的证据。** 上架错了是一条 feed 失败,占用/开类目错了是
**永久烧掉一个槽位**(无自动释放)。凡属永久决策的动作,证据门槛单独提高
(体现在 §三.3 的 PT 实证要求)。

## 五、占用台账设计

**`catalog.claims`**(品牌占用 + 产品占用,一行一个占用):

| 列 | 说明 |
|---|---|
| kind | `brand` / `product` |
| claim_key | 品牌键(`services/brand_key`)或 ASIN |
| store | 占用店铺 |
| status | `active` / `released` |
| walmart_pt / pt_source / audit_version | **决策时快照**——映射表是活表(catmap 在写)、重采会把 approved 翻 pending,不快照就无法回答"当初按什么分的"(08-15) |
| claimed_at / released_at / released_reason | 生命周期与审计(released 行保留不删) |

排他性由 PG 保证,不靠代码自觉:
`UNIQUE (kind, claim_key) WHERE status='active'`(部分唯一索引),
并发领用与 UPC 池同款事务纪律。

**没有 store_categories 表、也没有 store_channel 表**(2026-08-15 定稿):
店铺档案的两项约束——准入大类与配送方式——**权威都在飞书限额表的列里**
(类目1/2/3、配送限制),引擎只读不写。这样定的三个理由:
① 所有者改一格就生效,不需要跑任何 workflow;
② 引擎**永不自行开类目**,"开新大类要不要实证 PT"这个难题直接消失
   (84% 候选是推断 PT,靠证据等级卡门槛会把空店全部卡死);
③ 类目档案本就是运营决策不是系统状态,放系统里反而要造一套同步机制。
判定唯一出处:`services/store_targets.allowed(cfg_row, category)`。

## 六、生命周期与释放

1. **占用产生于分配,不产生于上架**:产品分给某店的那一刻,事务内同时
   占品牌 + 占产品 + 核类目 + 核渠道,占不到就不能分给这家店。之后下架、
   清零、从未真正上架,占用都不动。品牌已属于某店的产品只能"定向"去那家店
   (还得过它的类目/渠道/容量),去不了就淘汰。
2. **暂停 = 什么都不做**,占用天然保持;SUSPENDED 店的在线行仍计入冲突统计。
   停用只是暂时不给它分新货,**不代表别店可以来拿它的品牌与产品**——
   店没在关,它的东西就还是它的(§一 所有者原述)。
   ⚠ 2026-08-15 晚一度被误改成"当作全新店(不建占用)",所有者当即纠正:
   **口径没变,仍是「暂停不释放、占用保持」**。要某店暂时不接新货走 2a,
   那是配额开关,与占用归属是两件事。
2a. **"暂时不给某店分货"的正确做法**:限额表「**单店最大在线数**」填 `0`
   (`services/store_targets.accepts_allocation`,所有者定稿 2026-08-15 晚)。
   与类目、配送限制同一治理方式——改表格一格就改行为,不建表、不改代码,
   **也不动占用**。**三态不许压成两态**:`0` = 所有者按下"不接货";
   `None` = 还没填(报告点名补填);`>0` = 参与。写成 `not max_online`
   会把没填的店一并算成不接货 —— 它于是永远分不到货,而且不报错。
3. **终止 = 显式释放**:workflow `store_release --store X`(dangerous,默认
   dry-run 列清单):该店全部 active 占用置 released(reason=terminated)、
   **同步把该店 walmart_items 行标 missing_since**(§九.4;`-p mark_offline=0`
   可关)。类目与渠道是飞书配置,不归它管。
   **留痕在 claims 表自身**(released 行 + reason + 时间),不写 product_events
   ——事件账本的入账边界是"产品生死与观测事实",占用是决策,两边各记一份
   反而要维护两套口径。
4. **手动个别释放**:同 workflow `--brand` / `--asin` 精确释放。
   除以上两条显式路径外无任何自动释放。
5. **TERMINATED 只触发"可释放资格"**:审计发现"已终止仍有 active 占用"→
   告警列清单 → 人跑 store_release。KPI 是外部观测,误报若触发自动释放,
   品牌被别店占走后不可撤销。

## 七、分配引擎

### 7.1 候选池

从 `catalog.products` 取:审核 approved ∧ 有标题 ∧ PT 有效 ∧ 大类查得到 ∧
产品未被占用 ∧ 渠道已知(FBA/FBM;未知的不参与,计数可见)。
逐层收窄的真实数字由 `alloc_audit` P1 给出。

### 7.2 分配单元 = 品牌组

按 `services/brand_key` 分组:
- 品牌组整组定店;组过大时可只分组内产品分 top-N,其余不占 product 占用
  ——品牌已占用,后批这些品自动定向同店,排他不破;
- 真·无品牌(brand 与 manufacturer 皆占位符)= 逐 ASIN 为单元,只占 product。

### 7.2b 规划范围外的店(不参与,但数据照用)

`registry.alloc_excluded_stores()` 命中的店(当前 = 店名含「谭总」)整体
退出分配体系:不进候选店集合、不占品牌与产品、不判类目与渠道、其在线
商品不进冲突清单、也不参与 list_new 的全局 ASIN 去重(⇒ 规划内的店**可以**
与它们重复上同一品牌/产品)。
**销量数据不受影响**:它们的订单照常进产品/品牌/类目三个全局销量维度,
是别的店选品时的有效信号。排除的是"归属"不是"数据"——这条区分要记牢,
把数据也一起排掉会白白丢掉一大块选品依据。

### 7.3 两条流水

- **定向流**(品牌已被占用):只能去占用店;过该店硬闸(状态 ACTIVE ∧ 在册 /
  类目 / 渠道 / 容量 / 黑名单)→ 过不了**整组淘汰**,淘汰行进方案表并注明
  被哪道闸拦下(所有者可选择先点名释放品牌再重分)。定向流**不分梯队**
  (品牌绑定是强制路由)。
- **自由流**(品牌未占用 / 无品牌):走 7.4~7.5 打分匹配。

### 7.4 店铺经营水平(所有者定稿 2026-08-15 晚,**取代原"固定除以 30"**)

> **原文这里写的是**「近 30 天日均 GMV 分母固定用 30(与日目标自洽),不用
> "有记录天数"」。**这条是错的,所有者当日指出**:三个月里店铺暂停过,
> 那段时间根本不存在销售额,拿日历天数当分母会把"停过业"读成"卖得差"。
> 后果是反向的 —— 缺口被高估 ⇒ 配额被放大 ⇒ **停过业的店反而被灌最多货**。

**分母一律是「在售天数」,不是日历天数。** 数据现成:`ops.store_kpi_daily`
逐店逐日一行,带 `store_status` / `items_online` / `orders_count` /
`sales_amount`。

```
窗口 = [as_of − N 天, as_of)             # N 默认 90;与冲突判定共用 sales_window
rec_i     = 窗口内该店**有 KPI 记录**的天数
active_i  = 其中 coalesce(upper(store_status),'ACTIVE') = 'ACTIVE' 的天数
cover_i   = rec_i / N                     # 覆盖率,低了下面的比值都不可信
items_i   = 窗口内 active 天的 items_online **均值**(不是最后一天的值)
```

⚠ **没有 KPI 记录的那些天既不算 active 也不算停用**——那是"没抓到",不是
"没营业"。所以 `active_i` 只从有记录的天里数,并且 `cover_i` 必须一起报出来:
覆盖率低就说明这家店的指标本来就不该拿来跟别人比(处理见下面的收缩)。

三个归一化指标(都用 `active_i` 当分母):

| 指标 | 算式 | 回答什么 |
|---|---|---|
| **日均净销售额** | `净额_窗口 / active_i` | 规模:这家店一天能净卖多少(退款已扣,见 7.4e) |
| **单品日产出** | `净额_窗口 / active_i / items_i` | **效率:给它一个货位值多少钱** |
| **日均订单** | `orders_窗口 / active_i` | 需求密度 |

**单品日产出是分配最该看的那个**,理由:一家 500 SKU 做 500 美元/天的店,
每个货位只值 1 美元;一家 100 SKU 做 300 美元/天的店,每个货位值 3 美元。
后者才是好货该去的地方,而只看总 GMV 会得出相反的结论。

**样本不足要收缩,不能直接用。** 与 §八 层级回退同一套写法:

```
active_i <  14  → 三个指标**一律取全店中位数**(所有者拍板:少于 14 天
                  就不信它的数据),方案表标记「样本不足」
active_i >= 14  → shrunk_i = w·本店 + (1−w)·全店中位数,
                  w = active_i / (active_i + 14)
```

为什么 14 天以下是**硬切**而不是继续收缩:那个区间的比值噪声大到没有
信息量(一单大额就能把单品日产出抬十倍),而收缩公式在 `active=2` 时
仍会留 12.5% 权重给它。**新店 active_i=0 落在同一条规则里**,
天然冷启动,不需要特判。

`cover_i < 0.3` 的店在方案表单独标记「KPI 覆盖不足」——不是不给货,是提醒
所有者这家店的三个指标都是中位数顶上来的,不代表它真实水平。

### 7.4a 配额(目标缺口 + 效率,双驱动)

```
gap_i   = clamp01((日目标销售额_i − 日均GMV_i) / 日目标销售额_i)   # 分母已是在售天数
room_i  = max(0, 单店最大在线数_i − (在线数_i − 待下架数_i))       # ★ 预支下架名额
eff_i   = 单品日产出_i(收缩后)/ 全店单品日产出中位数,clamp 到 [0, 2]
need_i  = w_gap·gap_i + w_room·min(1, room_i/批量) + w_eff·min(1, eff_i/2)
quota_i = min(room_i, ceil(批量 × need_i / Σ need))
```

**`w_eff` 是新增项,它防的是"只看缺口"这个陷阱**:一家店缺口大,可能是因为
它卖不动,再猛给货只是把库存压过去。gap 与 eff 有意拉反方向 —— 要找的是
**低于目标、但有能力**的店。权重初值 **`w_gap=0.6 / w_room=0.25 / w_eff=0.15`**(所有者拍板 2026-08-15 晚:
**把货给离目标最远的店** ⇒ 缺口主导);进配置文件,首批 dry-run 对着方案表砍,
要纯缺口驱动就把 `w_eff` 设 0。

**★ 容量预支**:`room` 要减掉「待下架数」(类目不符 + 渠道不符 + 冲突输家
三份清单里属于该店的行)。所有者是**一边下架一边上架**的,不预支的话,
一家马上要空出 300 个货位的店会被算成"满了",这一批一件都分不进去。
待下架的货**已经不产生占用**(§三.16 类目闸在 `claimable` 里),所以那些
品牌与 ASIN 此刻就能分给别人,**不必等实际下架完成**。

### 7.4b 反堆积:分层轮转发牌(所有者定稿 2026-08-15 晚)

§7.5 的警告说了"不许按分数顺序分配",这里是它的具体做法。

```
1. 自由流候选按产品分降序,切成若干**分数层**(层厚初值 10%,配置化);
2. **逐层**发牌;层内不按"这一组最适合谁",而按
       已接量_i / quota_i  升序轮转 —— 谁离自己的配额最远谁先拿;
3. 该店过不了硬闸(品牌/类目/渠道/容量/黑名单)→ 顺延下一家,不回头;
4. 每发一组即时更新 已接量_i,下一次挑人看的是更新后的世界。
```

为什么分层:光靠"超配惩罚"只能保证**数量**分散,保证不了**质量**分散 ——
一家店可能先把 top 10% 吃到配额上限,后面全是尾货给别人。分层之后,
**每一层都按配额比例分给所有店**,好货天然摊开。

**验收指标(必须进方案表,不是"希望如此")**:

| 指标 | 期望 |
|---|---|
| 每个分数层的**店铺分布直方图** | 与各店 quota 占比接近 |
| 每店「拿到的 top 层数量占比」 ÷ 「quota 占比」 | 落在 [0.7, 1.3];超出就是参数没调对 |
| 单店本批接货量 / 全批 | 不超过 `1.5 × quota_i/Σquota` |

**首批 dry-run 必须人眼看这三个数**。一家独大 = 参数错了,不是"模型判断"。

### 7.4c 产品没有销量怎么办(常态,不是异常)

实测绝大多数候选没有任何订单史。三条纪律:

1. **缺失不等于 0**,禁止 `or 0`(§三.8)。该项**不计入**,权重按比例
   **摊回其余信号** —— 不是给它 0 分,那等于惩罚"新品"。
2. **层级回退取代理信号**(§八):
   `该 ASIN 销量 → 该品牌销量 → 该大类需求基线 → 全局基线`,
   逐级按 `w = n/(n+N0)` 收缩,N0 初值 30。
   ⚠ 前两级**依赖 A1.5**(`order_lines` 加 asin 列),没做之前只有
   「该大类基线」这一级可用 —— 这是 A2 的硬前置,不是可选项。
3. **销量只加分不减分**(§三.8):卖过且卖得动是强信号;没卖过只是没信息。

### 7.4d 货位值:**量出来的历史均值,不是预测**(所有者追问 2026-08-15 晚)

「好货放进去能产出多少」**预测不了**,也不该假装能。能量的是这个:

```
货位值(店 i, 大类 c) = 净销售额(i,c,窗口) / active_i / 在线数(i,c)
                                 ↑            ↑         ↑
                            退货已扣      在售天数   该店该大类的在线件数
```

三条纪律:

1. **按大类分,不按整店分。** 整店单品产出会被该店的品类结构污染 ——
   一家店 Home 卖得好、Fashion 卖得烂,整店均值对两边都不对。要回答的是
   "在这家店放一个 **Home** 货位值多少钱"。
2. **净销售额,不是 GMV。** 见 7.4e。GMV 不扣退货是虚高,而退货率是店铺
   履约能力的直接体现 —— 两家店同样卖 1000 美元,退掉 400 的那家实际只
   产出 600,还多赔一次运费和一个差评。
3. **它是历史均值,不是对新品的预测。** 样本不足(新店、新开的类目)按
   `w = n/(n+N0)` 收缩回**全店同大类中位数**,n = 该店该大类近窗订单数。
   真正的预测能力要等 §7.8 的决策快照攒够 2-3 个月,A3 回归出来才有。

**产品分与货位值不相乘。** 相乘等于假装能算出"这个品在这家店能卖多少钱",
那是没有依据的。两者分工明确:

| 量 | 决定什么 |
|---|---|
| 产品分 | **发不发、先发谁**(淘汰线 + 排序) |
| 货位值(店×大类) | **发给谁**(同一组货,哪家店的这个类目货位更值钱) |

### 7.4e 退货:销量口径一律用净额(所有者追加 2026-08-15 晚)

「不止看销量,还要看退货」。落到三处:

| 用处 | 口径 | 数据源 |
|---|---|---|
| 店铺货位值 / 日均 GMV | **净销售额 = GMV − 退款额** | `orders.return_lines`(PK `(return_order_id, order_line_id)`,按 `order_line_id` 回连 `order_lines`;`refund_total` / `refunded_qty`) |
| 产品分·退货率 | 该 ASIN 的 `退货件数 / 售出件数`,**减分项** | 同上,依赖 A1.5 的 asin 列 |
| 店铺履约 | KPI 表 `return_rate` / `refund_rate` 列 | `ops.store_kpi_daily`(展示用;阈值未拍板前不进公式,同 8 率) |

⚠ **历史期算不出退货**(§四"历史行的三条语义"):`order_history_import`
只导销售六列,「退款原因」「统计状态」都没进来,`return_lines` 也只有
API 期的数据。所以:
- **窗口跨历史期时,退货率按"没数据"处理,不当"零退货"**(禁 `or 0`);
- 净销售额在历史期 = 毛额,**方案表必须标注该店的窗口有多少天落在历史期**,
  否则 API 期的店会因为扣了退货而显得比历史期的店差,那是口径不同不是经营差。

### 7.4f 「待下架数」怎么来(所有者追问 2026-08-15 晚)

三份处置清单里属于该店的行,**按 `(店, SKU)` 取并集去重**:

```
待下架_i = |{ (店,SKU) : 店 = i } ∩ (
              alloc_类目不符下架清单.csv
            ∪ alloc_渠道不符下架清单.csv
            ∪ 两份冲突处置.csv 里 处置='下架' 的行 )|
```

⚠ **必须去重**:同一行可能同时是"类目不符"和"冲突输家"(很常见 ——
类目闸本来就是冲突判定的硬闸)。不去重会把 room 高估一倍,配额跟着虚高。

⚠ **预支只影响配额,不放宽容量硬闸**:

| 环节 | 用哪个数 | 为什么 |
|---|---|---|
| 算 `quota_i`(谁多分谁少分) | `max_online − (在线数 − 待下架数)` | 乐观:马上要空出来的货位应该参与分配 |
| `list_new` 真上架时的容量闸 | **当前真实在线数** | 保守:下架没做完就上架会真的超 `max_online` |

分配是**计划**,上架是**执行**。计划可以预支,执行时按实际核实 ——
所以方案表要标注「本店 N 件依赖 M 件下架先完成」,让所有者知道先后顺序。
清单是**建议**不是事实:所有者未必全下架,所以预支天然乐观,
方案表把「当前 room」与「预支后 room」两个数都列出来,差多少一眼可见。

### 7.4g 三个参数定稿(所有者拍板 2026-08-15 晚)

| # | 参数 | 拍板 | 落到哪 |
|---|---|---|---|
| 5 | 效率 vs 缺口 | **把货给离目标最远的店** ⇒ `w_gap` 主导 | `w_gap=0.6 / w_room=0.25 / w_eff=0.15`;要纯缺口驱动把 `w_eff` 设 0 |
| 6 | 在售天数下限 | **少于 14 天就不信它的数据** | 硬规则,见下 |
| 6a | 薄样本的**缺口**怎么算(08-15 晚追加,两条决策冲突后拍板) | **缺口用实测、效率用中位数** —— 两条各管各的量 | 「不信薄样本」管的是**比值**(货位值,一单大额能抬十倍);「把货给离目标最远的店」管的是**缺口**,而一件没卖的空店确实最远。拿中位数替换缺口会让它显示成「平均水平」排在真卖得动的店后面 —— 方向反了。生产实测:82杨乾良 在线 0、一件没卖,却和中位数店 M001 并列缺口 66% |
| 7 | 分数层层厚 | **10%** | §7.4b 发牌分 10 层 |

**关于 5,已提示过的风险记在这里,不再重复**:缺口大有可能正是因为这家店
卖不动,纯缺口驱动会把货压给最卖不动的店。所有者已知情并选择缺口优先;
`w_eff=0.15` 保留为**同缺口时的次级排序**,首批 dry-run 看方案表再砍。

**关于 6,`active_i < 14` 是硬规则不是收缩**:

```
active_i <  14  → 三个指标**一律取全店中位数**,方案表标记「样本不足」
active_i >= 14  → shrunk = w·本店 + (1−w)·中位数,  w = active_i/(active_i+14)
```

两段而不是一段的理由:14 天以下的比值噪声大到没有信息量(一单大额就能
把单品日产出抬十倍),收缩公式在 `active=2` 时仍会留 12.5% 的权重给它,
而所有者的判断是"这种数据一点都不信"。**新店 active=0 落在同一条规则里**,
不需要特判 —— 天然冷启动。

### 7.5 匹配循环(两梯队 + 事务内占用)

> **⚠ 不许"按分数从高到低顺序分配"**(所有者定稿 2026-08-15 晚)。
> 那样跑,评分最高的一批品会连续命中同一家适配分最高的店,**好货全堆在
> 一家**,其余店只拿到尾货 —— 而分配的目的正是把货**分散到多个店铺**。
> 三条落到实现上的约束:
> 1. **超配惩罚必须是每分配一组就即时生效**(下面第 2、4 步),不能整批
>    算完再罚 —— 罚项滞后一批,前一批照样堆完了;
> 2. **同一轮内按"店铺剩余缺口"轮转**:每次挑下一组时,优先喂**当前缺口
>    占比最大**的店,而不是每次都问"这一组最适合谁";
> 3. **好品要跨店铺打散**:同一大类的高分组不许连续落同一家店,
>    实现见批次 A2 的"轮转 + 超配惩罚"双保险,方案表按店铺分布出直方图,
>    **首批 dry-run 必须人眼看这张分布**——一家独大就是参数没调对。
>
> 这条改的是**顺序与配额**,不改硬闸:品牌排他、类目准入、渠道、容量
> 四道闸任何时候都不许为了"分散"而放宽。


**梯队 1 = ACTIVE ∧ 在册 ∧ 有在线产品**(在营主力)先完整跑一轮;
**梯队 2 = ACTIVE ∧ 在册 ∧ 空店**只分梯队 1 消化不完的剩余池。
(空店目标缺口天然巨大,同池竞争会把最好的品吸走。)

每轮内品牌组按组内最高产品分降序排队;对每组:

1. 候选店 = 过全部硬闸的店。**类目闸**:组主大类 ∈ 店已有类目;店类目 < 2
   时"开新大类"也算候选但适配分吃惩罚项,方案表高亮「将为店 X 开辟第 2
   大类 Y」,一批内一家店最多开 1 个新大类;开新类目额外要求 PT 实证
   (§三.3)。**渠道闸**:产品渠道 = 店「配送限制」列;该列未填的店不接
   自由流分配(摘要点名补填)。
2. 店铺适配分 = w1·类目份额(该店该大类近 90 天销量份额,样本稀按 §八
   层级回退混全局基线)+ w2·gap_i + w3·剩余容量比 − w4·(本批已接量/quota_i)
   (超配惩罚,好货不堆一店)。
3. 取分最高店,**事务内**占品牌 + 逐 ASIN 占产品 + 核类目(占不到 = 并发
   被抢,顺延次优店);打平 → 剩余容量比 → 轮转。
   ⚠ 这里的"分最高"是**罚过之后**的分:第 2 步的 w4 超配惩罚已按该店本批
   已接量扣过,所以连续喂同一家店时它的分会一路走低,自然让位。
4. 每分配一组即时扣该店 quota,后续组看到更新后的世界。
5. quota/容量耗尽后剩余组标「本批未分」留池等下批——与产品分不及格的
   「淘汰」**分开计数**,方案表两个口径都可见。

### 7.6 产品分(0~100,低于淘汰线不分)

## 八、销量统计维度化

**事实表 + 维度视图,统计与"店"解绑**(2026-08-12 所有者指正:两年订单里
必有已不存在的店,只按店统计会错很多数据)。

事实表 = `orders.order_lines`(行级:店×SKU×日期×数量×金额)。店名原文永存、
死店行不迁不改不删(店铺本就被刻意排除出行身份)。引擎**不直接按店 JOIN
订单**,只读四个维度聚合视图(A2 建,只读不落表):

| 视图 | 维度 | 范围 | 消费方 |
|---|---|---|---|
| 产品销量档案 | asin | **全店含死店** | 产品分:"卖过且卖得动"是最强选品信号 |
| 品牌销量档案 | brand_key | 全店含死店 | 品牌组排序参考 |
| 类目需求基线 | 大类 × 月份 | 全店含死店 | 需求基线 + 季节性系数(两年数据可算) |
| 店×类目近况 | store × 大类 × 近 30/90 天 | **只算在册店** | 店铺适配分 |

⚠ 前三个视图**依赖 A1.5**(order_lines 加 asin 列,§十);店×类目视图不依赖
(走 walmart_items 主路)。

**类目归属链**:主路 `order_lines(store,sku) ⋈ walmart_items(store,sku)`
(PK 对齐,sku 大小写敏感)取 `product_type` → `risk_product_types.category`;
兜底 sku → `sku_asin.extract_asin`(numeric 形态先按 `walmart_items.item_id`
倒查)→ `products.walmart_pt` → 同 JOIN。两路都提不出 → **未归类桶,计数
可见,绝不静默丢**。

**店铺适配分层级回退**(解决店×类目样本稀):
`score = w·店×类目份额 + (1−w)·全局类目基线`,`w = n/(n+N0)`
(n = 该店该大类近窗订单数,N0 初值 30,配置化)。新店零样本 → 全靠全局
基线 + 目标缺口,天然冷启动。

**死店三答**:
1. **数据层**:订单/KPI/快照历史行全部永存原文——死店的两年销量**全部沉淀
   在产品/品牌/类目/季节四个维度继续起作用**,只有"店×类目"这一层天然
   只属于在册店,一条数据都不报废;
2. **占用层**:死店的品牌/SKU 走 store_release 显式释放,释放后其品曾经
   "卖得动"的历史反而是回到自由池后的加分项;
3. **映射层**:死店**不需要**店名映射;需要映射的只有"还在营但改过名"的店。
   库内 store 列已混三个来源(order_sync=凭证表现名 / order_history_import=
   excel 旧名 / kpi_history_import=旧 sheet 标题),无程序化映射——旧名行
   自动只进全局三视图,不污染店×类目视图;真需要时以一张小映射表在**视图层
   折叠**,永不改写事实表。

## 九、与现有链路的接缝

### 9.1 list_new 闸门链

现"全局 ASIN 去重"读在线快照(`walmart_items`),产品下架即失守,且被死店
冻结行污染 ⇒ 改为**占用闸**(读 claims),快照只做辅助;品牌占用检查同轮加入。
分配是计划层,**不受 list_new 日配额闸影响**(配额只约束执行节奏)。

### 9.2 上架表写入(两处硬约束)

1. 现有五个写函数全部按行号定点写,**无一能新建行** ⇒ 追加新行要照
   `services/maint_sheet.append_records` 的水位模式另写(`ops.cursors` 水位 +
   逐 50 行验空防漂移 + 500 行/块 + **每块成功即落水位**)。
2. 分配要写的 A/B/D/E 四列**正是审核批次 D 投影的目标列**(`product_audit`
   明写"投影在批次 D 切换日开闸")⇒ **写列权责必须与批次 D 同一次拍板**,
   否则投影器与分配器互相覆盖。E 列写 `pass`(飞书侧词表,不是 approved)。

### 9.3 事件账本

`services/product_events` 的 `record_many` 对未登记事件码抛错 ⇒ 分配留痕前
**先登记新码**。

### 9.4 死店冻结行(已知缺陷,处置归 A1)

`catalog_sync` 只扫在册店 ⇒ 已从凭证表删除的店,其 `walmart_items` 行
**永久冻结为"在架"**,污染三处:①飞书在线产品总表投影;②**list_new 全局
去重闸**(不分店);③maintenance 每轮空转生成意图再"凭证缺失跳过"。

处置:`store_release --store X --execute` 时同步
`UPDATE catalog.walmart_items SET missing_since = now() WHERE store = X AND
missing_since IS NULL`——店铺终止后商品事实上已全部下架,这是**校正观测**
不是伪造(dry-run 先列行数)。存量清单由 `alloc_audit` A4 给出。

⚠ 判"不在册"必须用 `stores.registered_names()`(凭证表全集),**不能用
`load_stores()`**(它按启用/ClientId/代理筛过,会把"代理没配的在营店"
误判成死店,而死店清单直通整店释放)。
