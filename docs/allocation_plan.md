# 第一部分 现行设计(唯一权威)

## 一、需求(所有者原述,未变)

1. 一个品牌只能同时存在于一家店(采集数据带真实品牌;提交沃尔玛仍
   Unbranded,两不冲突);
2. 一个产品(ASIN)只能同时存在于一家店;
3. 一个店最多做**两个大类目**;
4. 一个店只做**一种配送方式**(FBA 或 FBM)(2026-08-13 追加);
5. 约束在**前期产品进来后的分配阶段**执行;
6. 店铺终止运营 → 释放其占用的品牌与产品;暂停 → 绑定保持;
   救不回来的暂停店 → 手动点名释放;
7. **只要没决定停止运营,品牌和产品就不能出现在其他店——即使当前没有上架
   到这个店也不行**(占用与在线状态无关);
8. 分配本身是复杂决策:好坏产品要筛,店铺间怎么分要参考订单/销量/销售额/
   在线数/容量等数据。

## 二、核心原则

**占用是决策台账,不从在线快照推导。** 在线产品(`catalog.walmart_items`)
是观测,天天抖动;归属(占用)是决策,只有"分配"和"释放"两个显式动作能改。
两者解耦,占用才稳定——与病历(`product_events`)的"决策/观测"分层同源。

**释放只走显式动作,没有任何代码自动释放占用。** 这是稳定性的根本保证。

**永久决策要更硬的证据。** 上架错了是一条 feed 失败,占用/开类目错了是
**永久烧掉一个槽位**(无自动释放)。凡属永久决策的动作,证据门槛单独提高
(体现在 §三.3 的 PT 实证要求)。

**`catalog.claims`**(品牌占用 + 产品占用,一行一个占用):

| 列 | 说明 |

**没有 store_categories 表、也没有 store_channel 表**(2026-08-15 定稿):

(类目1/2/3、配送限制),引擎只读不写。这样定的三个理由:
① 所有者改一格就生效,不需要跑任何 workflow;
② 引擎**永不自行开类目**,"开新大类要不要实证 PT"这个难题直接消失

③ 类目档案本就是运营决策不是系统状态,放系统里反而要造一套同步机制。
判定唯一出处:`services/store_targets.allowed(cfg_row, category)`。

## 六、生命周期与释放

1. **占用产生于分配,不产生于上架**:产品分给某店的那一刻,事务内同时
   占品牌 + 占产品 + 核类目 + 核渠道,占不到就不能分给这家店。之后下架、
   清零、从未真正上架,占用都不动。品牌已属于某店的产品只能"定向"去那家店
   (还得过它的类目/渠道/容量),去不了就淘汰。
2. **暂停 = 什么都不做**,占用天然保持;SUSPENDED 店的在线行仍计入冲突统计。
   停用只是暂时不给它分新货,**不代表别店可以来拿它的品牌与产品**——
   店没在关,它的东西就还是它的(§一 所有者原述)。
   ⚠ 2026-08-15 晚一度被误改成"当作全新店(不建占用)",所有者当即纠正:
   **口径没变,仍是「暂停不释放、占用保持」**。要某店暂时不接新货走 2a,
   那是配额开关,与占用归属是两件事。
2a. **"暂时不给某店分货"的正确做法**:限额表「**单店最大在线数**」填 `0`
   (`services/store_targets.accepts_allocation`,所有者定稿 2026-08-15 晚)。
   与类目、配送限制同一治理方式——改表格一格就改行为,不建表、不改代码,
   **也不动占用**。**三态不许压成两态**:`0` = 所有者按下"不接货";
   `None` = 还没填(报告点名补填);`>0` = 参与。写成 `not max_online`
   会把没填的店一并算成不接货 —— 它于是永远分不到货,而且不报错。
3. **终止 = 显式释放**:workflow `store_release --store X`(dangerous,默认
   dry-run 列清单):该店全部 active 占用置 released(reason=terminated)、
   **同步把该店 walmart_items 行标 missing_since**(§九.4;`-p mark_offline=0`
   可关)。类目与渠道是飞书配置,不归它管。
   **留痕在 claims 表自身**(released 行 + reason + 时间),不写 product_events
   ——事件账本的入账边界是"产品生死与观测事实",占用是决策,两边各记一份
   反而要维护两套口径。
4. **手动个别释放**:同 workflow `--brand` / `--asin` 精确释放。
   除以上两条显式路径外无任何自动释放。
5. **TERMINATED 只触发"可释放资格"**:审计发现"已终止仍有 active 占用"→
   告警列清单 → 人跑 store_release。KPI 是外部观测,误报若触发自动释放,
   品牌被别店占走后不可撤销。

## 七、分配引擎

### 7.1 候选池

从 `catalog.products` 取:审核 approved ∧ 有标题 ∧ PT 有效 ∧ 大类查得到 ∧
产品未被占用 ∧ 渠道已知(FBA/FBM;未知的不参与,计数可见)。
逐层收窄的真实数字由 `alloc_audit` P1 给出。

★ **不满足选品条件的直接不进池**(所有者 2026-08-21 拍 Q3)。分成两类,
**落点不同,别混**:

**(一)产品自身的硬闸** —— `product_score.gate`,与店无关:

| 挡什么 | 依据 | 处置 |
|---|---|---|
| 落地价算不出 | price 或 shipping 为 NULL | 补采集 |
| 库存未知 / 不足 | `amz_source.MIN_INVENTORY` | 补采集 / 换货 |

**(二)店铺条件的并集** —— `alloc_plan._pool_reach` / `_in_reach`,
**全部从限额表同一行读,一个字面量都不写**(所有者 2026-08-21 原话:「每一个
店,对于配送时间的限制、配送方式的限制都在表格里……分配的时候会读取表,这些
信息都能拿到,再拿着条件去拿品过来分配」):

| 条件 | 并集怎么取 | 什么情况整条不筛 | 处置 |
|---|---|---|---|
| 渠道 | 各店「配送限制」的集合 | 无 | 开一家该渠道的店 |
| 货期 | 各店**生效上限**的 **max**(未填回落 7 天) | 无 —— 不存在"不限"的店 | 放宽某店该列或换货源 |
| 品类 | 各店准入品类(折五品类)的并集 | **任一店三列全空 = 不限制** | 给某店开这个品类 |

★ **「配送时长限制」未填的回落方向 2026-08-21 改了**:原本分配这边"未填 = 不限",
而上架链 `store_limits.cap_for(caps, store, MAX_LEAD_DAYS)` 未填回落 7 —— 同一列
两条链方向相反。所有者当日拍板统一到 **7**。改前的风险是静默的:只要有一家店空着
这一列,池口并集就变成"不限",慢货与货期未知的货全池涌入,而且不报错。
连带口径:**采不到配送天数的货现在没有任何店会收**(改前未填的店会照单全收)。

⚠ **"任一店放开就整条不筛"不是偷懒,是并集的定义**:只要存在一家店可能要它,
这件货就有去处,池口没资格替发牌阶段做决定。反过来写(取 min / 取交集)会把
一家店的严格条件强加给所有店,静默丢货。

⚠ **一度写死过 7 天,当天撤回**(2026-08-21):货期是逐店的,写死一个全局数
两头错 —— 有店填 10 就白白丢掉它能卖的货,全店都填 5 又让 6~7 天的货空占池子。

⚠ 用的是**参与分配的店**(在册 ∧ 规划内 ∧ participates),不是 `registered_names()`
——后者连已终止的店都在里面,拿死店的限额表行去放宽池口 = 货进来了没人接。
已满的店仍在集合里(`room` 是发牌阶段的事),所以"今天恰好满了"不会被读成
"我们不做这个渠道"。**由此 `stores` 的构建必须排在候选漏斗之前**。

归因**按第一道拦下它的条件**分,货期里再分「超期」与「没采到」——后者补一次
采集就能进池,合并成一个数就把能救的那批藏起来了。

### 7.2 分配单元 = 品牌组

按 `services/brand_key` 分组:
- 品牌组整组定店;组过大时可只分组内产品分 top-N,其余不占 product 占用
  ——品牌已占用,后批这些品自动定向同店,排他不破;
- 真·无品牌(brand 与 manufacturer 皆占位符)= 逐 ASIN 为单元,只占 product。

### 7.2b 规划范围外的店(不参与,但数据照用)

`registry.alloc_excluded_stores()` 命中的店(当前 = 店名含「谭总」)整体
退出分配体系:不进候选店集合、不占品牌与产品、不判类目与渠道、其在线
商品不进冲突清单、也不参与 list_new 的全局 ASIN 去重(⇒ 规划内的店**可以**
与它们重复上同一品牌/产品)。
**销量数据不受影响**:它们的订单照常进产品/品牌/类目三个全局销量维度,
是别的店选品时的有效信号。排除的是"归属"不是"数据"——这条区分要记牢,
把数据也一起排掉会白白丢掉一大块选品依据。

### 7.3 两条流水

- **定向流**(品牌已被占用):只能去占用店;过该店硬闸(状态 ACTIVE ∧ 在册 /
  类目 / 渠道 / 容量 / 黑名单)→ 淘汰行进方案表并注明被哪道闸拦下(所有者
  可选择先点名释放品牌再重分)。定向流**不分梯队**(品牌绑定是强制路由)。
  ★ **类目按件筛,不整组淘汰**(2026-08-16 所有者追问"定向流淘汰是什么意思"
  时更正):去向店已被品牌占用**固定死**,不存在"该给谁"的竞争,按件筛是
  良定义的、且严格更划算。原来的写法会因为组大类取件数多数派,让"60% 厨房 /
  40% 家居"的品牌被只做家居的占用店**整组拒收**——连那 40% 本来就能上架的
  家居商品一起。剪完要**重算组分与组大类**,否则方案表上写的是被剪掉那批的
  属性。⚠ **自由流不许这么做**:那边组的完整性参与竞争(组分与 size 都会变),
  按件筛等于让同一个品牌在不同店之间被拆开,品牌排他就破了。
  ★ **定向流也吃批量**,且容量**累计**判(见 #16f)。
  ★ 淘汰摘要按「**店 × 缺的大类**」摊开:光给总数没法动手,摊开后所有者一眼
  看出"给 A085 开厨房能救回多少件"——那是他真能做的决定。
- **自由流**(品牌未占用 / 无品牌):走 7.4~7.5 打分匹配。

### 7.4 店铺经营水平(所有者定稿 2026-08-15 晚,**取代原"固定除以 30"**)

> **原文这里写的是**「近 30 天日均 GMV 分母固定用 30(与日目标自洽),不用
> "有记录天数"」。**这条是错的,所有者当日指出**:三个月里店铺暂停过,
> 那段时间根本不存在销售额,拿日历天数当分母会把"停过业"读成"卖得差"。
> 后果是反向的 —— 缺口被高估 ⇒ 配额被放大 ⇒ **停过业的店反而被灌最多货**。

**分母一律是「在售天数」,不是日历天数。** 数据现成:`ops.store_kpi_daily`
逐店逐日一行,带 `store_status` / `items_online` / `orders_count` /
`sales_amount`。

```
窗口 = [as_of − N 天, as_of)             # N 默认 90;与冲突判定共用 sales_window
rec_i     = 窗口内该店**有 KPI 记录**的天数
active_i  = 其中 coalesce(upper(store_status),'ACTIVE') = 'ACTIVE' 的天数
cover_i   = rec_i / N                     # 覆盖率,低了下面的比值都不可信
items_i   = 窗口内 active 天的 items_online **均值**(不是最后一天的值)
```

⚠ **没有 KPI 记录的那些天既不算 active 也不算停用**——那是"没抓到",不是
"没营业"。所以 `active_i` 只从有记录的天里数,并且 `cover_i` 必须一起报出来:
覆盖率低就说明这家店的指标本来就不该拿来跟别人比(处理见下面的收缩)。

三个归一化指标(都用 `active_i` 当分母):

| 指标 | 算式 | 回答什么 |
|---|---|---|
| **日均净销售额** | `净额_窗口 / active_i` | 规模:这家店一天能净卖多少(退款已扣,见 7.4e) |
| **单品日产出** | `净额_窗口 / active_i / items_i` | **效率:给它一个货位值多少钱** |
| **日均订单** | `orders_窗口 / active_i` | 需求密度 |

**单品日产出是分配最该看的那个**,理由:一家 500 SKU 做 500 美元/天的店,
每个货位只值 1 美元;一家 100 SKU 做 300 美元/天的店,每个货位值 3 美元。
后者才是好货该去的地方,而只看总 GMV 会得出相反的结论。

**样本不足要收缩,不能直接用。** 与 §八 层级回退同一套写法:

```
active_i <  14  → 三个指标**一律取全店中位数**(所有者拍板:少于 14 天
                  就不信它的数据),方案表标记「样本不足」
active_i >= 14  → shrunk_i = w·本店 + (1−w)·全店中位数,
                  w = active_i / (active_i + 14)
```

为什么 14 天以下是**硬切**而不是继续收缩:那个区间的比值噪声大到没有
信息量(一单大额就能把单品日产出抬十倍),而收缩公式在 `active=2` 时
仍会留 12.5% 权重给它。**新店 active_i=0 落在同一条规则里**,
天然冷启动,不需要特判。

`cover_i < 0.3` 的店在方案表单独标记「KPI 覆盖不足」——不是不给货,是提醒
所有者这家店的三个指标都是中位数顶上来的,不代表它真实水平。

### 7.4a 配额(目标缺口 + 效率,双驱动)

```
gap_i   = clamp01((日目标销售额_i − 日均GMV_i) / 日目标销售额_i)   # 分母已是在售天数
room_i  = max(0, 单店最大在线数_i − (在线数_i − 待下架数_i))       # ★ 预支下架名额
eff_i   = 单品日产出_i(收缩后)/ 全店单品日产出中位数,clamp 到 [0, 2]
need_i  = w_gap·gap_i + w_room·min(1, room_i/批量) + w_eff·min(1, eff_i/2)
quota_i = min(room_i, ceil(批量 × need_i / Σ need))
```

**`w_eff` 是新增项,它防的是"只看缺口"这个陷阱**:一家店缺口大,可能是因为
它卖不动,再猛给货只是把库存压过去。gap 与 eff 有意拉反方向 —— 要找的是
**低于目标、但有能力**的店。权重初值 **`w_gap=0.6 / w_room=0.25 / w_eff=0.15`**(所有者拍板 2026-08-15 晚:
**把货给离目标最远的店** ⇒ 缺口主导);进配置文件,首批 dry-run 对着方案表砍,
要纯缺口驱动就把 `w_eff` 设 0。

**★ 容量预支**:`room` 要减掉「待下架数」(类目不符 + 渠道不符 + 冲突输家
三份清单里属于该店的行)。所有者是**一边下架一边上架**的,不预支的话,
一家马上要空出 300 个货位的店会被算成"满了",这一批一件都分不进去。
待下架的货**已经不产生占用**(§三.16 类目闸在 `claimable` 里),所以那些
品牌与 ASIN 此刻就能分给别人,**不必等实际下架完成**。

### 7.4b 反堆积:分层轮转发牌(所有者定稿 2026-08-15 晚)

§7.5 的警告说了"不许按分数顺序分配",这里是它的具体做法。

```
1. 自由流候选按**组分降序**切成分数层。★**按排名切,不按分数区间切**:
   每层恒定装 层厚×组数(初值 10%),层数 = 1/层厚,与店铺数无关;
2. **逐层**发牌;层内不按"这一组最适合谁",而按
       已接量_i / quota_i  升序轮转 —— 谁离自己的配额最远谁先拿;
3. 该店过不了硬闸(品牌/类目/渠道/容量/黑名单)→ 顺延下一家,不回头;
4. 每发一组即时更新 已接量_i,下一次挑人看的是更新后的世界;
5. ★**层内上限** `cap_i = ceil(quota_i × 层厚 × 松弛)`(松弛初值 1.3):
   本层已接满 cap 的店跳过(**跳这一家,不是放弃这一组**)。被上限压回来的组
   排进**下一层的队头**优先重试;最后一层还压着的走**收尾扫描**(取消上限
   再走一遍,只剩配额与容量闸)—— 不丢货。
```

⚠ **压回来的组必须排在下一层前面,不能攒到最后再扫**(2026-08-16 回归测试
逼出来的):攒到最后的话,它想去的那家店会先被后面几层的货填满配额,
上限于是从"晚一点拿"变成"永远拿不到",**净发牌量下降**。两种写法都
"看起来在均衡",但一种是倒扣 —— `tests/test_alloc_engine.py` 钉死了这一条。


★ **为什么按排名而不是按分数区间**:实测分数堆在 40~70(P10 28 / 中位 50.6 /
P90 63.4),按"每 10 分一档"切,50~60 一格能装三分之一的货,90~100 一格
凑不出 10% —— "最好的那层"根本不成层。按排名切则层厚随分布自适应:
中间密的地方层薄(2.6 分宽),两端疏的地方层厚(28 分宽),**每层货量恒等**。

★ **为什么还要层内上限**(2026-08-16 模拟发现,不是拍脑袋):光靠轮转不够。
轮转管的是**顺序**,管不住**某张牌只有一个人能接** —— 大类覆盖稀时(某个
大类只有一两家店的类目闸放行),那些组无视轮转顺序全落到它们头上;配额小的
店被这么喂几次,就把配额的一大截花在了顶层。用真实店铺数据模拟(批量 3000、
10 家店),顶层验收比值 H007=1.41 / M001=1.37,**双双越界**;加上限后
1.28 / 1.26 全部落回区间,而**全批发牌量一张不少**(2841 → 2841),
只是把它们在顶层多吃的挪到后面几层。

为什么分层:光靠"超配惩罚"只能保证**数量**分散,保证不了**质量**分散 ——
一家店可能先把 top 10% 吃到配额上限,后面全是尾货给别人。分层之后,
**每一层都按配额比例分给所有店**,好货天然摊开。

**验收指标(必须进方案表,不是"希望如此")**:

| 指标 | 期望 |
|---|---|
| 每个分数层的**店铺分布直方图** | 与各店 quota 占比接近 |
| 每店「拿到的 top 层数量占比」 ÷ 「quota 占比」 | 落在 [0.7, 1.3];超出就是参数没调对 |
| 单店本批接货量 / 全批 | 不超过 `1.5 × quota_i/Σquota` |

**首批 dry-run 必须人眼看这三个数**。一家独大 = 参数错了,不是"模型判断"。

### 7.4c 产品没有销量怎么办(常态,不是异常)

实测绝大多数候选没有任何订单史。三条纪律:

1. **缺失不等于 0**,禁止 `or 0`(§三.8)。该项**不计入**,权重按比例
   **摊回其余信号** —— 不是给它 0 分,那等于惩罚"新品"。
2. **层级回退取代理信号**(§八):
   `该 ASIN 销量 → 该品牌销量 → 该大类需求基线 → 全局基线`,
   逐级按 `w = n/(n+N0)` 收缩,N0 初值 30。
   ⚠ 前两级**依赖 A1.5**(`order_lines` 加 asin 列),没做之前只有
   「该大类基线」这一级可用 —— 这是 A2 的硬前置,不是可选项。
3. **销量只加分不减分**(§三.8):卖过且卖得动是强信号;没卖过只是没信息。

### 7.4d 货位值:**量出来的历史均值,不是预测**(所有者追问 2026-08-15 晚)

「好货放进去能产出多少」**预测不了**,也不该假装能。能量的是这个:

```
货位值(店 i, 大类 c) = 净销售额(i,c,窗口) / active_i / 在线数(i,c)
                                 ↑            ↑         ↑
                            退货已扣      在售天数   该店该大类的在线件数
```

三条纪律:

1. **按大类分,不按整店分。** 整店单品产出会被该店的品类结构污染 ——
   一家店 Home 卖得好、Fashion 卖得烂,整店均值对两边都不对。要回答的是
   "在这家店放一个 **Home** 货位值多少钱"。
2. **净销售额,不是 GMV。** 见 7.4e。GMV 不扣退货是虚高,而退货率是店铺
   履约能力的直接体现 —— 两家店同样卖 1000 美元,退掉 400 的那家实际只
   产出 600,还多赔一次运费和一个差评。
3. **它是历史均值,不是对新品的预测。** 样本不足(新店、新开的类目)按
   `w = n/(n+N0)` 收缩回**全店同大类中位数**,n = 该店该大类近窗订单数。
   真正的预测能力要等 §7.8 的决策快照攒够 2-3 个月,A3 回归出来才有。

**产品分与货位值不相乘。** 相乘等于假装能算出"这个品在这家店能卖多少钱",
那是没有依据的。两者分工明确:

| 量 | 决定什么 |
|---|---|
| 产品分 | **发不发、先发谁**(淘汰线 + 排序) |
| 货位值(店×大类) | **发给谁**(同一组货,哪家店的这个类目货位更值钱) |

### 7.4e 退货:销量口径一律用净额(所有者追加 2026-08-15 晚)

「不止看销量,还要看退货」。落到三处:

| 用处 | 口径 | 数据源 |
|---|---|---|
| 店铺货位值 / 日均 GMV | **净销售额 = GMV − 退款额** | `orders.return_lines`(PK `(return_order_id, order_line_id)`,按 `order_line_id` 回连 `order_lines`;`refund_total` / `refunded_qty`) |
| 产品分·退货率 | 该 ASIN 的 `退货件数 / 售出件数`,**减分项** | 同上,依赖 A1.5 的 asin 列 |
| 店铺履约 | KPI 表 `return_rate` / `refund_rate` 列 | `ops.store_kpi_daily`(展示用;阈值未拍板前不进公式,同 8 率) |

⚠ **历史期算不出退货**(§四"历史行的三条语义"):`order_history_import`
只导销售六列,「退款原因」「统计状态」都没进来,`return_lines` 也只有
API 期的数据。所以:
- **窗口跨历史期时,退货率按"没数据"处理,不当"零退货"**(禁 `or 0`);
- 净销售额在历史期 = 毛额,**方案表必须标注该店的窗口有多少天落在历史期**,
  否则 API 期的店会因为扣了退货而显得比历史期的店差,那是口径不同不是经营差。

### 7.4f 「待下架数」怎么来(所有者追问 2026-08-15 晚)

三份处置清单里属于该店的行,**按 `(店, SKU)` 取并集去重**:

```
待下架_i = |{ (店,SKU) : 店 = i } ∩ (
              alloc_类目不符下架清单.csv
            ∪ alloc_渠道不符下架清单.csv
            ∪ 两份冲突处置.csv 里 处置='下架' 的行 )|
```

⚠ **必须去重**:同一行可能同时是"类目不符"和"冲突输家"(很常见 ——
类目闸本来就是冲突判定的硬闸)。不去重会把 room 高估一倍,配额跟着虚高。

⚠ **预支只影响配额,不放宽容量硬闸**:

| 环节 | 用哪个数 | 为什么 |
|---|---|---|
| 算 `quota_i`(谁多分谁少分) | `max_online − (在线数 − 待下架数)` | 乐观:马上要空出来的货位应该参与分配 |
| `list_new` 真上架时的容量闸 | **当前真实在线数** | 保守:下架没做完就上架会真的超 `max_online` |

分配是**计划**,上架是**执行**。计划可以预支,执行时按实际核实 ——
所以方案表要标注「本店 N 件依赖 M 件下架先完成」,让所有者知道先后顺序。
清单是**建议**不是事实:所有者未必全下架,所以预支天然乐观,
方案表把「当前 room」与「预支后 room」两个数都列出来,差多少一眼可见。

### 7.4g 三个参数定稿(所有者拍板 2026-08-15 晚)

| # | 参数 | 拍板 | 落到哪 |
|---|---|---|---|
| 5 | 效率 vs 缺口 | **把货给离目标最远的店** ⇒ `w_gap` 主导 | `w_gap=0.6 / w_room=0.25 / w_eff=0.15`;要纯缺口驱动把 `w_eff` 设 0 |
| 6 | 在售天数下限 | **少于 14 天就不信它的数据** | 硬规则,见下 |
| 6a | 薄样本的**缺口**怎么算(08-15 晚追加,两条决策冲突后拍板) | **缺口用实测、效率用中位数** —— 两条各管各的量 | 「不信薄样本」管的是**比值**(货位值,一单大额能抬十倍);「把货给离目标最远的店」管的是**缺口**,而一件没卖的空店确实最远。拿中位数替换缺口会让它显示成「平均水平」排在真卖得动的店后面 —— 方向反了。生产实测:82杨乾良 在线 0、一件没卖,却和中位数店 M001 并列缺口 66% |
| 7 | 分数层层厚 | **10%** | §7.4b 发牌分 10 层 |
| 7a | 层内上限松弛(08-16 模拟追加,非所有者拍板 —— **默认值待首批 dry-run 核** ) | **1.3** | `cap_i = ceil(quota_i × 层厚 × 1.3)`。数值直接取自验收指标上界 [0.7, **1.3**],所以它不是独立参数:调宽验收区间就得同步调它,否则上限比验收线还严,层层压回收尾扫描 |

**关于 5,已提示过的风险记在这里,不再重复**:缺口大有可能正是因为这家店
卖不动,纯缺口驱动会把货压给最卖不动的店。所有者已知情并选择缺口优先;
`w_eff=0.15` 保留为**同缺口时的次级排序**,首批 dry-run 看方案表再砍。

**关于 6,`active_i < 14` 是硬规则不是收缩**:

```
active_i <  14  → 三个指标**一律取全店中位数**,方案表标记「样本不足」
active_i >= 14  → shrunk = w·本店 + (1−w)·中位数,  w = active_i/(active_i+14)
```

两段而不是一段的理由:14 天以下的比值噪声大到没有信息量(一单大额就能
把单品日产出抬十倍),收缩公式在 `active=2` 时仍会留 12.5% 的权重给它,
而所有者的判断是"这种数据一点都不信"。**新店 active=0 落在同一条规则里**,
不需要特判 —— 天然冷启动。

### 7.4h 主序重排:切口切产品,组队挪进片内(所有者定稿 2026-08-22)

**所有者原述**(2026-08-21 立案时给过一次,这次照它核代码才发现没落对):

> 候选池 5 万,5 家店各要 2000 ⇒ 取排名前 10000 的**品**,分 10 片,每片 1000 个
> 产品,**然后再给这 1000 个产品按品牌分组**……每一片都是如此。

**代码当时的顺序是反的**:建店 → 漏斗 → **全池组队** → 算配额 → 按组分切口 →
发牌。所有者一眼看出后果:「**你会把大量排名靠后的产品拉到前面来**」。

机制在这两行:组分取 `max(组内产品分)`,切口按组分排序。一个品牌里
1 个 95 分的爆款 + 40 个 41 分的平庸品 ⇒ **整组按 95 分排进切口,41 分的
40 件全跟着进来**。

**顺带查出一个单位错配**:`cut = int(total_q * HEADROOM)` 里 `total_q` 的单位是
货位(产品),却拿去切**组**的列表。平均一组 k 件 ⇒ 牌堆实际装了约
`1.5×k×total_q` 件,比标称多 k 倍,而报告还写着"候选切口 N 组(×1.5)"。

#### 新主序

```
建店 → **算配额** → 候选漏斗 → 按产品分降序
  └ 轮次:取 N = 各店剩余差额之和 件
      └ 分 10 片(按**产品数**)
          ├ 片内组队(组分 = 0.7×均分 + 0.3×最高)
          ├ 定向组(已被占用的品牌)直接归占用店
          └ 自由组轮转:离配额最远的先挑(**相对比值**)
             每店每片上限 = **片产品数 ÷ 店数**
             ⚠ **定向与自由共用这一个上限**(所有者 2026-08-22 更正)
      └ 收尾扫描:去掉片内上限再走一遍
  └ 还有店没满、池里还有货 ⇒ 取下一个 N,再来一轮
```

#### 三个待定点的拍板(所有者 2026-08-22)

| # | 问题 | 拍板 | 备注 |
|---|---|---|---|
| Q1 | 组分用什么 | **加权**:0.7×均分 + 0.3×最高 | 纯取最高分的道理("一个爆款带一堆平庸品的品牌不该整体掉下去")**前提是切口在组这一层**;切口挪到产品层后,平庸品在切口就挡住了,均分不会再拖累爆款。留 0.3 让有爆款的品牌仍然优先 |
| Q2 | 轮转排序键 | **相对比值**(已接量 ÷ 配额) | 绝对差额会让大店连着先手、小店总排后面 |
| Q3 | 每片每店上限 | **片产品数 ÷ 店数** | 固定值 —— 不随店挑完缩水,可复现优先。原述是"剩余待分配产品的 1/5",拍板时简化 |
| Q3′ | 定向组占不占这个上限 | **占**(2026-08-22 当日更正) | 不占的话,一家手上老品牌多的店可以每片先把定向吃满、**再照常参与自由流轮转** —— 上限就管不住它了,而上限存在的理由正是"别让一家店把最好的那批拿光"。实现上三段(压回的 / 定向 / 自由)共用同一个 `take_ct` 与同一个 `cap`,走同一次 `_try_place` |

#### 由此消失/改变的四样东西

- **`HEADROOM` 删除**:留余量由"一轮不够取下一个 N"取代,按实际缺口续取比拍倍数准,单位错配一并消失;
- **`LAYER_SLACK` 删除**:片内上限不再跟配额挂钩,没有可松弛的对象;
- **「搭车上架」结构上不可能**:组只由取到的产品组成,而取到的全在切口之上 ⇒ 组内不可能有低于切口线的件。报告那一节撤掉(报恒为 0 的数是噪声),不变量由测试钉着;
- **组会被切口截断**:40 件的品牌遇上总配额 12 ⇒ 这一轮只取它排名最高的 12 件。剩下 28 件排队,而且因为品牌已经占给这家店,下一轮只能回同一家 —— 排他不破。

#### 取货量为什么远大于货位数(所有者 2026-08-22 追问)

生产首跑:**可分 26,852 个货位,实发 26,785,取货却是 50,457 件 / 35 轮**。

因为**取货是按产品取的,而取进来的产品未必发得出去**:过不了闸、占用店不接、
组队时被剔除。每轮取「各店剩余差额之和」件,发不满就再往下取一轮 ——
所以总取货量 = **为了填满配额一共往下翻了多深**,高于货位数是正常的。

问题出在报告没把这笔账对上,而且**三个数不同单位**:取货报件、实发报货位、
「未发出」报的却是**组数**。人只能自己去减,减不出来。

⇒ 补两样:

1. **取货对账行**:`实发 + 过不了闸 + 定向淘汰 + 定向按件剪掉 + 组队剔除 = 取货`。
   ⚠ **对不上就把差额印出来** —— 有一笔货在实现里凭空消失的 bug,从任何单项
   数字上都看不出来,只有做减法才会露头;
2. **「未发出」补上件数**(组 / 件并排),与取货、实发同单位。

#### ⚠ 轮次护栏撞了要喊出来

`MAX_ROUNDS = 20`(每梯队)是**死循环护栏,不是模型参数**。撞上它而停 ≠ 发完了。

静默截断在这里最危险:报告会说"未发出 N 组",读起来像**闸挡的**,而真相是
**我们根本没往下取**。所有者会跑去改类目/渠道配置,而该做的是提高护栏、
或者先查为什么每轮发得这么少。

⇒ `deal` 记 `capped_tiers`(**只在"既没填满配额、池子也还有货"时才记** ——
正常收敛跑满轮次不算,混起来会天天误报,人就学会忽略它了),报告里 ⚠⚠ 双标点名。

#### 两个必须分开的东西(实现时踩到的)

1. **本轮新落的归属要喂回组队。** 同一个品牌可能被切口切在两片里;第一片发给
   了 A,第二片再遇到它**必须还归 A**,否则一个品牌在一轮之内被拆给两家店。
2. **「已占品牌」≠「同轮续发」。** 上一条的机制会让第二片看到它"已经有主",
   但那是本轮自己刚发的。合并报的实测后果:**一条占用都没有时,报告照样说
   "定向流 45 件(补齐已占品牌)"** —— 所有者会去查一个空台账。两者在漏斗与
   摘要里分开计数。

### 7.5 匹配循环(两梯队 + 事务内占用)

> **⚠ 不许"按分数从高到低顺序分配"**(所有者定稿 2026-08-15 晚)。
> 那样跑,评分最高的一批品会连续命中同一家适配分最高的店,**好货全堆在
> 一家**,其余店只拿到尾货 —— 而分配的目的正是把货**分散到多个店铺**。
> 三条落到实现上的约束:
> 1. **超配惩罚必须是每分配一组就即时生效**(下面第 2、4 步),不能整批
>    算完再罚 —— 罚项滞后一批,前一批照样堆完了;
> 2. **同一轮内按"店铺剩余缺口"轮转**:每次挑下一组时,优先喂**当前缺口
>    占比最大**的店,而不是每次都问"这一组最适合谁";
> 3. **好品要跨店铺打散**:同一大类的高分组不许连续落同一家店,
>    实现见批次 A2 的"轮转 + 超配惩罚"双保险,方案表按店铺分布出直方图,
>    **首批 dry-run 必须人眼看这张分布**——一家独大就是参数没调对。
>
> 这条改的是**顺序与配额**,不改硬闸:品牌排他、类目准入、渠道、容量
> 四道闸任何时候都不许为了"分散"而放宽。


**梯队 1 = ACTIVE ∧ 在册 ∧ 有在线产品**(在营主力)先完整跑一轮;
**梯队 2 = ACTIVE ∧ 在册 ∧ 空店**只分梯队 1 消化不完的剩余池。
(空店目标缺口天然巨大,同池竞争会把最好的品吸走。)

每轮内品牌组按组内最高产品分降序排队;对每组:

1. 候选店 = 过全部硬闸的店。**类目闸**:组主大类 ∈ 店已有类目;店类目 < 2
   时"开新大类"也算候选但适配分吃惩罚项,方案表高亮「将为店 X 开辟第 2
   大类 Y」,一批内一家店最多开 1 个新大类;开新类目额外要求 PT 实证
   (§三.3)。**渠道闸**:产品渠道 = 店「配送限制」列;该列未填的店不接
   自由流分配(摘要点名补填)。
2. 店铺适配分 = w1·类目份额(该店该大类近 90 天销量份额,样本稀按 §八
   层级回退混全局基线)+ w2·gap_i + w3·剩余容量比 − w4·(本批已接量/quota_i)
   (超配惩罚,好货不堆一店)。
3. 取分最高店,**事务内**占品牌 + 逐 ASIN 占产品 + 核类目(占不到 = 并发
   被抢,顺延次优店);打平 → 剩余容量比 → 轮转。
   ⚠ 这里的"分最高"是**罚过之后**的分:第 2 步的 w4 超配惩罚已按该店本批
   已接量扣过,所以连续喂同一家店时它的分会一路走低,自然让位。
4. 每分配一组即时扣该店 quota,后续组看到更新后的世界。
5. quota/容量耗尽后剩余组标「本批未分」留池等下批——与产品分不及格的
   「淘汰」**分开计数**,方案表两个口径都可见。

### 7.6 产品分(0~100,低于淘汰线不分)

## 八、销量统计维度化

**事实表 + 维度视图,统计与"店"解绑**(2026-08-12 所有者指正:两年订单里
必有已不存在的店,只按店统计会错很多数据)。

事实表 = `orders.order_lines`(行级:店×SKU×日期×数量×金额)。店名原文永存、
死店行不迁不改不删(店铺本就被刻意排除出行身份)。引擎**不直接按店 JOIN
订单**,只读四个维度聚合视图(A2 建,只读不落表):

| 视图 | 维度 | 范围 | 消费方 |
|---|---|---|---|
| 产品销量档案 | asin | **全店含死店** | 产品分:"卖过且卖得动"是最强选品信号 |
| 品牌销量档案 | brand_key | 全店含死店 | 品牌组排序参考 |
| 类目需求基线 | 大类 × 月份 | 全店含死店 | 需求基线 + 季节性系数(两年数据可算) |
| 店×类目近况 | store × 大类 × 近 30/90 天 | **只算在册店** | 店铺适配分 |

⚠ 前三个视图**依赖 A1.5**(order_lines 加 asin 列,§十);店×类目视图不依赖
(走 walmart_items 主路)。

**类目归属链**:主路 `order_lines(store,sku) ⋈ walmart_items(store,sku)`
(PK 对齐,sku 大小写敏感)取 `product_type` → `risk_product_types.category`;
兜底 sku → `sku_asin.extract_asin`(numeric 形态先按 `walmart_items.item_id`
倒查)→ `products.walmart_pt` → 同 JOIN。两路都提不出 → **未归类桶,计数
可见,绝不静默丢**。

**店铺适配分层级回退**(解决店×类目样本稀):
`score = w·店×类目份额 + (1−w)·全局类目基线`,`w = n/(n+N0)`
(n = 该店该大类近窗订单数,N0 初值 30,配置化)。新店零样本 → 全靠全局
基线 + 目标缺口,天然冷启动。

**死店三答**:
1. **数据层**:订单/KPI/快照历史行全部永存原文——死店的两年销量**全部沉淀
   在产品/品牌/类目/季节四个维度继续起作用**,只有"店×类目"这一层天然
   只属于在册店,一条数据都不报废;
2. **占用层**:死店的品牌/SKU 走 store_release 显式释放,释放后其品曾经
   "卖得动"的历史反而是回到自由池后的加分项;
3. **映射层**:死店**不需要**店名映射;需要映射的只有"还在营但改过名"的店。
   库内 store 列已混三个来源(order_sync=凭证表现名 / order_history_import=
   excel 旧名 / kpi_history_import=旧 sheet 标题),无程序化映射——旧名行
   自动只进全局三视图,不污染店×类目视图;真需要时以一张小映射表在**视图层
   折叠**,永不改写事实表。

### 9.4 死店冻结行(已知缺陷,处置归 A1)

`catalog_sync` 只扫在册店 ⇒ 已从凭证表删除的店,其 `walmart_items` 行
**永久冻结为"在架"**,污染三处:①飞书在线产品总表投影;②**list_new 全局
去重闸**(不分店);③maintenance 每轮空转生成意图再"凭证缺失跳过"。

处置:`store_release --store X --execute` 时同步
`UPDATE catalog.walmart_items SET missing_since = now() WHERE store = X AND
missing_since IS NULL`——店铺终止后商品事实上已全部下架,这是**校正观测**
不是伪造(dry-run 先列行数)。存量清单由 `alloc_audit` A4 给出。

**批量:`store_release -p dead=1`**(2026-08-22 建,所有者要一次性清干净)。
它就是把上面那条**对每一家不在营的店各跑一遍**,不是另一套逻辑。用法:
**把不再运营的店的「启用」取消勾选**(不必删行,历史凭证留着),再跑。

判据不写进代码 —— 店铺名录是会变的业务数据,写死在代码里下次开新店就得改
代码(铁律 3)。

三道拒跑闸,每一道都对应一种"看起来像死店、其实是我们自己错了":

| 闸 | 触发 | 为什么不能放过 |
|---|---|---|
| 凭证表读不到 / 读回空 | 飞书挂了 | 拿不到真值时**不许降级**,更不许当成"全死了" |
| **近似名撞车** | 库里「A085 朱丽霖」↔ 在营「A085朱丽霖」 | 名字漂了不是店没了。自动对齐 = 替所有者决定两个字符串是同一家店,猜错一次就把在营店整店下线 |
| 一家都不保留 | 店名格式整体对不上 | 所有店同时终止的概率,远小于格式对不上 |

⚠ **规划外 ≠ 不在营**:判定只看「启用」,**不看** `alloc_excluded_stores`
(「谭总」那些)—— 它们不参与分配,但货是真在卖的。
⚠ 两张名单(清理 / 保留)**全列不截断**:这条命令唯一的人工控制点就是它们。

### 9.5 冲突判定先看已有占用(所有者定稿 2026-08-22)

所有者原话:「**那张表要问有没有被占用。因为有的品牌可能是已经被占用的呀,
如果不看这个,给出的建议就是不可靠的,甚至完全相反的建议**」——
他已经按上一版建议下架过一批、也按分配名单上架过一批。

改之前 `alloc_audit` / `alloc_survey` **零处读 `catalog.claims`**:冲突表完全
由在线行算出来,只回答"同一个键此刻在几家店的货架上同时出现"。

**为什么占用不是又一级阶梯,而是先于阶梯**:占用是**决策**不是观测(§二),
没有任何自动释放。品牌已经占给 X,报告却按销量算出"留 Y" —— 人照做以后
X 的货没了、品牌还锁在 X,**谁也上不了**。这不是判得不准,是判反了。

判定顺序:**类目/渠道硬闸 → 已有占用 → 销量降级阶梯**。

| 形态 | 结论 | 依据 |
|---|---|---|
| 占用店在这组里、且过硬闸 | 留占用店 | `BY_CLAIM` |
| 占用店**在这组里没有在架行**(占位≠上架,上一轮定了还没上) | 仍留占用店,别家全下架 | `BY_CLAIM` |
| 占用店有货、却被类目/渠道闸挡下 | **不改判给第二名**,报出来先释放 | `CLAIM_STUCK`(归 `NEEDS_HUMAN`) |
| 占用店手上的货全都在 | 不进清单(正常状态) | — |

第三种最要紧:直接改判给第二名等于**绕过 `store_release`**(全系统唯一释放
路径)—— 报告没有资格替人撤一条不可逆的决策。

**顺带补上一个此前完全看不见的洞**:只有一家店在卖、而这个品牌占给了另一家 ——
按"跨店"数它不是冲突(只有一家),所以旧版从不报;而 `claim_audit` 只查
**占用店自己**的货踩没踩闸。两边都不管,这条侵占就永远没人知道。现在归
`BY_CLAIM` 报出来。

⚠ **占用读不到时不静默退回销量阶梯**:那正是会给出相反建议的那条路。报告
显式打「本轮没看占用」,csv 的「已有占用」列整列写「(本轮没读到)」——
空列有歧义,分不清"确实没占用"与"我们没查"。

### 9.4a 在营判据统一到「启用」(所有者定稿 2026-08-22)

所有者原话:「**应该以我在店铺凭证表中,勾选是否启用为准。这个是否启用的
判定,是由某个基础模块统一确认的吧?所有工作流都会遵循的标准**」——
答案当时是**没有**。判断埋在 `stores._normalize` 的循环里,和 ClientId、代理
两条过滤混成一体,没有任何函数单独回答得了"这家店还在不在营"。

于是分配链六处拿 `registered_names()`(**连启用都不看**)当在营判据:
**所有者勾了停用的店照样占着品牌、照样用冻结行拦着别的店上架。**

抽出 `stores.is_enabled()` 单一谓词 + `stores.enabled_names()`,三层分清:

| 函数 | 回答 | 谁该用 |
|---|---|---|
| `registered_names()` | 在不在**册**(含停用) | 只有"查无此店 vs 在册但停用"这种报错分流 |
| **`enabled_names()`** | 在不在**营** | **判死店、判占用、判分配范围,一律用它** |
| `load_stores()` | 现在能不能**调 API** | 真要发请求的链(还筛 ClientId/代理) |

⚠ **「启用」是意图,ClientId/代理是技术就绪**,两者不许合并 —— 合并的两个
方向都严重:拿 `load_stores()` 判在营,「在营但代理没配的店」被当成死店而
整店下线;拿 `registered_names()` 判在营,停用店被当成还在营。

已换的六处:`alloc_plan` / `alloc_stores` / `alloc_backfill` / `claim_audit` /
`alloc_audit` / `store_release -p dead=1`。这条已提进 **CLAUDE.md 工程规范**。

⚠ 判"不在册"必须用 `stores.registered_names()`(凭证表全集),**不能用
`load_stores()`**(它按启用/ClientId/代理筛过,会把"代理没配的在营店"
误判成死店,而死店清单直通整店释放)。

**Q2 的答案否掉了两个方案,留痕防重提**:

- ❌ **方案 B(品牌 × 大类排他)**:侵权责任跟着**商标**走,不跟品类走。

  论据用错了维度,结论跟着错。
- ✅ 只剩**方案 A**(整组归店保排他 + 按件落地),见 §11.3 #5。品牌排他一个字不动。

**残余损耗是有意的**:五品类口径下仍有 105,571 件(16.3%)属于"跟着品牌到了

# 第三部分 代码盘点(按功能;2026-08-16 上线前归拢)

分配链共 **7 条 workflow + 9 个 service**,合计约 4,000 行,回归 195 条
(全仓 1,202 条)。**没有一条 workflow import 另一条 workflow**;services 只
向下依赖 services / api / registry;全链唯一碰外部系统的是 `store_targets`
(读飞书限额表)—— 其余全是库内计算,**不调沃尔玛、不调 LLM**。

## 12.1 四类职责

分配链的每一块只干四件事之一。判断新代码该放哪儿,先问它属于哪类:

| 类 | 干什么 | 谁 |
|---|---|---|
| **取数** | 把散在各表的原始行捞成一个口径统一的池子 | `product_pool` `store_perf` `store_targets` `alloc_survey` |
| **判分** | 给产品/店铺一个可排序的数,并说清这个数怎么来的 | `product_score` `store_perf` |
| **决策** | 谁去哪家店 —— 纯函数,不碰 IO | `alloc_groups` `alloc_engine` |
| **落痕** | 决策写进台账,并能对账、能撤 | `claims` `alloc_backfill` `alloc_plan` `claim_audit` `store_release` |

## 12.2 七条 workflow

**入口一律 `python cli.py <name> [-p k=v] [--dry-run]`。**
危险的三条(`dangerous=True`)**缺省即真跑**;加 `--dry-run` 才只打印将做什么
(2026-08-16 口径反转,此前是"默认 dry-run、真跑加 --execute")。

| workflow | 危险 | 干什么 | 产出 |
|---|---|---|---|
| `alloc_audit` | 否 | **动工前的存量勘察**:每店在线数、品类/大类分布、渠道、配置缺口,以及跨店的同 ASIN / 同品牌冲突 | 6 张 csv(类目建议 / 渠道不符下架 / 类目不符下架 / 店铺总览 / 同 ASIN 冲突 / 同品牌冲突)。⚠ 类目那两张 2026-08-22 起**判据在品类层、证据在 26 类层**,见 §A.5b |
| `alloc_stores` | 否 | **店铺侧体检**:在售天数归一的三个经营指标 + 缺口 + 货位值,回答"这家店还能吃多少货" | `alloc_店铺经营水平.csv` |
| `alloc_products` | 否 | **产品侧体检**:漏斗、五个信号的覆盖率、分数分布。⚠ 覆盖率那栏最要紧 —— 权重再合理,信号采不到就是空的 | `alloc_产品分.csv` |
| `alloc_backfill` | **是** | **一次性回填**:把已经在线的商品倒推成占用台账,让新系统认得存量 | 落 `catalog.claims` |
| `alloc_plan` | **是** | **主流程**:出这一轮的分配方案并落占用。全链唯一会大批量落不可逆占用的地方 | `alloc_分配方案.csv` + `alloc_未入选.csv` + `alloc_品牌组.csv`,落 `catalog.claims` |
| `claim_audit` | 否 | **台账对账**:已落的占用现在还站得住吗(店的类目/渠道/货期后来改过) | `alloc_该释放占用.csv` + 可直接粘的 `store_release` 命令 |
| `store_release` | **是** | **撤**:整店 / 点名品牌 / 点名 ASIN / `-p from_csv=` 批量释放 / **`-p dead=1` 批量清死店**(凭证表里没有的店) | 改 `catalog.claims`;整店释放时一并标 `walmart_items` 下线 |

### 例行一跑(复核 pass)

四条只读/dry-run 的串成一条,`&&` 保证前一条挂了就不往下走:

```bash
python cli.py alloc_audit && \
python cli.py alloc_stores && \
python cli.py alloc_products && \
python cli.py alloc_plan
```

跑完看四组数、审 `alloc_分配方案.csv`,确认无误再单独一条:

```bash
python cli.py alloc_plan --execute
```

⚠ **`--execute` 故意不放进串里**,这不是省事没做:落占用不可逆,而串起来
跑意味着"最后一条的输入是前三条的输出、人却没看过"。安全铁律要求 dry-run
之后**人眼确认**才允许 `--execute` —— 一条命令跑到落库,这道确认就没了。

⚠ 每条 `cli.py` 各自拿锁、各自写 `ops.runs`、各自发飞书通知 —— 这是对的:
中间挂了能从 `ops.runs` 看出断在哪条,而不是一条大记录说"失败了"。

**钉窗口右端**(复现某天的结果,或跨零点跑怕窗口漂移)给每条加同一个
`as_of`;`days`(店铺 90)与 `sales_days`(产品 365)有默认值,不用传:

```bash
D=2026-08-16; python cli.py alloc_audit -p as_of=$D && \
python cli.py alloc_stores -p as_of=$D && \
python cli.py alloc_products -p as_of=$D && \
python cli.py alloc_plan -p as_of=$D
```

### 特殊时候才跑的三条

- `alloc_backfill --execute` —— **只做一次**,新系统认存量用。跑完接
  `claim_audit` 清掉回填时闸没拦住的;
- `claim_audit` —— **每次改完飞书限额表都要补跑**(开类目 / 换渠道 /
  调配送时长限制),已有占用不会自己失效;
- `store_release` —— 占用落错了、或 `claim_audit` 报出该释放的,拿它撤。
  **批量走 `-p from_csv=`,别把 csv 最后一列几百条命令逐条粘**(2026-08-22
  实证:所有者一次粘了 ~600 条)。两个理由:
  · 逐条粘漏一条你不会知道;`from_csv` 一次跑完并报"命中 / 没命中"两个数;
  · 单条命令按 (类型, 键) 释放,**不带占用店**;`from_csv` 按三条件释放 ——
    占用在你出表之后换了店的那些会自然放不到,而不是把新店的好占用误放。
  ⚠ csv 那一列的命令 2026-08-22 前**没有 shell 引用**:品牌键含空格/逗号/
  `&` 的(`cor cordium` / `knape & vogt` / `phillips safety products, inc.`)
  被 shell 拆开,匹配不到任何占用 ⇒ 报「无任何可释放的行」**并退出码 0**,
  人以为放掉了其实一条没动。已改用 `shlex.quote` 并补上 `-p store=`。

## 12.3 九个 service

| service | 行 | 干什么 | 为什么单独一块 |
|---|---|---|---|
| `brand_key` | 58 | 品牌名归一化 | **占用键的唯一出处**。两处各写一遍归一化,同一个品牌会变成两个键,排他直接失效 |
| `sku_asin` | 54 | SKU → ASIN 清洗 | 同上,唯一出处。沃尔玛侧的 SKU 与亚马逊 ASIN 靠这一条规则对齐 |
| `claims` | 161 | 占用台账 `catalog.claims` 的**唯一**读写口 | 占用是决策不是观测,**没有任何自动释放**;PG 偏索引 `UNIQUE (kind, claim_key) WHERE status='active'` 兜底排他 |
| `store_targets` | 167 | 从飞书「上下架限额表」读准入类目 / 渠道 / 容量 / 日目标 / 配送时长限制 | 全链**唯一**碰外部系统的地方。字段名只从 registry 常量取 |
| `store_perf` | 209 | 在售天数归一的三指标 + 配额输入 | 店铺"现在什么水平"的唯一算法。窗口 90 天 |
| `alloc_survey` | 590 | 在线商品富化、冲突判定、店铺画像,以及**共享闸谓词** `offends_category` / `offends_channel` / `claimable` | 占用闸与处置清单必须用**同一套**判断 —— 两边各写一遍,回填会锁进一批下架清单同时要求下架的货 |
| `product_pool` | 184 | 候选池取数一处定义(池 / 窗口销量 / 全历史 / 退货 / 黑历史) | 体检与真分配必须看到**逐字相同**的池子;两边各写一遍,体检说"可分配 27 万"而分配只认 19 万 |
| `product_score` | 318 | 产品分 0~100 + 硬闸 | 口碑 ≤60 + 销量加分 ≤40 − 罚分;淘汰线 40。窗口 365 天 |
| `alloc_groups` | 110 | 候选 → **品牌组**(一张牌)的组装 | 品牌排他 ⇒ 组是原子的。组分 = 组内最高分、组大类 = 多数派、组货期 = 最长、组渠道 = 多数派且少数派剔除 |
| `alloc_engine` | 363 | **分层轮转发牌**,纯函数 | 把牌堆按名次切 10 层,层内按「已接量 ÷ 配额」轮转;层上限 + 顺延到下一层头部 + 末尾扫尾。另出验收指标「顶层比值」 |

## 12.4 两个数据口径(全链共用,别在别处再算一遍)

- **两个窗口**:`days=90` 管**店铺经营水平**("这家店现在什么水平"),
  `sales_days=365` 管**产品销量信号**("这个品到底卖没卖过")。合成一个都会坏
  —— 详见口径 #17a。
- **占位 ≠ 上架**:候选池排除**已在架**的 ASIN,不排除**已占位**的。占位只是
  决策的落库记录,上架才是执行 —— 详见口径 #16l。

## 12.5 上线前必须知道的三条

1. **真跑之前一定先 `--dry-run` 并人眼过方案表。** ⚠ 2026-08-16 起缺省即真跑,
   默认值**不再替你挡** —— 这条从"默认值兜底"降级成纪律,所以更要自觉。
2. **占用不可逆(靠人撤,不靠系统)。** 分配落的是 `catalog.claims`,
   没有任何自动释放路径。落错了走 `store_release`,不要改库。
3. **配置改完必跑 `claim_audit`。** 飞书限额表一改(开类目 / 换渠道 /
   调配送时长限制),已有占用可能就站不住了 —— 它不会自己失效。
