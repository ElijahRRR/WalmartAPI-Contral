# 前端设计计划

> **这份文件是设计画布的施工图**,不是给别人的提示词(2026-08-18 改:所有者
> 决定由本仓会话直接用 `design` 生成画布,不再外包给设计侧)。
>
> 里面的表名、状态取值、工作流名都是从代码核出来的真值(有脚本核对,零编造);
> 画出来的每一个状态、每一列,都要能对上库里真有的东西 —— 画一个库里没有的
> 状态,等于给以后的实现挖一个坑。
>
> 所有者定稿:①只给所有者一个人用,飞书表格照旧归运营;②前端能真的触发危险
> 工作流,但**危险操作强制先 dry-run 预览**。

## 一、这个系统是什么

沃尔玛(Walmart Marketplace)多店铺(约 45 家店)运营的自动化系统。本质是
**66 条工作流脚本 + 定时调度 + 一个 PostgreSQL 中心库**,已在生产运行:
11 条自动任务(电脑 launchd 2 条高频 + 智能体 9 条每日/每周),其余 55 条手动。

它每天自动做这些事:拉订单并审核、扫在架商品、从亚马逊采集产品数据、
审核产品能不能卖、上架新品、改价改库存、删掉出问题的商品、收集黑名单、出日报。

## 二、⚠ 决定整个交互模型的那条约束

**这个系统的写路径全世界只有一道门:命令行 `python cli.py <工作流名>`。**

没有 REST API、没有 ORM、没有"点一下就改数据库"。任何改变世界的动作(改价、
上架、删商品)都是**启动一个工作流进程**,它跑几秒到几十分钟,过程写日志,
结束时往 `ops.runs` 写一行,并发一条飞书通知。

所以这个前端**不是 CRUD 后台**,是两件事:

1. **观察窗** —— 直读 PostgreSQL 的表与视图(只读);
2. **发令台** —— 触发工作流 → 看它跑 → 看结果。

⚠ **不画"编辑这个产品的价格然后保存"这种表单。** 那样的写入通道不存在,
也不该存在 —— 价格是工作流按业务规则算出来的,人改的是**规则**(在飞书配置表
里),不是单条结果。这个系统里**唯一要填的表单是"工作流参数"**
(`-p limit=3000` / `-p store=A085` / `-p l3=off`),那才是要认真设计的输入形态。

### 危险操作的交互形态(21 条工作流复用同一个组件)

`DANGEROUS=True` 的 21 条会真的写沃尔玛、不可逆。它们有统一约定:加
`--dry-run` 就是空跑、只算不做、打印"这一轮会做什么"。所以界面上必须是两步:

```
[预览这一轮会做什么] → 破坏面(要删哪 N 个 SKU / 要改哪些价 / 影响哪些店)
                     → 人眼确认 → [执行] → 实时进度 → 结果摘要
```

这不是我加的谨慎,是项目写在铁律里的纪律。低危/只读工作流可一键直跑,
但界面要**一眼看出**哪个按钮是危险的。

### 运行的四种结局(必须四种,不是两种)

| 退出码 | 含义 | 界面 |
|---|---|---|
| `0` | 成功 | 正常 |
| `1` | 失败 | 报错 + 日志尾部;⚠ **不给"自动重试"按钮** —— 这些链会写沃尔玛,重跑的代价可能是重复提交 |
| `3` | 没抢到锁,上一轮还在跑 | ⚠ **不是失败**,是"它正忙"。中性样式,**不许用红** |
| `2` | 工作流名写错 | 配置问题 |

## 三、信息架构

### 导航:左侧栏分组 + 全局命令面板

十个域直接平铺会变成一堵墙。按**你多久看一次**分三组:

```
每天看
  ├ 总览            ← 首页。今天系统怎么样 + 需要我管的事
  ├ 订单待人工       ← 唯一一个每天真的要动手的队列
  └ 运行记录        ← ops.runs

按需查
  ├ 产品            ← 列表 / 详情(含产品病历)
  ├ 上架            ← 闸门漏斗 / UPC 池 / 变体组
  ├ 维护与清理       ← 建议 → 执行 → 落定
  ├ 订单            ← 订单行 / 售后 / 绩效 / 对账
  ├ 黑名单中心
  ├ Feed 追踪
  ├ 采集监控
  └ 店铺

操作
  ├ 工作流          ← 66 条,按业务域分组,危险的走两步
  └ 调度            ← 11 条自动任务(只读展示)
```

**全局命令面板(⌘K)** 是给单用户重度使用者的主要入口:输 ASIN 直接跳产品详情、
输工作流名直接开触发面板、输店铺名跳店铺页。十个域的导航是给"不知道要找什么"
时用的,⌘K 是给"知道要找什么"时用的 —— 后者才是日常。

### 页面之间必须能跳

排查时人是顺着链路走的,断一处就得回去重新搜:

```
运行失败 → 那条工作流的日志 → 涉及的 SKU
产品详情 → 它的 feed 提交 → 回执错误码
维护建议 → 产品详情 → 病历时间线
上架漏斗某一档 → 被拦掉的那批行 → 逐行拦截理由
店铺 → 该店的在架商品 / 配额 / KPI
```

## 四、三种页面形态(组件库由此而来)

十个界面其实只有三种骨架,认出它们就不必为每个页面各造一套组件:

| 形态 | 用在哪 | 关键组件 |
|---|---|---|
| **列表 + 详情** | 产品、订单、店铺、feed、运行记录 | 大数据量表格(虚拟滚动 + 服务端分页)、筛选栏、详情抽屉/整页 |
| **阶段流转** | 上架闸门漏斗、维护建议(建议→执行→落定)、审核分层 | 漏斗图、阶段徽章、"卡在这一档的有哪些" |
| **触发运行** | 工作流面板、调度 | 参数表单、预览破坏面、实时输出、结果摘要 |

## 五、十个界面各自的数据源与业务含义

### 1. 总览 / 驾驶舱(首页)

一眼看清"系统今天还好吗":

- **今天的自动任务跑得怎么样** —— 11 条自动任务的时间轴,每条的状态、耗时、摘要
  首行。数据源 `ops.runs`(每次运行一行:工作流名、开始/结束时间、状态、摘要全文、
  谁触发的)。
- **当天的次序是硬约束**,时间轴要能体现出这条链路关系:
  `产品链 13:00 → 黑名单 15:00 → 审核 18:10 → 上架 20:00`,谁提前谁就是拿昨天的
  数据做今天的判断。
- 几个关键数:在架商品数、待审产品数、待处置建议数、在途 feed 数、UPC 池余量。
- **需要人管的事**(最重要的一块):失败的运行、卡住的 feed、凭证失效的店铺、
  UPC 池告急、待人工审核的订单。

### 2. 产品界面

系统里"产品"有**两个侧面**,界面要能对照着看 —— 这是整个业务的核心张力:

| 侧面 | 表 | 是什么 |
|---|---|---|
| **亚马逊侧** | `catalog.products` + `catalog.snapshots` | 我们从亚马逊采集来的:标题、品牌、价格、库存、类目、运费、图片。`snapshots` 是历次采集快照(有 `catalog.latest_snapshot` 视图取最新一条) |
| **沃尔玛侧** | `catalog.walmart_items` | 沃尔玛后台现在实际是什么样:在架状态、价格、库存、SKU、UPC |

一个产品的身份是 **ASIN**(亚马逊标准码)。要有:

- **产品列表**:多维度筛选(店铺 / 审核状态 / 在架状态 / 品牌 / 类目 / 有无采集数据 /
  货期 / 价格区间),支持大数据量(几十万行)。
- **产品详情**:两侧数据并排对照 + **完整生命周期时间线**。
  时间线的数据源是 `catalog.product_events` —— 这张表是产品的"病历",记录它从入库、
  审核、上架、观测、下架到删除核验的每一件事。事件类型:入库 / 审核通过 / 审核拒绝 /
  上架提交 / 删除提交 / 停用提交 / 维护提交 / 问题归类 / 商品出现 / 商品消失 /
  状态变更 / 删除已核验 / 删除未生效。
  ⚠ 这条时间线是回答"这个商品当初为什么被删/被拒"的**唯一**答案来源,是详情页
  最有价值的部分,别做成小角落里的折叠区。
- **审核结论**:`audit_status` 四态 —— `NULL`(未审)/ `pending`(待定,类目解不出
  或 LLM 故障)/ `approved` / `rejected`,附拒绝理由。
  ⚠ `pending` 是**中间态不是结论**,视觉上要和 approved/rejected 区分开。

### 3. 订单界面

- **订单行列表**:数据源 `orders.order_lines`。⚠ 一行的身份是
  `订单号 + SKU`(店铺和行号都不参与身份,同订单同 SKU 必合并为一行)。
- **订单审核结论**:`audit_status` 取值是中文 —— `通过` / `拒绝` / `钓鱼` / `待人工`。
  审核是六道闸依次判:钓鱼(邮编)→ 采集完整性 → 商品一致性(标题相似度)→
  配送时长 → 采购方匹配 → 限价。
  ⚠ **任一道给不出确定答案一律"待人工",绝不当通过。** 所以「待人工」不是异常,
  是正常的一档,而且是**人要真的去处理的那一档** —— 界面上它该有自己的工作队列,
  不是筛选器里的一个选项。要能看到"是哪一道闸把它判成待人工的"、以及支撑判断的
  证据(亚马逊快照、截图、算出来的成本与限价)。
- **售后单** `orders.return_lines`、**绩效问题订单** `orders.perf_events`
  (配 `orders.perf_event_spans` 视图看影响范围)、**对账明细**
  `orders.settlement_lines`(配 `orders.settlement_by_line` 视图)。

### 4. 黑名单中心

四类黑名单,来源方向**不同**,界面必须让人分得清(现实中混过一次):

| 表 | 方向 | 是什么 |
|---|---|---|
| `catalog.brand_blacklist` | 飞书 → 库 | 人工归拢的品牌总清单 |
| `catalog.brand_err_hits` | 库 → 飞书 | **程序自产**:沃尔玛后台报错里拿到的品牌 |
| `catalog.asin_blacklist` | 库(自产)+ 导入 | 永久禁售的 ASIN(六类:禁售/品牌/知产/限类/药品/审查) |
| `catalog.seller_blacklist` / `catalog.amazon_cat_blacklist` | 飞书 → 库 | 黑名单卖家 / 黑名单亚马逊类目 |

⚠ **有一件反直觉的事必须在界面上说清**:黑名单在库里写下的那一刻**拦截就生效了**
(上架和审核读的是数据库),而飞书表格只是**投影**,晚两小时才更新。人常误以为
"表格没更新 = 还没生效"。

要能:查某个品牌/ASIN 是否被拦、看它是哪条规则哪一天入的、看拦截命中统计。

### 5. 上架中心

上架是这个系统最复杂的链路。一个产品要上架得过**七道闸门**,然后领 UPC → LLM 生成
属性 → 规格一致化 → 提交 feed。界面要:

- **展示闸门漏斗**:待上架 N 条 → 各道闸拦掉多少(非 ACTIVE 店 / 超配额 / 风控 /
  黑名单 / 全局去重 / 防呆 / 数据不全)→ 实际提交多少。这个漏斗是所有者判断
  "今天为什么只上了 40 条"的主要工具。
- **提交结局三态**(不是两态):`已提交` / `失败`(被拒,附错误码)/
  **`结局不确定`** —— 第三态是网络原因导致不知道到底提交成功没有,系统的处理是
  **不重复提交**、等自愈链收尾。⚠ 这一态必须单独呈现,它既不是成功也不是失败。
- **UPC 池**:`catalog.upc_pool`,状态 `空`(可用)/ `claimed`(已领)/ `used`(已用)/
  `conflict` / `bad_prefix`。余量告急要在总览预警。
- **变体组**:同一组产品(同款不同颜色/尺寸)要作为一组上架,界面要能看出分组
  和每组的主变体。

### 6. 维护与清理中心

系统每天扫在架商品,**产出"建议"**,再由执行件去做。这是个两段式流程,界面要
体现"建议 → 执行 → 落定":

数据源 `ops.dispositions`,状态四态:`suggested`(已建议,待执行)→
`executing`(已提交 feed,等生效核验)→ `done`(已落定)/ `withdrawn`(撤销 ——
商品自己恢复正常了)。

动作类型:`改标题` / `改价` / `改库存` / `删除` / `停用` / `反补上架`。

⚠ 每条建议都带**原因码**,而且原因码是关键信息:四条清零判据在表面上长得一模一样
(库存 12 → 0),没有原因分不出是"商品不可售"还是"没有 Buy Box"还是"缺货"还是
"货期超限";删除那类更要紧(`商品在亚马逊已下架` 和 `标题相似度 42%` 都是删除,
但正确性判断完全不同)。**原因码不能藏在详情里,要在列表上就看得见。**

### 7. Feed 追踪(沃尔玛提交回执)

所有对沃尔玛的写操作都通过"feed"提交,异步返回结果。三层台账:

- `ops.feed_log`:每次提交一行,状态 `pending` / `submitted` / `done` / `failed`
- `ops.feed_items`:SKU 级结果,状态 `submitted` / `success` / `failed` / `missing`
- `ops.feed_item_errors`:错误码明细(配 `ops.v_feed_error_stats` 视图看错误排行)

⚠ **有一种故障长得像正常,界面应该帮人发现它**:`pending` 状态的 feed 是"提交结局
不确定"的,系统不会自动补交(写操作宁停不重)。它的表现是那批 SKU 每轮都被报
"在途防重跳过 N 个"而 **N 一直不变** —— 看着像正常防重,实际是**再也发不出去了**。
如果能设计一个"在途超过 N 天的 feed"预警,那是很有价值的一块。

### 8. 调度与运行记录

- 11 条自动任务的配置一览(几点跑、跑哪几步、上一次结果)。⚠ 时间表的唯一权威在
  代码里,前端只读展示,**不要设计"在界面上改调度时间"** —— 那会造成两份时间表。
- **运行历史** `ops.runs`:可按工作流筛选,看摘要全文、耗时趋势。
- **手动触发面板**:66 条工作流按业务域分组,危险的走"预览 → 确认"两步。
  每条工作流有自己的参数(如"限单店"、"限制数量"、"关掉 LLM 层"),
  界面要能填参数。

### 9. 采集监控

产品数据来自一个亚马逊采集服务(异步批次制)。`ops.scrape_batches` 状态
`pushed` / `running` / `completed` / `timeout` / `failed`;
`ops.scrape_failures` 有逐 ASIN 的**真实失败原因**(11 类:网络 / 超时 / 被拦 /
验证码 / 解析失败 / 邮编切换失败 / 变体偏移 / …)。

⚠ 失败原因的区别是有用的:验证码换个时段重采能好,变体偏移重采一百次还是一样。
界面别把它们统一显示成"采集失败"。

### 10. 店铺视角

约 45 家店。每家店有:凭证状态(⚠ 会失效,失效时那家店整体被跳过)、
在架商品数、日/周 KPI、上下架配额、经营指标。要有店铺列表 + 单店详情。

## 六、设计系统(画之前先定死,免得每块画板各长各的)

### 场景决定密度

单用户、桌面大屏、**每天从早盯到晚**的工具。不是展示页 —— 不要大留白、
不要营销式插画、不要动效。信息密度高但有层次。

| 项 | 值 | 为什么 |
|---|---|---|
| 画板 | 1440 × 900(详情类可加高到 1440 × 1400) | 桌面大屏,表格要宽 |
| 页面 padding | 24px;卡片间距 16px | 紧凑档 |
| 表格行高 | 36px(紧凑)/ 44px(舒适),可切 | 几十万行,行高即可视条数 |
| 界面字体 | `system-ui`(生产机是 macOS) | 不引入 web 字体,本机工具没必要 |
| 数字 | `tabular-nums` | 表格里的价格/数量必须竖直对齐 |
| ID(ASIN/SKU/feedId/UPC) | 等宽 `ui-monospace`,字距略紧 | 这些是要**逐字符比对**的东西 |

### 色板(浅色为主,深色等价映射)

```
底      #FAFAFA      面板 #FFFFFF      边框 #E4E4E7
文字    主 #18181B   次 #71717A       弱 #A1A1AA
主色    #4F46E5(靛蓝)
```

⚠ **不用沃尔玛蓝**。这是我们自己的内部工具,染成沃尔玛的品牌色会让人误以为
是官方后台 —— 尤其这个界面上的按钮真的会写沃尔玛。

### ⚠ 三组必须区分的语义(这是整套设计的核心)

这三组是这个系统里最容易被界面搞混的。搞混了,等于把辛苦建的护栏在 UI 上又拆了。

**① 运行结局:四种,不是两种**

| 语义 | 色 | 形 |
|---|---|---|
| 成功 | `#16A34A` 绿 | 实心圆点 + 文字 |
| 失败 | `#DC2626` 红 | 实心圆点 + 文字 |
| **忙(退出码 3,上一轮还在跑)** | `#64748B` 石板灰 | **中性**,不许红 |
| **结局不确定(feed `Unknown` / `pending`)** | `#D97706` 琥珀 | 空心圆点(区别于实心=已落定) |

⚠ 中间两态如果都染成红,人会把"它正忙"和"它坏了"当成一回事,天天去查一个
根本没坏的东西;而真正该管的"结局不确定"会淹在红色里。

**② 只读 vs 危险操作**

| 档 | 样式 |
|---|---|
| 只读/查询 | 幽灵按钮(描边 + 中性字) |
| 常规写入(同步、投影、扫描) | 主色实心 |
| **危险(`DANGEROUS=True`)** | **深红实心 + ⚡ 图标**,且**永远先出现"预览"那一步**,不给直达 |

⚠ 危险按钮的红与"失败"的红是同一色相 —— 靠**形状**区分(按钮 vs 徽章)+ 图标。
画板上要把这两个放在一起对照,确认一眼分得开。

**③ 中间态 vs 终态**

`pending`(审核待定)、`executing`(建议已提交等核验)、`Unknown`(提交结局不确定)
都是**还没完**的状态,不该和 `approved`/`done` 一样的视觉重量:
终态用实心徽章,中间态用**浅底 + 虚线描边**,并且列表里可一键筛出。

### 组件清单(按复用度排)

1. **数据表格** —— 虚拟滚动、服务端分页、列显隐、多维筛选栏、行内跳转、
   密度切换。⚠ 这是决定这个工具能不能用的那一个组件。
2. **状态徽章** —— 把上面三组语义落成具体样式,一处定义全站用。
3. **"预览 → 确认 → 执行"流程组件** —— 21 条危险工作流复用。
4. **工作流参数表单** —— 从 `_KNOWN_PARAMS` 渲染;带危险标记与一句话说明。
5. **实时运行输出** —— 流式日志 + 进度 + 结局徽章。
6. **时间线** —— 产品病历(`catalog.product_events`)、运行历史。
7. **漏斗** —— 上架闸门;每一档可点开看被拦的行。
8. **KPI 数字块** —— 大数 + 环比 + 迷你趋势。
9. **命令面板(⌘K)**。
10. **需要我管的事** 卡片 —— 首页那块,不是列表是**待办**。

## 八、不画的东西

- ❌ **单条数据的编辑表单**(改价格/标题/库存)—— 写入通道不存在;人改的是规则。

### 为什么服务端是 Python 而不是 Next.js / SvelteKit

服务端必须存在(浏览器读不了 PostgreSQL,触发工作流是起进程),但**它必须是
Python 的**:服务端要知道「66 条工作流各叫什么、**哪 21 条是危险的**、每条收哪些
参数、调度表长什么样」——这些真值全在 Python 代码里
(`workflows/*.DANGEROUS`、`registry/schedule.JOBS`、各工作流的 `_KNOWN_PARAMS`)。

Node 服务端只能把它们**再抄一份到 TypeScript**,而抄漏一条的后果是:
那条工作流在界面上少了"预览 → 确认"那道闸,**点一下直接真跑**,且不报错。
FastAPI 则是直接 import —— 加一条新工作流,界面自动就有、危险标记自动就对。

服务端既然是 Python,Next.js/SvelteKit 最大的价值(自带服务端运行时)就用不上,
只剩当 SPA 打包器,那是 Vite 更擅长的事。

⚠ **TanStack Table 不是可选项**:产品表几十万行,普通表格组件会卡死。
headless(只给逻辑不给样式)+ TanStack Virtual 窗口化 + 服务端分页。

### ⚠ 服务端的边界(设计时按这个假设)

FastAPI 层**只做两件事**:①只读查 PostgreSQL;②起 `cli.py` 进程、流式读它的输出。

**它绝不自己写库。** 一旦绕过 `cli.py` 直接 INSERT,单实例锁、`ops.runs` 运行记录、
飞书通知这三样全部失效 —— 那是本项目「写路径只有一道门」的全部意义所在。

所以设计时可以假设这些能力存在:列出工作流(带危险标记与参数)、
起一次运行(可带 `--dry-run`)、实时拿到它的输出、查任意表与视图。
**不能**假设"保存这一行的修改"这种能力存在。
